## 1. What this is, for the frontend

Lotero is a multi-tenant management app for Brazilian lottery houses (*lotéricas*); each **Branch** is one tenant. Operators record the day's money movements and close their day; managers review closes, watch cash variance and receivables, and lock the month. Two subsystems run in parallel: the **money system** (transactions, daily close, fiado, cheques, cards) and the **people system** (time tracking).

> Domain reference (do not duplicate): `loto-specs.md` §1 (domain overview), §2 (multi-tenancy & user model), §3 (entities), §4 (enums), §5 (seed data), §6 (business rules).

## 2. Roles → UI gating

Three backend concepts the UI must respect (detail in `loto-specs.md` §2): **User** (login identity) → **BranchUser** (role in a branch: `Admin` / `Manager` / `Member`) → **Operator** (employee/history identity, optionally linked to a login, including a Manager/Admin's). The branch role grants permission; the operator link supplies own-work context. **Gestão** and **Meu turno** are navigation modes, never roles or impersonation.

**Two-stage authentication, in UI terms:**
1. `POST /user/login` or verified `POST /user/google/sign-in` → `ResponseUserLoginJson {UserId, Name, Email, ResponseToken}`; `ResponseToken` carries `Token` and `RefreshToken`. Google sign-in first obtains a single-use state/nonce challenge, and an unknown Google identity creates an account only with a matching invitation. Identity authority opens **Branch picker / session**. The required caller `UserId` supports own-row and self-recorded markers without decoding tokens (gap U backend resolved). Identity-only Profile/name, password change and logout now have server contracts (gap N backend resolved); `ResponseUserProfileJson` also reads `IsPlatformOperator` and `HasPassword` without allowing either to be edited. Their screens — Session menu, Profile, Change password, Forgot/Reset password and Invitation — are cataloged in the 0.4.6 addendum.
2. `POST /branch/session {BranchId}` → `ResponseCreateBranchSessionJson {Token, Branch}`; `Branch.Role` sets the initial home and UI gating; the server rechecks current membership and permission on every request, and `GET /branch/current` returns the live role for UI reconciliation. A branch token gates branch screens, each still subject to its role/account/operator rules.
3. `POST /user/renew-token {Value}` → `ResponseTokenJson {Token, RefreshToken}`. The renewed token is **global identity authority**, not a renewed branch session: recreate the intended branch session and recheck permission before resuming. Login replaces active refresh authority with a new session; renewal rotates its value inside the same stable server session, so another-device login prevents renewal here; web tabs sharing credentials must coordinate renewal and replacement. Failures, re-login, and scoped recovery follow [the cross-screen patterns](screens.md#cross-screen-patterns). Every API `ErrorMessages` entry renders verbatim.

**Three gating tiers:**

| Tier          | Backend filter                               | UI sees                                                    |
|---------------|----------------------------------------------|------------------------------------------------------------|
| Identity      | `[TokenAuthenticate]`                        | Branch picker / session; Session menu, Profile, Change password, Sair; Invitation acceptance |
| Platform identity | `[TokenPlatformOperator]`                 | Plataforma — Nova lotérica, after a fresh stored flag check; no branch data access |
| Branch member | `[TokenAuthenticateBranch]`                  | member-scoped views — scope is screen-specific (see below) |
| Manager/Admin | `[TokenAuthorize(Role.Manager, Role.Admin)]` | whole-branch financials, approvals, admin, lock            |

**Member scope is screen-specific:** transaction reads use **linked accounts** (§6.10 — a shared account shows *both* operators' rows; `Mine=true` narrows to the caller's own operator); mutation ownership and current-day checks are separate. Operator/time-entry reports resolve the **own operator**, with each endpoint's empty-scope fallback. Clients are shared counter work for any branch role except deactivation. The shipped Client statement access (gap H, server M7.7 Phase 5) requires an explicit Tab grant and shows complete client debt across the branch, not a partial per-drawer debt. Managers/Admins have whole-branch access subject to each command's rules.

**Navigation follows the existing IA:** Members start in Meu turno; Manager/Admin start in Gestão and, when linked to an active Operator, may switch to Meu turno. An unlinked Manager/Admin retains Close day, Fix & resubmit, approval and recall access in Gestão and may start a turno for a granted operator only as a reasoned exception (server M9.6 P2); starting their own turno and own-shift mode need the link. Manager/Admin always use the **snapshot** time-entry contract in Time-entry management, even for their own hours; the Member tap shape never follows a mode switch. The snapshot reconciles segment ids; omission does not delete a segment and existing `ClockIn` changes use the granular route. See the authoritative [route table and screen entries](screens.md#navigation--information-architecture).

## 3. Platform rule — mobile clones web

**Web and mobile ship the same screen set and semantics.** “Mobile clones web” means the same jobs, data meaning, permission gates, states, validation, financial confirmation, and return destinations. Dense tables may become readable grouped rows; browser history, keyboards, native back, touch, focus, and screen-reader interaction follow each platform. No required action depends on hover, a desktop-only gesture, or hidden columns. There is **one** catalog and one cross-screen behavior contract.

**Web branch navigation (D-M2-1, owner confirmed 2026-10-22):** branch destinations use `/f/{branchId}/…` independently per tab; identity/account/global routes stay unscoped. Switching branch clears only the initiating tab’s switched-away active context; another tab keeps its branch, filters, mode and return. The URL is untrusted intent, not authority. Session-wide login/logout and backend membership checks remain authoritative across tabs. Same-tab reload/back/forward retains validated mode/origin/focus in app navigation state as well as URL context; URL-only bookmark/copied/fresh-tab entry uses the fallback/default role mode. Duplicated browser state is revalidated, not assumed absent. Navigation never replays a mutation or carries a token/capability. Mobile keeps equivalent scoped stack parameters. See the [decision](decisions.md#d-m2-1--independent-web-branch-context) and [IA](screens.md#navigation--information-architecture).

Each app owns its UI, transport, token storage, durable local-input storage, cache and navigation. `design/` remains non-runtime; `shared/api` supplies generated API types and `shared/core` pure/injected formatting and helpers. Neither shared package owns a browser/native session or persistence adapter. MVP financial writes are explicitly **online-only**; saved-on-device input is not an offline money queue or a server save.

## 4. Screen index

One-line purpose per screen; full semantic definition (access, data, actions, states, navigation) lives in [`screens.md`](screens.md).

**Auth & session**
- **Login** — authenticate by password or verified Google, get the identity token.
- **Branch picker / session** — choose a branch, open a branch session.
- **Session menu** — identity, branch/mode, Gestão ↔ Meu turno, account actions, Sair.
- **Profile** · **Change password** — own name and sign-in method; confirmed password change that ends every session.
- **Forgot password** · **Reset password** — enumeration-safe request and the e-mailed capability that defines a new password.
- **Invitation** — preview, then join by password, Google or an existing account; or decline.

**Plataforma** *(platform operators only — never branch access)*
- **Plataforma — Nova lotérica** — operated onboarding and owner-invitation follow-up.

**Manager work queue & approvals** *(Manager/Admin)*
- **Manager Work Queue** — exception-first home, with the owner setup checklist while required setup is pending: pending approvals, not-submitted accounts, biggest unapproved variances, an earlier-days backlog banner, rejected/fix-needed closes, draft transactions blocking lock, reconciliation blockers.
- **Daily-close approval** — review a submitted close as a comparison (opening → closing → variance) with every Conferir attempt as evidence, approve or reject with reason; the approver is never the recorder, submitter or custodian (v60), except through the explicit, reasoned **Aprovar como único gestor**; **Aprovar dia do caixa** approves a cashbox day's sessions all or nothing.

**Transactions ledger** *(Member: reads + entry scoped to linked accounts, §6.10/§6.11; Manager/Admin: whole branch — same screens on both platforms)*
- **Transactions list** — filter and browse the ledger.
- **Transaction — Create (fast entry)** — operator-speed, type-driven entry with an automatic, non-blocking impact preview.
- **Transaction — Edit (correction / audit)** — restricted-field correction with full impact preview (manager-control).
- **Installment (pre-dated cheque) plan** — build and preview a cheque plan and its downstream impact.
- **Client statement (Extrato de fiado)** — one client's fiado debt and history (*quanto deve e desde quando*); entry to Receber pagamento.
- **Receber pagamento** — settle a client's fiado debt, partially or in full.

**Reports** *(Manager/Admin)*
- **Daily ledger** · **Fiado balance** · **Fiado aging** · **Open-cheque aging** (plans and standalone cheques) · **Cash-variance summary** · **Monthly reconciliation + lock** (advance `LockDate`).
- **Dashboard** — read-only overview of every report's latest facts, each linking to its full report; never the home and never an action surface.
- **Upcoming settlements** — card and cheque receivables by due date, overdue kept apart.
- **Monthly financial report** — official variance and bolão fee per Terminal/day, leftovers, hours per operator/day; no grand total.

**Operator self-service** *(Member; also linked Manager/Admin in the catalog's explicit Meu turno mode; also web)*
- **My transaction summary** · **My time-entry balance**.

**Day close flows** *(dual-mode: the Cockpit orchestrates them in Meu turno — Member by default, linked Manager/Admin through the explicit Gestão ↔ Meu turno switch — and Gestão handles their exceptions; mobile-first)*
- **Operator Day Cockpit** — the operator's "today" home; surfaces the next action across the steps below.
- **Open day** (Conferir abertura e iniciar a turno, or carry the acknowledgment on the first operation) · record transactions via **Transaction — Create (fast entry)** · **Close day** (blind count: opening visible, expected closing and difference only after **Conferir**, **Recontar** when needed, submit the confirmed attempt — v60) · **Fix & resubmit** on rejection.

**Time clock & management**
- **Clock in / out** *(Member only)* · **Time-entry management** *(Manager/Admin, including own hours)*.

**Admin & configuration** *(Manager/Admin)*
- **Operators** · **Account assignment** · **Accounts** · **Clients** *(exception: also counter — any branch role except deactivate)* · **Categories & Transaction Types** · **Products** · **Holidays** · **Settings** · **Branch members**.
- **Add employee** · **Offboard employee** — guided journeys composed from the delivered operator, assignment, invitation and membership commands; partial completion is shown, never hidden.

## 5. Promises and delivery boundaries

**Blind count and separation of duties — server M9.6 P4–P5, canonical v60 (source semantics reconciled).** The operator counts without seeing what the cashbox should hold: the opening stays visible, and the expected closing and the difference appear only after **Conferir**, as an immutable server attempt that a double press never duplicates. Editing the count after Conferir makes the result outdated; a sale or correction recorded after Conferir shows a separately labelled recalculation that is never a confirmed difference, until the operator either recounts or confirms that the count still describes the cashbox. Submit carries the confirmed attempt, so the official variance is exactly what the operator saw. A manager approves only work they neither recorded, submitted nor held; a branch with one active manager uses the explicit, reasoned and audited *Aprovar como único gestor*. The app shows these states and actions from the server's `Count` and `AllowedActions`; it never calculates a Draft difference itself. The handover screens and the app implementations (Web/Mobile M5, M7) are still to come.

**Provider settlements and bank verification — server M9.7 P3–P5, canonical v63 (semantics independently accepted 2026-11-05; app UI acceptance separate).** The manager selects an identified provider and bank account, allocates exact remaining claims, and explicitly confirms the fee with evidence or leaves it unknown. Each batch expects one bank receipt. A short statement amount remains unexplained; the product never calls it a card fee. Recolhimento in cash posts one protected internal-transfer pair, with a pending external-verification receipt; whole cheques retain their existing custody/deposit sequence. Reimbursements and bank fees require explicitly observed facts and their own typed provenance. Importing an OFX changes no balances: the manager sees every exact candidate and confirms the displayed identities, amounts and versions. A match verifies the existing receipt, never duplicates the credit. Unmatched/ambiguous evidence stays visible. Contracts are delivered here; app screens/native execution and P6/P7 reports remain with their existing owners. See canonical §3.32/§6.25 and the transaction/report blueprint increments.

**v63 banking correction semantics (semantics independently accepted 2026-11-05):** Later manager fee evidence is append-only and versioned through `POST /card-settlement/fee-evidence`; it can resolve unknown fees or discrepancies without changing original batch/receipt amounts or claim allocations. Reads expose history and the effective expectation; any revision invalidates prior matching proposals. Cofre→Bank uses dedicated recolhimento types, refusing drawer/cofre system roles. OFX line identity is semantic across export formatting, preserving raw evidence. The bank ledger alone omits the card/cheque receipt subledger; discovery lists and split/grouped statement matching remain explicit server API gaps. A full credit plus separate return debit before confirmation is unsupported pending verified bank behavior (owner: not yet verified, 2026-11-05). See transaction/report/admin blueprint increments; app UI remains with Web/Mobile M6/M8. Both review markers are v63 after independent semantic acceptance on 2026-11-05; real-app acceptance remains separate.

**Inherited v62 baseline — receivables, cheques and frozen classification, server M9.7 P1–P2 (source semantics independently accepted as the v63 baseline on 2026-11-05; whole-phase runtime acceptance separate).** A deposit, return, re-presentation or conversion is now its own dated event and never edits the original sale, even in a locked month; each event keeps when it happened and when it was recorded, and receivable reports say which date they use (the recording date by default, so an earlier report can be reproduced). Cheques can go to the cofre without being paid, be deposited in batches that each expect one bank receipt (initially pending; v63 adds statement confirmation of that receipt), come back from the bank for an identified client, be presented again, or become that client's fiado with no cash movement. Report classifications are fixed when a row is recorded: changing a type affects only what is recorded afterwards, and an open period can be explicitly reclassified with a reason; a locked month never changes. Old *pago* marks became reconstructed history, never a new payment. Screens for these flows are not drawn yet (Design 4.9.9–4.9.12, Web/Mobile M6/M8); v63 delivers card batches, bank movements and matching as described above; P&L and shortages now have v64 candidate server contracts; independent acceptance and Web/Mobile M8 UI remain pending.

**Fiado boundaries, close-form fields and the cofre — server M9.6 P6, P7, P9, canonical v61 (source semantics reconciled).** Every fiado sale at the counter now also writes the cash the drawer did not receive (*saída do caixa*) on the paired caixa's turno — there is no question to the operator and no way to record an unpaired sale; debts that never passed through the counter (opening balances, imports, returned cheques converted to fiado) will come with their own flows and never touch the caixa. Receiving a fiado payment still requires choosing how it was paid; a new lotérica starts with **Dinheiro** and **PIX**, and only cash enters the drawer. The close form carries three fields typed once per turno — **Relatório do terminal** (may be negative), **Tarifa Bolão** and **Tarifa Especial** — each kept by the server as one automatic movement, so a fee is never forgotten or entered twice; changing one after Conferir asks for a new confirmation. **Depósito Dinheiro** moves cash from the caixa to the **cofre** in one step, so the money leaving the drawer is always the money arriving in the cofre; the cofre has no turno or count of its own. A new caixa comes with its fiado account, and a new lotérica starts with the 32 expense types the shop already uses. The app never calculates these effects itself; it shows what the server returns.

**M9.5 financial reconciliation — shipped source `07cdb76` / v55 (superseded for data entry by the v61 close-form fields above).** With Q3 now confirmed and Q9 report details still pending, the fresh default product catalog excludes Tarifa Bolão and Operador: until v61 operators recorded each actual daily amount through Transaction — Create on the Terminal, as Receita/In and Entradas/In, both SameDay with no Tab/client requirement. Cash stays in the physical count. Operador’s editable label awaits shop question 9; no automatic fee, rate, receipt or required daily row is implied. Ordinary cash sales are count-only under Q5 (stock down, cash up, no transaction), confirmed by product Q5 at equal purchase/sale value (2026-10-23). These facts do not prove historical Access parity. Retired saved fee values remain visible; AA still gates their save/preview recovery, and the migration refuses retirement on unlocked retained counts. Locked history and prior opening values remain intact, so the first transition is not certified reconciled. Existing roles, locks, statuses and navigation are unchanged; `IsCashVarianceProduct` identifies the system row in responses. Q8 keeps existing fiado linked legs with no mandatory product selector. M10 opening/import remains pending; the M11 report classification and reads shipped at v56 (see MVP reporting below). The revision marker covers these source-checked financial semantics; it does not accept the unresolved AA migration/transition policy, the separate 0.4.6 addendum or real-app behavior.

## People controls — v67 candidate

The employee is an Operator, not a login or membership. A deactivated or unlinked person remains available to authorized management through historical reads. The monthly **Demonstrativo da pessoa** puts sessions under custody, official differences and explicit responsibility adjustments beside attendance, recorded items and a separate commission proposal. Unknown source/rule/initial hours appear as **Não comprovado**, **Não configurado** or **Incompleto**, never a verified zero. Unassigned/Neither evidence remains informational branch context, never an employee charge.

Manager/Admin deliberately records additions/deductions under configurable category names, reason, source month/date and posting date. A deduction requires the responsible owner's written policy; a shortage or alert creates none. A recorded item is not a cashbox expense, bank payment or paid salary. Commission uses an explicit person/date rule and evidenced source roles, with no default percentage or legacy prize allocation. **Comissão calculada** does not become **Total de itens registrados** without the dedicated deliberate record; its source rule/basis/cutoff is retained. The server supplies all totals.

A separately evidenced initial hour balance anchors the **Banco de horas**. Carry-over, period attendance, **Pagamento de horas**, **Ajuste de horas** and closing balance remain distinct, without fake punches or money conversion. Existing own-time period figures retain their published labels and access. Special draws hold name/modality/period/contest/prize; explicit official Tarifa Especial allocations retain their evidence, with undistributed/unsupported amounts visible. Print is a managerial statement, not a statutory payslip or proof of payment. Web/Mobile M8–M10 own all new UI; M10 import/go-live and real legacy data remain separate.

M9.8 v67 keeps actual fee-publication history and the original economic date separate. Branch-wide unresolved custody or missing posting proof blocks commission registration.
