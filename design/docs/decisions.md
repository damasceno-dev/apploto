## The direction to preserve

- **Character:** calm, practical, finance-oriented; clear tasks and legible records rather than decorative dashboards.
- **Palette:** deep blue navigation and blue ordinary actions; white/cool-grey work surfaces; restrained orange for the principal operator next action. Dark mode uses deep blue-black surfaces with brighter blue links and semantic feedback. Turquoise is a secondary contextual accent, not another primary CTA.
- **Typography:** system UI sans-serif, strong but compact headings, labelled controls, tabular numerals and right-aligned money. Do not introduce a downloaded display face or a CAIXA wordmark.
- **Geometry and density:** 4px spacing base; rectangular controls and panels with corners no greater than 4px; thin dividers; little elevation outside menus, drawers and dialogs. Small rectangular status badges retain text. Avatars and tiny indicator dots may remain circular.
- **Shell:** persistent grouped blue sidebar when space permits; a compact top bar with branch/session context, theme controls and avatar menu; an off-canvas drawer on narrow web. Gestão ↔ Meu turno belongs in the avatar menu and keeps the catalog's permissions and route ownership.
- **Work hierarchy:** manager exception sections with scannable tables; one clear operator next action; visible access to today's close even when another task has priority; filter controls above ledgers; form and audit sections divided by rules.
- **Themes:** light-first, with Claro / Escuro / Sistema as a device preference. Both themes belong to the implementation. Retain selected readability while supporting browser/platform text enlargement.

The [implementation handoff](../references/claude/implementation-handoff.md) supplies concrete palette pairs, authored sizes, component anatomy, motion/layers, screen families and the required adaptations. Its [style inventory](../references/claude/selected-2026-10-20/style-inventory.json) records observed values; it is **not** the M2 token system or a runtime stylesheet.

## D-M2-1 — independent Web branch context

**Owner decision explicitly confirmed 2026-10-22 in the Design M4 4.8.4 / Web M2 correction assignment:** keep branches independent per browser tab, using branch context in the URL. Every branch-scoped Web destination uses `/f/{branchId}/…`. This resolves the open D-M2-1 alternatives recorded in committed Web M2 at `7166b07`; the earlier one-branch-per-browser implementation is historical evidence, not the accepted product behavior. Identity/account/global paths remain unscoped. This is frontend navigation, not a backend route or contract change; canonical v57 markers remain unchanged.

`branchId` is untrusted context. It selects the intended branch for the session gate; current backend membership, scoped session and resource permission authorize every read/write. No bearer/refresh token, capability, operation candidate or authority claim enters the URL. Identity login/logout and credential replacement remain session-wide; this decision does not create independent users per tab or mode-based permissions. Identity renewal remains coordinated across tabs, with credential pairs confined to the app-owned secure session layer, not BroadcastChannel payloads readable by app JavaScript.

Tab A switching from branch X to Y clears A's switched-away active queries/details/versions, permission state, filters, mode, selections and return chain, stopping pending dispatch and detaching late responses. It preserves only isolated device input/recovery under X for later authorized restoration. Tab B at X keeps its own branch, filters, mode, origin and pending view; A must not broadcast a branch replacement or end B's branch context. This also holds when both tabs initially opened the same branch. Session-wide logout/login identity replacement clears app authority across tabs; password change/reset follows the existing refresh-session revocation and natural JWT-expiry semantics, not a new immediate bearer-revocation promise; branch membership revocation remains authoritative for every tab using that branch and is reconciled on the existing gate/read/foreground/403 checks. Retaining a route is not retaining permission.

Same-tab reload and back/forward preserve the URL plus app-owned non-secret navigation state: mode, parent origin chain, applied filters, section/row and scroll/focus. Apps persist enough tab-scoped context for a shared route such as `/f/X/transacoes` to keep a linked manager’s Meu turno mode on reload. Before restoration, recheck identity, URL branch, live membership/role and mode availability, then validate each origin/resource against that scope; restore focus only after the destination is ready. A valid shared route keeps the restored mode; a mode-specific route follows its owning mode. Stale or mismatched state is discarded and uses the catalog fallback/default role mode, never another branch’s context.

A bookmark, copied link or fresh tab with no app navigation state carries only the allowlisted URL branch, ids and filters: no origin, and the role’s default mode for shared routes. Browsers may copy history state/sessionStorage when duplicating a tab; duplication cannot reliably be detected. If copied state is present, treat it as an untrusted restoration candidate under the same checks, not as a guaranteed fresh entry or a privileged origin. Subsequent mode/filter/branch changes stay independent per tab. Neither restored nor URL-only navigation grants permission, restores an ended session/stale write precondition, or submits/replays a mutation. Back into a switched-away branch requires fresh scope checks. Mobile retains its equivalent scoped stack context; `/f/` is Web-only.

Web owns implementation/testing in its lane; these notes do not certify runtime behavior.
