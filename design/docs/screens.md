## Per-screen template

Every screen is defined with this fixed shape (fields marked *(where relevant)* are skipped when they don't apply, e.g. Default view on a pure form):

- **Purpose** — one line: why this screen exists.
- **Primary job** — the one thing the user must finish *fast* here; it drives what should lead.
- **Access** — auth tier (identity / branch-member / manager-admin), role, data scope (own-operator vs whole-branch).
- **Permission fallback** *(member-scoped screens)* — what a Member sees with no linked operator or empty account scope (usually the §6.10 empty short-circuit / a 403).
- **Default view / filter** *(list & report screens)* — the default date / account / operator / status, and *why* that default fits the job.
- **Data shown** — each field tagged by source: `[DTO]` direct from a shipped request/response DTO · `[derived]` computed in the UI from DTO fields · `[composed]` needs >1 endpoint joined · `[gap]` not in the contract yet (see gaps section).
- **Actions** — what the user can do, each → the endpoint it calls.
- **Audit / lock context** *(transactional / close screens)* — who submitted/approved/rejected + timestamps; `LockDate`; whether the user can still edit/act.
- **States** — loading · empty · error · success (+ meaningful variants, e.g. read-only-after-finalize).
- **Navigation** — entry points + deep-link *targets* (which screen an alert/blocker opens).

**Writing rules.** (1) An entry states what the user sees and does. Server-side invariants — concurrency tokens, coordination, cascade and floor mechanics — live in `docs/loto-specs.md` and are referenced by section, not restated. (2) When an entry states a rule for one actor, one direction, or one origin, it says whether the counterpart is deliberately excluded or merely unstated, so an unstated counterpart is a visible gap rather than a silent one.

**Conventions.** Errors render `ResponseErrorJson.ErrorMessages` verbatim (pt-BR from the backend). Branch-scoped screens require an active branch session. Lists paginate where the endpoint paginates. The [cross-screen patterns](#cross-screen-patterns) define semantic recovery, filter/source context, and durable scoped input; M4 chooses visual hierarchy and platform-specific deep-link/state-storage mechanics. **Unsaved input is kept on the device and restored only within its verified identity/branch/resource scope**, never replayed into another tenant. Close day additionally autosaves to the server on today's plain Draft (see that entry).

## Navigation & information architecture

This section is the authority for **semantic route ownership**: which authentication tier or work mode owns a destination, where a journey enters, and where it returns. It does not prescribe a sidebar, bottom tabs, item count, responsive placement, pixels, or any other visual layout; those decisions belong to M4. The route table's entry targets stay authoritative and exhaustive for semantic entry; M4 may add **navigation shortcuts** to any destination the caller can already reach (for example **Nova transação** in both modes, within the caller's account scope). A shortcut is not a new entry point: it inherits that journey's ownership and return rules unchanged.

### Session gate and home resolution

Authentication remains two-stage, and navigation never treats an identity token as permission to render branch data:

| Current authority                           | Reachable destination                | Home / gate resolution                                                                                                                                                                                                       |
|---------------------------------------------|--------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Anonymous, with no usable identity token    | Login; Forgot password; Reset password and Invitation when opened from an e-mailed capability link | A successful password or Google login receives an identity token and continues to Branch picker / session. A requested branch-scoped deep-link remains only an intent until a branch session exists; no resource is fetched before then. A capability link is not a deep-link intent: its token is consumed by its own anonymous journey (see Capability links below). |
| Identity token only                         | Branch picker / session; Session menu, Profile and Change password; Invitation acceptance for the signed-in account; **Plataforma** only for a platform operator | Selecting a branch calls `POST /branch/session`; identity alone never opens branch data. Profile/name/password/logout and invitation acceptance use identity-tier contracts. The server's platform-only guard rechecks a fresh stored flag on the same identity token for operated onboarding, without any branch membership: platform access is never branch access. |
| Active branch session, `Member`             | **Meu turno** → Operator Day Cockpit | Every plain Member lands on the cockpit, including an unlinked Member; the latter sees its cataloged setup-needed state rather than being routed into management.                                                            |
| Active branch session, `Manager` or `Admin` | **Gestão** → Manager Work Queue      | Every elevated role starts in management mode. After session creation, `GET /operator/self-context` determines whether an additional **Meu turno** mode is available; it does not alter the branch token or its role.        |

Every Web branch-scoped deep-link uses `/f/{branchId}/…` (D-M2-1); the branch id is untrusted intent, never data authority. Identity, account and platform routes remain unscoped; backend API paths do not change. Every branch-scoped deep-link first passes the same gate. With a valid session for the intended branch and sufficient permission, it opens its target; a linked Manager/Admin enters the target's owning mode when that target is mode-specific. A shared destination such as Transactions list keeps the current mode. If the target is unavailable for the caller, navigation returns to that role's available home and explains the permission or setup requirement; it never probes another branch or invents a broader scope. Once an authorized deep-linked target is open and has no source screen to return to, closing it falls back to the owning mode's home: Manager Work Queue for a management route, Operator Day Cockpit for a shift route, and the active mode's home for a shared destination. **Route guard:** Open day, Close day, and Fix & resubmit are never gated behind an operator-link check for a Manager/Admin in Gestão — the operator-link requirement is a Member / Meu turno constraint only.

### Role and mode navigation

`Role` is the server-authorized `BranchUser.Role`; **mode** is only the active navigation/home context within that branch. Switching mode does not mint a token, impersonate a Member, remove Manager/Admin permissions, or change endpoint authorization.

| Caller in the active branch                   | Initial home                         | Primary semantic destinations                                                                                                                                      | Other mode                                                                                                                                                                                                                                                                                                     |
|-----------------------------------------------|--------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Member                                        | **Meu turno** / Operator Day Cockpit | Cockpit; today's close flow; Transactions list and entry flows within linked-account scope; Clients; Clock in / out; My transaction summary; My time-entry balance | None                                                                                                                                                                                                                                                                                                           |
| Manager/Admin without an active Operator link | **Gestão** / Manager Work Queue      | Work Queue and approvals; whole-branch Transactions; Reports (including the read-only Dashboard); Time-entry management; Operators, account setup, and the remaining admin/configuration screens | None. An attempted Meu turno/Cockpit entry returns to Gestão with a full-page setup explanation (not a banner or toast) and points to Operators (then Account assignment if needed), instead of showing a broken shift mode.                                                                                   |
| Manager/Admin linked to an active Operator    | **Gestão** / Manager Work Queue      | The same management destinations as above                                                                                                                          | An explicit **Gestão ↔ Meu turno** switch exposes Operator Day Cockpit and the own-operator working set. Meu turno defaults transaction authorship to the caller's linked operator and uses `mine` on self reports and as the Transactions list default; management/on-behalf controls remain Gestão concerns. |

For a linked Manager/Admin, Meu turno is not a reduced-permission session: direct management deep-links still work and activate Gestão, while returning to Meu turno restores the cockpit as that mode's home. Actions remain role-shaped. In particular, the Member **Clock in / out** tap does not become available to Manager/Admin, because `PUT /timeentry` still requires the elevated snapshot shape for those roles; they record their own hours and corrections in Gestão → Time-entry management (Manager/Admin format, own operator). The **Gestão ↔ Meu turno** switch lives in the **user (avatar) menu** — the session menu, reachable from the top bar at every width — not in the navigation list, and is one-shot: activating it changes mode and lands on that mode's home. The same menu holds **Minha conta** (Profile), **Alterar senha** and **Sair** (see Session menu); the mode switch is independent of those account actions. For a Manager/Admin without an active link the menu still lists Meu turno, marked unavailable, with the reason and a link to Operators, so the second mode is discoverable before the person tries it. Three presentation questions left open at 0.4.1 — whether a Member's menu explains that Gestão belongs to management, whether the menu repeats **Trocar filial**, and where the current mode shows when the top bar is narrow — are presentation, not permission, and are settled by the [shell blueprint](../specs/screens/shell-and-identity.md); none adds a destination or changes a role. An active operator link with no usable account assignment still exposes Meu turno, but the cockpit shows its account setup-needed state and points back to Gestão → Account assignment.

**Meu turno unavailable — content of the full-page explanation.** The explanation an unlinked Manager/Admin receives (row above) only points; it never names a candidate operator and offers no one-click "link me". It holds: a heading saying Meu turno is not available to the person in this branch; one paragraph naming the screen that was attempted and why it is unavailable — Meu turno exists for whoever records their own till work, and depends on the login being linked to an active operator of the branch; one paragraph saying the role is unchanged and every Gestão screen remains available, followed by what to do — register as an operator in Operators, or link the login to an operator that already exists, then assign that operator a terminal in Account assignment. Actions: **Ir para Operadores** (primary), **Contas dos operadores**, **Voltar para a fila de trabalho**. It covers the case where no operator exists for the person yet. Final wording goes through the copy guidelines.

**Operator link lost mid-session.** When `GET /operator/self-context` stops returning an active linked Operator while the person is working (another administrator clears the link, or removes the last account), the person returns to the initial state, with a way to where it is fixed — linking an operator to the login, or an operator to an account — as on first entry. Unsaved input follows the durable-scoping pattern below: retained, with writes stopped and authority rechecked before recovery. Per case: link gone → Meu turno is no longer offered and the same full-page explanation applies; link kept but no usable terminal → Meu turno stays offered with the cockpit's setup-needed state. With no push contract, the client learns of the loss only at a self-context read — session creation or recreation, the mode switch, entry to a Meu turno route, and foreground return — or from a write's 403/400; the shell blueprint fixes those read points. *Open, not decided:* whether the explanation says the link **was removed** instead of the first-time wording; the client cannot tell removal from never-linked without a history contract, so the first-time wording stays until one exists.

### Branch switching and branch-session loss

**Switch branch** is a shell action on branch-scoped screens, not a Profile screen, offered only when the identity has more than one branch (the visibility rule is on Branch picker). **D-M2-1 (owner confirmed 2026-10-22):** Web branch context is independent per browser tab and carried in `/f/{branchId}/…`; identity/account/global routes remain unscoped. In the initiating tab only, switching exits Gestão or Meu turno, releases this tab’s switched-away branch-session binding (without ending another tab’s session) and clears this tab’s branch-scoped route/data state (including selected operator/account, filters, mode, and return origin), and returns to Branch picker / session under identity authority. Another tab keeps its own branch, filters, mode and return intact; selecting a branch must not publish a browser-wide branch replacement. Mobile uses its branch-scoped navigation parameters, never fake Web URLs. The newly selected branch mints a new branch token and resolves its default home afresh: Member → Meu turno; Manager/Admin → Gestão. A previous branch's mode or resource deep-link is never replayed into the new tenant.

If the branch session is lost while the identity token remains usable, the same branch gate takes ownership and returns to Branch picker / session; if identity authority is also unavailable, Login takes ownership. After authentication/session is restored, an intended deep-link may resume only after branch and permission checks; otherwise navigation uses the applicable role home. Renewal, re-login and isolated local-input retention follow the cross-screen patterns below; retained input is not active branch-scoped route/data state.

## Cross-screen patterns

These semantic requirements are the authored deliverable for **design M0 0.4.2**. The existing template, route table and gap → screen map remain authoritative. Source contracts are the current `server.Communication` DTOs, controllers and use cases, read with `loto-specs.md` v57 (§6.1, §6.5–§6.7, §6.10–§6.18); a pending marker is not a shipped contract. Formatting and literal UI copy follow [`formatting-ptbr.md`](../specs/formatting-ptbr.md) and [`copy-guidelines.md`](../specs/copy-guidelines.md). Web/mobile own their storage, transport, focus and navigation implementations; `design/` adds no runtime code.

### Feedback, errors and read states

| State | Shared behavior |
|-------|-----------------|
| Initial loading | Announce **Carregando…** once, mark the region busy, and show the screen's loading placeholder. Unknown money/count/status stays unknown, never zero or an all-clear. Disable only actions whose required context is not yet loaded. |
| Refresh / filter / page loading | Keep the entered filters and local input. Previously loaded data may remain visibly marked as updating under its original context; never label an old page with a new date/account. Ignore responses superseded by a newer request or identity/branch generation. |
| Empty | Only a successful, scoped response establishes emptiness. Distinguish no records, no matches (**Limpar filtros** where useful), all-clear, and the endpoint's empty-scope/setup fallback. Never turn 403, failed dependencies, a loading count, or a missing page into zero. |
| Error | Keep recoverable input and context. Render **every** `ResponseErrorJson.ErrorMessages` string verbatim, in order, as a list: no rewriting, prefixes, deduplication or truncation. Resource names such as `DAILYCLOSE_STALE_WRITE` below are documentation identifiers, not error codes returned in an extra JSON field. |
| Success | Show the endpoint-confirmed outcome using copy such as **Transação salva** or **Fechamento enviado**, then follow the existing return rule and refresh affected reads. A local draft, preview, dispatched request or timeout is never success. Partial multi-row actions report confirmed rows and unresolved rows separately. |

For a 400, put the message beside a field only when its association is unambiguous; the API has a string list, no field-error dictionary. Otherwise use a form error summary with links to the relevant inputs where known. A 403 keeps the backend message alongside the screen's setup/permission explanation; it does not start an authentication loop. A 404 uses the unavailable-resource state without probing another branch or disclosing cross-branch existence. A 409 is resolved by its operation/context: stale version, locked period, frozen close, duplicate, or coordination busy are different recoveries. Never infer machine behavior by translating/substr-matching localized prose; use known command/read state and retain a generic reload/reconcile path where the response cannot distinguish the case.

With no usable error body, show **Não foi possível concluir a ação. Verifique sua conexão e tente novamente.** For any dispatched write, **every HTTP 5xx** (including gateway 502/503/504) means **Resultado não confirmado**, whether or not it carries `ErrorMessages`: show supplied messages verbatim plus **Não foi possível confirmar se a ação foi concluída.** A 500 can follow an uncertain database commit; an error body is not evidence of rollback or a known business rejection. Lost responses/timeouts follow the same uncertainty rule. Use the safe verification/retry path below; the generic **tente novamente** text never authorizes a fresh financial create. Keep explanatory client copy outside backend messages. A failed impact preview is non-blocking as cataloged; hide or mark its prior result as outdated. A failed authoritative balance/blocker/lock read cannot become a fabricated value or proof of write eligibility. Independent regions may retry separately, with each source and incomplete total identified.

### Pagination, filters and source context

Use the endpoint's real query fields and returned `Page`, `PageSize`, `TotalCount`, `TotalPages`, `HasNext`, `HasPrevious` where present. Start at page 1; a changed server filter or page size resets to page 1. Preserve the chosen date/window, account/operator/client, transaction type, status, mine flag, page size and page across authorized drill-down/return; show these in the source heading/filter summary on both platforms. A new navigation entry uses the catalog's default; a validated origin restores its own context instead. Do not invent search/sort for an endpoint without it. Client search is explicitly local only for a complete unpaginated collection (e.g. Clients), never a pretend branch-wide search over one page.

Server ordering/counts stay authoritative. A page-local subtotal is labelled **Subtotal desta página**; a full-window total comes from the response aggregate or a defined complete-page composition, never the currently visible rows. After a successful write, re-read the source and counts; if its old page is now beyond `TotalPages`, move to the last valid page (or page 1 for an empty collection) and re-fetch. No user action widens Member scope to make a page nonempty. A scope-empty result uses the endpoint-specific fallback: Transactions list empty-short-circuits, while a forbidden detail read is still a permission state.

### Return, breadcrumbs and safe fallbacks

An origin describes the authorized source journey, its mode and filter context; it is not an arbitrary URL supplied by a message or a trusted permission claim. Nested trips keep the parent chain: Monthly reconciliation → Draft list → Edit → list → reconciliation; Close day → Draft list → Edit → list → the same close; blocked Create/payment → Open day → the original form. Display a semantic breadcrumb or **Voltar para {origem}** naming that source; native back and browser back obey the same destinations. Same-tab reload/back/forward restores mode, origin and focus from app navigation state only after fresh identity/branch/permission checks; shared routes keep a valid restored mode. URL-only bookmark/copied/fresh-tab entries have no origin and use the role’s default mode for shared routes. Browser-duplicated history/sessionStorage is untrusted restoration state and must pass the same checks, never treated as reliably detectable duplication. No navigation restores stale write authority or replays a mutation. A direct/copied link has no invented origin and uses the route table's named fallback (Transactions list for a source-less edit; role/mode home where specified).

Validate branch, current permission, resource/status and mode before fetching/resuming each target, including a restored breadcrumb. Re-read the affected source on return; an old approval route may now be read-only or route to correction. A removed source or forbidden target falls back to the available role/mode home with an explanation; a branch gate takes precedence over any breadcrumb. Deep-link identifiers and local return descriptors never supply authorization. M4 chooses URL encoding, history integration and presentation; it must preserve these semantic returns and scoped input.

### Identity gate, renewal and branch boundaries

Keep identity authority, branch authority and navigation mode distinct. Login yields `{Name, Email, ResponseToken {Token, RefreshToken}}`; branch session yields `{Token, Branch}`, including `Branch.Id` and `Branch.Role`. Identity alone opens Branch picker, not Profile or any branch data. Guard a pending link as intent until both gates pass. Resolve elevated self-context separately; unlinked Manager/Admin retain the dual-mode close screens in Gestão and never acquire a Member time-entry tap through a mode switch.

**Trigger and rotation model.** An HTTP **401 from any authenticated endpoint** starts one bounded recovery cycle, except `/user/login` and `/user/renew-token`, which never recursively trigger renewal. The API returns localized strings only: `TOKEN_EXPIRED`, `TOKEN_INVALID`, `TOKEN_EMPTY` and `TOKEN_WITHOUT_USER` all map to 401; removed membership can also produce 401, so the client must not try to identify expiry by message text. A second 401 after that cycle stops recovery and returns to the appropriate Login/branch gate instead of renewing indefinitely. Pause affected writes/autosave; if no refresh token is stored, go to Login directly. Reads may retry once after recovery, while mutations still obey their specific retry/reconciliation rules below.

The server keeps **one active refresh token per user**: `RefreshTokenRepository.SaveRefreshToken` removes that user's previous refresh tokens on every login and renewal. Signing in on another device therefore ends this device's ability to renew; it does not immediately revoke an already-issued bearer token, and there is no push notification or response code proving which device displaced it. A failed renewal must not claim that expiry was necessarily the cause. Use **Não foi possível renovar sua sessão. Entre novamente.**, retaining any supplied backend messages verbatim.

**Across-tab single flight (web).** Coordinate renewal for the identity across **all tabs/windows sharing the session store**, not just within one tab. One lock/owner serializes login/renewal and credential replacement; waiting tabs re-read the current stored token generation after acquiring the lock and use a successful peer result instead of spending the stale refresh token. Replace `{Token, RefreshToken}` atomically in the secure session layer and notify waiting tabs without secrets; discard responses from an old identity/session generation so a late response cannot replace another login's credentials. Each tab keeps its URL-bound branch context (`/f/{branchId}`) and recreates the scoped session for that intended branch; never broadcast one tab's branch replacement into another tab. Token pairs stay in the app-owned secure session layer; browser JavaScript notifications carry only non-secret generation/invalidation signals, never tokens. A switch in tab A leaves tab B's branch, mode, filters and return intact even if both began in the same branch. Identity logout/login replacement and password/session ends still affect all tabs; revoked branch membership is denied for every tab regardless of a retained URL. Mobile applies equivalent single flight to all requests sharing its session. This coordination prevents client-originated rotation races, but it cannot coordinate independent devices or add server replay/grace semantics.

`POST /user/renew-token {Value: refreshToken}` returns a new **global** `Token` plus `RefreshToken`; replace both together under that coordination. It does **not** return `Branch` or branch authority. With usable identity authority, recreate the intended session through `POST /branch/session {BranchId}`, revalidate membership/role and refresh branch clock, settings/lock and necessary self-context before resuming. A 404 from session recreation (`BRANCH_NOT_FOUND` in the resources) returns to **Branch picker / session** with the verbatim message and an explanation that the previous filial is unavailable; retain that filial's input separately, re-read available branches, and do not auto-replay its intent into another branch. Do not trigger renewal for this 404 or a permission 403.

**Lost renewal response.** A timeout, connection loss or 5xx may occur after the server has committed rotation and deleted the old refresh token. Keep writes paused and show an unknown-renewal/connectivity state. After connectivity is usable, enter the same shared lock, re-read the latest stored credentials (a peer may have succeeded), and allow **one verification retry** with the stored refresh token if no successful peer result exists. A 401 from `/user/renew-token` is definitive for that token: clear unusable authority and route to Login with the neutral renewal-failure copy. If the retry also has an unknown transport/5xx outcome, remain paused, offer **Entrar novamente** and connection recovery, and do not loop renewals or resume writes on old authority. There is no renewal-status lookup or replay-safe renewal contract.

After re-login, Branch picker/session rechecks the intended branch; only an authorized route intent resumes. The same authenticated email and branch can restore input under the recovery rule below, including after another-device login or a lost rotation response. A different account never sees that input, and another selected branch or failed membership check resolves a fresh home.

**Switch branch (initiating tab only; D-M2-1):** before dropping its switched-away scope, persist unsaved input in its isolated scope. Stop debounces/retries, detach in-flight results from the new session, release this tab’s binding to the old branch session (without revoking or deleting authority used by another tab), and clear this tab’s tenant-specific authority, query/detail/lookup caches, loaded versions, permissions, routes, origins, filters, mode, workstation and operator/account/client selections. Cancel client requests where possible; cancellation cannot undo a committed server write. Keep an uncertain operation record only in its original isolated scope for later verification. The new session starts from its own role home; never transplant the previous tenant's draft, pending submit, resource id or idempotency key into it. Even a late response from the old branch cannot populate the new screen/cache or show its success message.

### Capability links, account sessions and platform authority

**Capability links.** Invitation and password links arrive by e-mail as `{application URL}/invitation#token=…` and `{application URL}/reset-password#token=…`; the token lives in the URL fragment, which the browser never sends to a server. The app reads the token once on entry, immediately replaces the address/history entry with the bare route, and holds the value only in memory for the current journey — tab-scoped session storage at most when the Invitation journey must survive a sign-in step in the same tab. It never writes the token to durable device storage, logs, analytics, crash reports, a query string or another URL, and capability routes load no third-party resource and send no referrer. Mobile app links follow the same rule. A reload after cleanup no longer has the token: the screen says the link must be opened again from the e-mail, never asks the person to paste it. A capability is consumed only in an API body (`Token`). `SECURITY_TOKEN_INVALID` (409) covers expired, used, declined, replaced and inactive-account capabilities alike; render it verbatim with the next step the screen offers, and never guess which case applied. Anonymous capability calls may return 429 with `SECURITY_RATE_LIMITED`: show it verbatim and do not retry automatically.

**Account-wide session ends.** A successful **Alterar senha** or password reset revokes **every** refresh session of that account, on every device, in the same commit. Already-issued identity/branch tokens expire naturally, so other devices keep working until their next renewal fails, which follows the renewal-failure path above (verbatim message, Login). On the device that changed the password, the app clears its credentials at once and returns to Login with **Senha alterada. Entre novamente com a nova senha.** rather than waiting for a later renewal to fail mid-task. Device-kept input survives under the recovery rule above, partitioned by the returned email. **Sair** revokes this device's stable refresh session (`POST /user/logout`, idempotent 204) and clears local credentials and branch state; it does not end other devices' sessions. If the logout response is lost, local credentials are still cleared, and the screen says the server could not confirm the end of the session; signing in again replaces it.

**Login failures stay generic.** `POST /user/login` returns the same 401 `PASSWORD_WRONG` text for a missing, inactive, wrong-password or passwordless account. The UI never adds “conta não encontrada” or suggests Google for a particular address; the only hints are static (**Esqueci minha senha**, **Continuar com Google**). Forgot password always shows the same confirmation, whatever happened (202). Repeated failures — and any request while a server budget is spent, the right password included — return 429 `SECURITY_RATE_LIMITED`, the same for every address: show it verbatim, keep the form usable for a manual retry, and promise no lockout length, countdown or unlock. **Esqueci minha senha** stays available: a successful reset clears the account's server-side failure budgets, but the per-network request limit is separate, so the next sign-in can still receive 429 for up to a minute. Keep the same verbatim state then; never promise that the reset unlocks at once.

**Platform authority is fresh and separate.** `ResponseUserProfileJson.IsPlatformOperator` is read-only and only decides whether **Plataforma** is offered; the server re-reads the stored flag on every `[TokenPlatformOperator]` call and refuses a branch token. A `403 PLATFORM_ONLY` hides the area, re-reads the profile and shows the message verbatim. A platform operator receives no branch membership from onboarding and can open a tenant only through an ordinary invitation and branch session. `IsPlatformOperator` and `HasPassword` are never editable controls.

**Membership guards.** Nobody acts on their own membership (`BRANCH_USER_SELF_MEMBERSHIP_CONFLICT`), a branch keeps at least one active Admin (`BRANCH_USER_LAST_ADMIN_CONFLICT`), and a Manager never targets or grants Admin. The UI disables the matching action in advance and keeps the reason in reachable adjacent text, while the server stays the gate and its message renders verbatim when a race gets there first. `SECURITY_COORDINATION_BUSY` (409) is a retryable access-change conflict: keep input and offer **Tentar novamente**.

### Server time and current-day authority

`GET /branch/current` returns `BranchLocalDate` (`YYYY-MM-DD`, calendar-only) and `BranchLocalDateTime` (offset-free branch wall time), captured together. Use them for “today”, initial business date/time and same-day hints; never parse them as UTC instants or derive authorization from device time. Audit instants such as `UpdatedAt` remain UTC instants rendered by formatting §4 in the device timezone; do not use them as a substitute business clock. Re-read branch time on session creation/recreation, foreground/return after suspension, and before a day-sensitive action when the snapshot may have aged. The same response includes the **live `Branch.Role`**, resolved from current membership: compare it to the active UI role, stop pending actions/autosave on change, clear permission-dependent caches and selections, refresh self-context, and re-evaluate the current route/mode/home before continuing. Never retain a privileged screen/action solely because an old token or navigation mode claimed an elevated role; the server rechecks membership and permission on every request. A device timer may request refresh; it never advances business authority itself. Without a fresh read, retain input and stop autosave/day-sensitive writes pending reconnection.

When the server day changes, announce **A data da filial mudou. Confira os dados antes de continuar.** Keep an already typed business date, count and Notes tied to their original resource; do not silently roll them forward or submit them as today's entry. Clear the cockpit workstation's per-day choice and re-evaluate defaults and permissions. Today-only Member transaction correction/voluntary Recall, current-day plain-Draft autosave and prior-day correction are distinct: the recording Member can correct a rejection/opening recheck until lock, but cannot infer the same right from an elevated prior-day Recall/Reopen. Before first count, an account-scoped Member may claim an unlocked backdated close; this does not grant ordinary prior-day Submit. Manager/Admin may act historically before lock without an operator link, and cannot create a future close. Keep the exact per-screen matrix and server rejection authoritative; `LockReady`, a client clock or an enabled button is never the final permission check. Time-entry overnight Close retains its explicit previous-date choice; manager snapshots use entry-date policy, not today's constants.

### Durable scoped input and recovery

Keep input durably on the device as it changes, including blanks versus zero, partially typed numbers, Notes/reasons, installment edits and the original business date. A navigation return, browser reload or mobile process recreation must not depend on an in-memory form alone. Partition by application, verified login identity, `Branch.Id`, form/operation, and resource/account/operator/date as applicable; separate two new-entry forms rather than overwriting one draft slot. Persist user input and the minimum operation/recovery metadata, not credentials, bearer/refresh tokens or a durable `xmin` precondition. Passwords (current, new and repeat), Google assertions and sign-in challenges never enter the durable-input store; keep them only in memory for the active authentication request or link-proof step, and clear them when that journey ends. Capability tokens follow the stricter capability-link rule above. App-owned secure session storage is separate. Device-only copy says **Rascunho salvo neste dispositivo — ainda não salvo no servidor**; it does not promise cross-device sync.

During a continuing verified identity session, restore only after the same branch, resource and required grants are rechecked. Fetch current server data first and compare it with the saved base values; if another actor changed it, keep both for deliberate reconciliation rather than overlaying stale input. A process restart may restore a verifiable still-valid session; if identity cannot be verified, keep the input quarantined. On link/grant loss stop saving, retain the input in that identity's scope, show the setup/permission fallback and require authority again before any edit replay. Another employee on the device must not see or submit it.

**Recovery after a fresh login.** Preserve the decided rule: unsaved input is kept on the device and restored on return, including re-login. For the current shipped account model, partition local input by the exact `Email` returned by a **successful authenticated login**, plus application/branch/form/resource scope. `User.Email` has a unique index and the current API exposes no email-change operation; the login mapper returns the stored email, so compare that returned value exactly, without inventing case-folding, using the typed login string, or treating a display name as identity. Restore the matching email's input only after the intended branch session, current permissions and resource state have been rechecked, and reconcile against fresh server values before any explicit write. Authentication, not a locally supplied email, unlocks the partition. Until login succeeds, or when a different email signs in, keep previous input isolated and undisplayed.

Email is a local recovery scope for this shipped model (M8 now returns its trimmed, lowercase canonical form), not the backend `UserId` used for authorization or idempotency. A future email-change/account-lifecycle contract must define safe partition migration before it ships; prefer the contracted `UserId` when M8 delivers it. M8 now contracts the login `UserId` (gap U backend resolved); adopting it for future local-storage partition migration still requires an explicit migration contract and does not silently transfer existing drafts. Never transfer or auto-submit an uncertain financial operation merely on an email match: it remains the same stored operation, under fresh branch/permission and replay-window checks. Switching branch within a continuing identity may later restore the original branch's draft only after reselecting that branch and checking its grants again; switching itself clears all active context.

**Blocker round-trips:** save the form locally before visiting drafts, an opening source, or Open day. On return restore the exact same count/Notes or create/payment candidate, refresh authoritative blockers/transactions/openings and recompute the preview; never replace typed closing values with refreshed opening values. Opening the terminal records only the open-day action; the pending sale/payment still needs confirmation. Recoverable validation, busy coordination, preview, connectivity and stale-version errors retain input. Clear only the acknowledged submitted snapshot after confirmed success, or input the user explicitly discards; edits made while an older snapshot was saving remain dirty. If durable device storage fails, say **Não foi possível guardar as alterações neste dispositivo. Mantenha esta tela aberta.**, keep the form in memory and offer explicit retry or deliberate discard before navigation; never claim durable retention succeeded. No TTL silently deletes unresolved input or uncertain-write records. Platform storage eviction/device loss cannot be represented as a server backup.

### Close-day autosave, dirty Save and repeat undo

The Close day entry owns the detailed count behavior. Autosave requires a permitted **today's plain Draft**: `Date = BranchLocalDate`, `Status = Draft`, `RejectionReason = null` and `OpeningRecheckRequiredAt = null`. Merely viewing or restoring unchanged data never claims the immutable first recorder. Debounce real item/Notes edits, keep one item-save in flight per close, and coalesce later edits into the next complete candidate. A response acknowledges only the sent snapshot; if typing continued, retain the newer values and dirty state. Use the returned new version for the next guarded save; a preview response cannot acknowledge input or arrive later and replace a newer preview.

**Salvar** stays visible and actually disabled when clean or while its save is in flight; permission, lock and read-only gates still apply independently. Dirty means the candidate differs from the last acknowledged server snapshot; a never-recorded first count (`ItemsFirstRecordedAt = null`) also requires explicit Save even if every displayed value is unchanged. Rejection corrections, opening rechecks and historical Drafts keep local input and require explicit **Salvar**, because an actual count change can invalidate a successor. Stop autosave on session/day/permission/state loss, stale conflict or uncertain save. Never promote a local draft or autosave to Submit.

`PUT /dailyclose/{id}/items` returns `ResponsePutDailyCloseItemsJson {DailyClose, AffectedSuccessor?}`. **Salvo às {hora}** uses the acknowledged `DailyClose.UpdatedAt`, formatted as an audit instant; `ItemsFirstRecordedAt` is only the immutable first-count time, not the latest save. There is no `SavedAt` field. Show date with time for a historical save; if no authoritative timestamp is available, use **Salvo** without fabricating a device receipt time. Keep **Salvando…**, **Não salvo — tentar novamente** and **alterações não salvas no servidor** distinct from preview and saved state. A returned `AffectedSuccessor` produces the existing explicit demotion explanation.

**Enviar para aprovação** is always explicit. Await any pending item-save, successfully save the latest dirty count/Notes under the same scope, and refresh/recheck blockers before issuing Submit; a failure or uncertain acknowledgement stops the chain with input intact. The action never silently submits the older persisted snapshot. Recall, Reopen and correction remain separate actions, with the existing permission matrix and retained first-recorder identity.

**Repetir abertura / Desfazer repetição** use the row's exact pre-copy local value (including a blank or unsaved text), not its last saved value. Keep one persistent undo action per changed row; a no-change repeat does not replace the retained value. Undo changes only that row and refreshes preview, survives successful autosave, and obeys the same explicit-save versus autosave rule. Manual editing that row, leaving the close, or successful Submit ends that row undo; durable form retention does not add undo history across navigation/reload. Restoring an already-saved copied value is a new guarded edit, never a rollback of audit, approval or successor recheck.

### Financial create retry and uncertain outcomes

MVP financial writes require a live connection. Local input persistence is allowed; **no offline money queue**, background money flush, or reconnect auto-submit is allowed. Offline/read-cache data is visibly outdated and cannot authorize financial actions. Reconnection refreshes identity/branch, clock, permission, lock and current resource state, then requires an explicit continuation. The Member time-entry tap's documented no-op retry behavior is specific to that command; it does not make other writes replay-safe or add offline attendance capture.

For the shipped `POST /transaction` and `POST /transaction/installment`, freeze a logical operation's endpoint, typed payload and a new client `Idempotency-Key` (1–128 visible ASCII characters) **before dispatch**, in the original identity/branch partition. One key covers the whole installment create. Disable duplicate activation while pending; a retry of that same operation sends the **same key and same payload**, including date, authorship and `SaveAsDraft`. Do not regenerate defaults, reorder installment arrays, or recompute dates on retry. The server scopes the key by endpoint + authenticated branch/user, compares its canonical typed-body hash, and replays the durable response/resource/version for 24 hours (§6.1). It is not a global deduplication key or an optimistic concurrency token. Bound retry eligibility conservatively from the first dispatch, never extend it after a retry or depend on an untrusted device wall clock; if elapsed time/window eligibility cannot be established after suspension/restart, use the expired/uncertain-window reconciliation path.

| Result / next intent | Required recovery |
|----------------------|-------------------|
| Confirmed successful create / replay | Acknowledge the returned resource once; refresh affected reads. A replay carries the original envelope, so fetch a current representation before later edits. Clear only this submitted candidate. A deliberate next transaction gets a new operation/key. |
| Timeout, lost response, connection loss or cancellation after dispatch | Mark **Resultado não confirmado** and keep the immutable candidate/key. Within the replay window and verified same scope, **Verificar e tentar novamente** sends that identical operation to obtain the durable replay or execute once. No new key, false success or assumption of rollback. |
| HTTP 5xx after dispatch, with or without an error body | Mark **Resultado não confirmado**; show backend `ErrorMessages` verbatim when present plus the confirmation warning. Keep the same immutable payload/key and use the same-operation verification path above within the safe window. This includes gateway 502/503/504 and a server 500 after uncertain COMMIT. Never mint a new key on the assumption that the write rolled back. |
| Confirmed validation/business rejection (not a 5xx) | Show backend strings, keep input and stop any automatic retry loop. After a known rejection, a corrected payload is a new operation/key. A strictly identical retry after resolving a blocker may retain the original key; no changed-payload reuse. |
| 409 `IDEMPOTENCY_KEY_PAYLOAD_CONFLICT` | Stop; preserve the original operation separately from current edits. Resolve/check the original result first. Never automatically replace its key to evade the conflict. Once resolved, a consciously new/changed submission uses a fresh key. |
| 409 coordination busy | Show the verbatim message and allow an explicit bounded retry of the same candidate/key. A committed replay is resolved before DailyClose account coordination; a busy response is not success. |

*Receber pagamento* (`POST /transaction/fiado-payment`, server M7.7 Phase 5.1) uses the same persisted `Idempotency-Key` contract under its own scope, covering the whole linked pair: a replay returns the original payment and its `GeneratedTransactionId`, never a second pair. The generic create refuses a Tab `In`, so payment is never faked through it, and a client never writes a Terminal movement for a fiado operation itself. Close opening/submission/approval/recall/reopen, ordinary CRUD and time-entry snapshots do **not** gain `Idempotency-Key` merely because the client adds a header. For these, a lost write response requires an authorized re-read and explicit reconciliation; never replay an unguarded mutation blindly. Open day can resolve an existing close by its exact account/date, as cataloged.

### Guarded edits and newer server versions

Apply the shipped precondition only to transaction update/finalize/cancel, DailyClose item-save, Setting update and lock-month. Read the current root's `Version` and matching response `ETag`; send one strong quoted positive decimal, e.g. `If-Match: "123"`. No weak tag, wildcard, unquoted/zero/list value, body-version duplicate or persisted cross-session token. The missing/malformed cases are 400 `CONCURRENCY_IF_MATCH_REQUIRED` / `CONCURRENCY_IF_MATCH_INVALID`; stale roots are 409 `TRANSACTION_STALE_WRITE`, `DAILYCLOSE_STALE_WRITE` or `SETTING_STALE_WRITE`, not an assumed 412. Success updates the in-session token from the returned root (`DailyClose.Version` inside the item-save envelope).

On stale conflict, stop autosave/retries, retain the user's candidate, and offer **Recarregar e conferir**. Reload the authorized current resource without destroying local edits, show current and proposed values in a reconciliation step, and require a deliberate choice before a fresh guarded save. Never silently put a new ETag on an old payload or overwrite the newer version. For a lost acknowledgement, re-read: if current values match the sent snapshot, they can be shown as confirmed server state, without inventing who wrote them; if they differ, reconcile. Keep later local edits dirty. `xmin` is a session-lived token, not an audit revision or persisted durable draft base.

For multi-installment per-row correction/cancellation, preserve each row's version and report individual confirmed results; there is no client-side atomic batch. A cheque plan finalizes only through `POST /transaction/installment/{originTransactionId}/finalize` with every Draft installment's version; the per-row finalize refuses plan installments (`TRANSACTION_PLAN_FINALIZE_REQUIRED`), so never loop per-row calls. Time-entry manager snapshots likewise have no claimed ETag coverage here: they reconcile all active segment ids, preserve existing `ClockIn`, use new `Id = null` segments, and use granular `PUT`/`DELETE` for correction/removal as the shipped entry specifies. Their stale domain validation or unknown outcome requires reload and deliberate reconciliation, never a replace-all promise.

### Keyboard, touch, focus and assistive reading

Both platforms preserve the same field meaning, actions and state announcements. Follow reading order: screen heading and branch/date/account context → relevant status/blocker explanation → filters/form → primary/secondary actions → results. Web supplies a skip-to-content path and semantic headings, labels, table headers, native links/buttons and visible focus; mobile exposes equivalent accessibility names, roles, hints and reading order. No positive tab index, hover-only explanation, drag-only control or whole-row click that swallows a nested button. Transactions retain the explicit accessible **Abrir transação** link with row-identifying context. Pointer row activation must preserve text selection, native link behavior and scrolling.

Keyboard users can reach every control; Enter activates an explicit link/button or form submission only when its scope is clear, never a surprise financial action while choosing a value. Escape/native back dismisses an overlay through its return rule, retaining input. A dialog names its purpose/consequence, moves focus inside, contains keyboard focus while modal, offers a clear return action and restores focus to the trigger (or a logical source heading if removed). Route entry focuses/announces the new screen heading; returning restores the originating row/control when still present. Paging/filter results announce count/page changes without stealing focus; removing the focused row moves to the next logical row or list heading.

Use comfortably separated **at least 44 × 44 logical-unit touch targets** for standalone actions, including row undo and icon controls; M3/M4 encode geometry per platform. Dense data may scroll horizontally with headers/context retained, but must not hide the only actionable label. Inputs have persistent labels, decimal/numeric keyboards where suitable, pt-BR formats, and spoken explanations distinguishing missing from zero, Entrada/Saída and falta/sobra. A status is named in text, never only color/icon; disabled actions expose their reason in reachable adjacent text rather than an unreachable tooltip. Large text/zoom must retain content and actions.

Announce a submitted form's error summary once, move focus to it or the first invalid field, associate inline error/help text with the input, and keep entered values. Use an assertive announcement for an action-blocking failure/session loss and a polite status region for loading completion, save, result counts and success. Do not read every autosave keystroke, timer tick or preview update; coalesce and announce a changed final status. Keep persistent visible feedback alongside announcements. **Desfazer repetição** remains reachable after autosave; a fleeting toast cannot own the only recovery action. M3/M4 and both app builds must verify keyboard-only, screen-reader and touch journeys, including all blocker/re-login returns; this authored catalog is not evidence that runtime accessibility has passed.

## Login

- **Purpose** — authenticate an existing account, by password or by a verified Google identity, and obtain the identity token that unlocks Branch picker.
- **Primary job** — get in fast: two fields and one button, or one Google step.
- **Access** — public (anonymous); everything else in the app sits behind this door. There is no public sign-up: onboarding is operated and people arrive by invitation (gap C, decided and shipped in server M8 Phase 6).
- **Data shown**
  - **Password form** — `Email`, `Password`. `[DTO: RequestUserLoginJson]`.
  - **Google option** — **Continuar com Google** first obtains a single-use challenge, `POST /user/google/challenge` → `[DTO: ResponseGoogleChallengeJson]` (`ChallengeId`, `State`, `Nonce`, `ExpiresAt` — five minutes, server UTC). The app passes `Nonce` to the platform's Google sign-in (web Google Identity Services, native Google sign-in on mobile — app-owned adapters) and returns the signed ID token with the challenge: `POST /user/google/sign-in {ChallengeId, State, IdToken, CurrentPassword?}` `[DTO: RequestGoogleSignInJson]`. The app never decodes the ID token for authority, sends no caller-chosen e-mail and never treats a Google token as branch authority.
  - **Link confirmation step** — when a Google e-mail matches an existing password account that has no recorded mailbox proof, the server answers 409 `GOOGLE_LINK_PROOF_REQUIRED`. The screen then asks for the **current Lotero password** of that account and resends the same `ChallengeId`, `State` and `IdToken` with `CurrentPassword` while the challenge is unexpired; the refused attempt consumed nothing. After `ExpiresAt`, or on `GOOGLE_CHALLENGE_INVALID`, the journey restarts from a new challenge. `[DTO]` request/response; the step itself is `[derived]` from the error. A wrong password repeats 409 `GOOGLE_LINK_PROOF_REQUIRED`: keep the confirmation step and unexpired challenge, show the returned message verbatim without inferring a new cause, clear only `CurrentPassword`, and let the person retry manually. Each wrong password spends the same server budget as **Entrar**, so repeated attempts end in the *rate limited* state; a refused proof still consumes nothing. Do not loop automatically; expiration still starts a new challenge.
  - **Static first-access hint** — **Primeiro acesso? Abra o link do convite recebido por e-mail.**, always shown, never conditional on what was typed. `[derived]`
  - **Signed-in identity** *(after success)* — `UserId`, `Name`, `Email`, identity + refresh tokens. `[DTO: ResponseUserLoginJson + ResponseTokenJson]`, identical for password and Google. Use the required caller id for self comparisons; no token decoding.
- **Actions** — **Entrar** → `POST /user/login`; **Continuar com Google** → challenge + provider + `POST /user/google/sign-in`; **Confirmar senha e vincular** (link step) → the same sign-in with `CurrentPassword`; **Esqueci minha senha** → Forgot password; silent renewal thereafter → `POST /user/renew-token` (never a visible screen).
- **States** — *validating* (400 verbatim) · *invalid credentials* (401 `PASSWORD_WRONG`, the same text for a missing, inactive, wrong-password or passwordless account — never refined by the client) · *loading* · *Google unavailable* (503 `GOOGLE_NOT_CONFIGURED` or `GOOGLE_PROVIDER_UNAVAILABLE`, verbatim; the password form stays usable) · *Google not confirmed* (401 `GOOGLE_ASSERTION_INVALID` — also what an unknown Google account without an invitation receives) · *link confirmation* (409 `GOOGLE_LINK_PROOF_REQUIRED`) · *identity conflict* (409 `GOOGLE_IDENTITY_CONFLICT`, verbatim; no retry offer) · *attempt expired* (401 `GOOGLE_CHALLENGE_INVALID` → start again) · *rate limited* (429 `SECURITY_RATE_LIMITED` verbatim, from **Entrar**, the Google calls or the link step; the server refuses even a correct password while a budget is spent, so never say or imply the password was wrong, and never name an account. `Retry-After` is advisory whole seconds: no automatic retry, no countdown promise, no lockout copy; the form stays usable for a manual retry) · *provider cancelled* (the person closed Google's dialog — back to the idle form, no error) · *success* (→ Branch picker).
- **Navigation** — app entry point and the target of every session-ending journey (logout, password change/reset, renewal failure, a declined or unusable invitation). Success passes through Branch picker / session, which may resume a validated pending target under the cross-screen recovery rules. Login abuse protection is shipped server behavior (M8 Phase 8, v57) whose only UI surface is the *rate limited* state; live Google acceptance remains a server M8 Phase 8 gate.

## Branch picker / session

- **Purpose** — choose which branch (tenant) to work in and open the branch session that unlocks everything branch-scoped.
- **Primary job** — get into the right branch in one tap; most users have exactly one.
- **Access** — identity tier (`[TokenAuthenticate]`).
- **Default view / filter** — the user's branches. Exactly one branch → auto-open its session and skip the screen; more than one → the selection; zero → the *empty* state. Switch branch is offered only when there is more than one branch, so a single-branch user never sees this screen after login. `[derived]`
- **Data shown**
  - **Branch options** — `Name`, `Cnpj?`, `Address?`, `Phone?`, and the caller's `Role` in that branch. `[DTO: ResponseListMyBranchesJson.Branches / ResponseBranchSummaryJson]`. The role tells the user what they'll see inside.
  - **Account context** — the signed-in name and e-mail, and whether **Plataforma** is offered: `[DTO: GET /user/profile → ResponseUserProfileJson]` (`IsPlatformOperator`), a capability hint the server rechecks on every platform call. A failed profile read hides the Plataforma entry with a retry; it never blocks branch selection.
- **Session context** — after selection, `GET /branch/current` returns `BranchLocalDate` as a calendar-only `YYYY-MM-DD` value and `BranchLocalDateTime` as an offset-free branch-wall-clock value from one server clock capture. These are the authoritative business-day defaults; do not pass either through device-timezone conversion (`BranchLocalDate` is not a JavaScript instant). The device clock is display-only. `[DTO: ResponseGetCurrentBranchSummaryJson]`.
- **Actions** — select a branch → `POST /branch/session {BranchId}` → branch token `[DTO: ResponseCreateBranchSessionJson]`; then route by role: Manager/Admin → Gestão / Manager Work Queue, Member → Meu turno / Operator Day Cockpit. After an elevated session, `GET /operator/self-context` determines only whether the Gestão ↔ Meu turno switch is available. Session context re-read → `GET /branch/current`. **Plataforma** (platform operators) → Plataforma — Nova lotérica. The Session menu (Minha conta, Alterar senha, Sair) is available here too.
- **States** — *loading* · *empty* (zero branches → **Você ainda não tem acesso a uma lotérica.** with guidance to open an invitation link or contact whoever manages the lotérica; lotéricas are created by operated onboarding, so there is no create action; **Sair** and **Minha conta** stay reachable; a platform operator also sees **Plataforma**) · *branch unavailable* (404 `BRANCH_NOT_FOUND` on session creation — verbatim, re-read the list) · *error* · *success*.
- **Navigation** — after Login, after a completed Invitation, and through the navigation shell's Switch branch action when the identity has more than one branch. Switching exits either mode and releases only this tab’s old branch-session binding and active branch-scoped state; another tab, including one using the same branch, keeps its binding and context. A single-branch platform operator reaches Plataforma from the Session menu, because this screen is skipped for them.

## Session menu

- **Purpose** — the person's account and session hub, reachable from every authenticated screen: who is signed in, which branch and mode are active, the mode switch, account actions and sign-out.
- **Primary job** — switch mode or leave safely, without hunting.
- **Access** — identity tier for the account items; the branch and mode items exist only while a branch session is active. The menu shows only what the caller can already do; it adds no permission.
- **Data shown**
  - **Identity** — `Name`, `Email`. `[DTO: ResponseUserLoginJson]`, refreshed from `ResponseUserProfileJson` after a profile read or name change.
  - **Branch and role** *(branch session)* — branch name and the **live** role label. `[DTO: ResponseGetCurrentBranchSummaryJson.Branch]`; the session-creation `Branch` is the initial value, never a substitute for the live read.
  - **Work mode** *(Manager/Admin)* — Gestão and Meu turno with the active one marked; Meu turno availability from `[composed: GET /operator/self-context]`, unavailable with its reason and a link to Operators when no active operator link exists (see Role and mode navigation). While self-context is loading, Meu turno reads **Verificando…** and is not actionable.
  - **Plataforma** — present only when `ResponseUserProfileJson.IsPlatformOperator` is true. `[DTO]`
  - **Theme** — **Claro / Escuro / Sistema**, a device preference, not account data. `[derived]` device-local.
- **Actions** — **Gestão** / **Meu turno** (one-shot, lands on that mode's home); **Trocar filial** (multi-branch identities; same semantics as the global action); **Minha conta** → Profile; **Alterar senha** → Change password (only when `HasPassword` is true); **Plataforma**; **Sair** → `POST /user/logout {RefreshToken}` `[DTO: RequestLogoutJson]`, then clear local credentials, branch state and caches.
- **Before Sair** — no confirmation is needed in the ordinary case: signing out is reversible. When this identity has input kept on the device or an operation with an unconfirmed result, the menu confirms first and says so: **Há alterações guardadas neste dispositivo. Elas continuam guardadas e voltam quando você entrar de novo com este e-mail.** and, for an unconfirmed financial operation, that its result still needs checking after the next sign-in. Sair never discards that input and never submits it.
- **States** — *ready* · *self-context loading* · *Meu turno unavailable* (reason + Operators link) · *signing out* · *sign-out unconfirmed* (logout response lost or failed: local credentials are cleared anyway; **Você saiu deste dispositivo. Não foi possível confirmar o encerramento da sessão no servidor.**).
- **Navigation** — opens over the current screen from the avatar trigger at every width; Escape/back closes it and returns focus to the trigger. Each item follows its destination's own return rule; Sair → Login.

## Profile

- **Purpose** — see and correct one's own account identity: name, sign-in e-mail and how the account signs in.
- **Primary job** — fix the display name; understand the account's sign-in methods.
- **Access** — identity tier (`[TokenAuthenticate]` on `GET/PUT /user/profile`), any signed-in person, with or without a branch session. It never shows branch data.
- **Data shown**
  - **Nome** — editable, trimmed, 1–255 characters. `[DTO: ResponseUserProfileJson.Name / RequestUpdateProfileJson]`.
  - **E-mail** — read-only, the canonical lowercase form; the contract has no e-mail change. `[DTO: ResponseUserProfileJson.Email]`.
  - **Senha** — `HasPassword`: **Senha definida** with the **Alterar senha** link, or **Sem senha — esta conta entra com Google** with **Receber link para criar senha**. `[DTO: ResponseUserProfileJson.HasPassword]`.
  - **Operador da plataforma** — a read-only marker shown only when `IsPlatformOperator` is true; never a control. `[DTO: ResponseUserProfileJson.IsPlatformOperator]`.
  - Whether a Google identity is linked is not in the contract and is not shown.
- **Actions** — **Salvar** → `PUT /user/profile {Name}` (disabled while unchanged or saving; `PROFILE_NAME_INVALID` verbatim); the returned profile replaces the name shown in the shell. **Alterar senha** → Change password. **Receber link para criar senha** → the anonymous `POST /user/forgot-password {Email}` with the profile e-mail, showing Forgot password's confirmation; the link leads to Reset password, which ends every session of the account when used.
- **States** — *loading* · *ready* · *saving* · *saved* (**Nome atualizado**) · *validation error* · *error* (verbatim) · *coordination busy* (409 `SECURITY_COORDINATION_BUSY`, keep input, retry).
- **Navigation** — from the Session menu; returns to the screen that opened the menu.

## Change password

- **Purpose** — replace the account password after confirming the current one.
- **Primary job** — change it once, correctly, knowing every device will sign in again.
- **Access** — identity tier; offered only when `ResponseUserProfileJson.HasPassword` is true. A Google-only account has no current password and uses **Receber link para criar senha** on Profile instead.
- **Data shown**
  - **Form** — `CurrentPassword`, `NewPassword` `[DTO: RequestChangePasswordJson]` and a repeat field for the new password `[derived]`, client-checked only for equality (**As senhas não conferem.**). Pre-validation reuses the backend wording for length: at least 8 characters (`PASSWORD_LENGTH`) and at most 72 bytes in UTF-8 (`SECURITY_PASSWORD_MAX_LENGTH`). Password fields allow paste and password managers and offer **Mostrar senha**.
  - **Consequence** — **Ao alterar a senha, todas as sessões desta conta são encerradas, inclusive neste dispositivo.** `[derived]` from §6.16.
- **Actions** — **Alterar senha** → `POST /user/change-password` → 204. On success the app clears its credentials and returns to Login with **Senha alterada. Entre novamente com a nova senha.** (see Capability links, account sessions and platform authority).
- **Wrong current password** — the server answers **401** `PASSWORD_WRONG`, which an authenticated client cannot tell apart from an expired identity token. Run the ordinary single recovery cycle; if renewal succeeds, show the original verbatim message without attributing the 401 to a password check or token expiry, clear only the current-password field, and ask the person to submit manually again. Never resend the change automatically; no change was committed on the 401. If renewal fails, the ordinary Login path applies.
- **States** — *editing* · *submitting* · *wrong current password* · *validation* (400 verbatim) · *coordination busy* (409) · *result unconfirmed* (lost response: the password may have changed and every session may already be revoked — say so and offer **Entrar novamente**, which proves which password works) · *success* (→ Login).
- **Navigation** — from Profile or the Session menu; cancel returns there.

## Forgot password

- **Purpose** — request an e-mailed link to define a new password, without revealing whether an account exists.
- **Primary job** — ask once and know what to expect.
- **Access** — anonymous (`POST /user/forgot-password`, recovery rate limit).
- **Data shown** — **E-mail** field `[DTO: RequestForgotPasswordJson]`; after submission, one confirmation regardless of outcome: **Se houver uma conta ativa com este e-mail, enviaremos um link para definir uma nova senha. O link vale por tempo limitado.** `[derived]` — the 202 is identical for existing, missing, inactive, cooled-down, throttled and undeliverable targets, so the screen promises no delivery and states no expiry minutes.
- **Actions** — **Enviar link** → `POST /user/forgot-password {Email}` → 202. Sending again is allowed; the server may suppress repeats silently, so the copy suggests checking the address and the spam folder after a few minutes instead of promising a new e-mail per click.
- **States** — *editing* · *submitting* · *sent* (the confirmation above) · *invalid e-mail* (400 verbatim) · *coordination busy* (409 verbatim, retry) · *no connection before dispatch* (standard fallback; no request sent) · *result unconfirmed after dispatch* (lost response or 5xx: the e-mail may have been requested; use the same generic confirmation guidance without asserting delivery or account existence, and offer an explicit retry).
- **Navigation** — from Login (**Esqueci minha senha**) or Profile (**Receber link para criar senha**, pre-filled and read-only); back → its source.

## Reset password

- **Purpose** — consume an e-mailed capability to define a new password. The same link activates the first platform operator created by the bootstrap command and creates a password for a Google-only account.
- **Primary job** — set the new password and know how to sign in next.
- **Access** — anonymous capability (`…/reset-password#token=…`, capability rate limit). There is no preview contract for recovery links: the screen cannot validate the link before submission and says nothing about the account.
- **Data shown** — title **Definir nova senha**; `NewPassword` and a repeat field `[DTO: RequestResetPasswordJson]`, with Change password's client checks and backend wording. The capability itself is never displayed.
- **Actions** — **Salvar nova senha** → `POST /user/reset-password {Token, NewPassword}` → 204: password set, every refresh session of the account revoked and remaining recovery links invalidated in one transaction. It does **not** sign the person in.
- **States** — *link missing* (opened without a token, or reloaded after cleanup → **Abra novamente o link recebido por e-mail.**) · *editing* · *submitting* · *unusable link* (409 `SECURITY_TOKEN_INVALID` verbatim + **Peça um novo link** → Forgot password) · *validation* (400 verbatim) · *rate limited* (429 verbatim) · *result unconfirmed* (lost response: try signing in with the new password; a retry of the same link returns the unusable-link state if it already worked) · *success* (**Senha definida. Entre com a nova senha.** → Login).
- **Navigation** — e-mail link only; success, cancel and unusable link → Login.

## Invitation

- **Purpose** — answer an invitation to a lotérica: see where and with which role, then join with a new password account, a Google account or an existing Lotero account — or decline.
- **Primary job** — join the right lotérica in one pass, with the account the invitation was sent to.
- **Access** — anonymous capability for preview, decline, register and Google (`…/invitation#token=…`, capability rate limit); identity tier for accepting with an already signed-in account, whose canonical e-mail must equal the invitation's. Membership, optional operator pre-link, any new user and the capability consumption commit all or none.
- **Data shown**
  - **Preview** — `POST /invitation/preview {Token}` → `[DTO: ResponseInvitationPreviewJson]`: `BranchName`, `Role` (label per copy §5), `ExpiresAt` (UTC instant, **Válido até {data/hora}**), `OperatorName?` (**Você será vinculado ao operador {nome}.**). The preview never returns the invited e-mail, so the screen says **Use o e-mail que recebeu este convite.** rather than naming it.
  - **Signed-in account** *(when an identity session already exists on this device)* — **Você entrou como {e-mail}** from the login/profile response `[DTO]`, with **Sair e usar outra conta**.
- **Actions** *(three ways to join and one to decline, shown together)*
  - **Criar conta com senha** — `Name`, `Password` + repeat → `POST /invitation/register {Token, Name, Password}` → 201 login envelope `[DTO: RequestRegisterInvitationJson → ResponseUserLoginJson]`. E-mail, branch and role come only from the invitation. Any existing account, active or inactive, is refused (`EMAIL_ALREADY_REGISTERED`, verbatim) and the screen points to **Já tenho conta**.
  - **Continuar com Google** — the Login Google journey with `InvitationToken` and `Name` (asked first: **Seu nome**, used only if this becomes a new account) `[DTO: RequestGoogleSignInJson]`. A different Google e-mail returns 403 `INVITATION_EMAIL_MISMATCH` (verbatim + choose the invited Google account); an existing password account without mailbox proof returns `GOOGLE_LINK_PROOF_REQUIRED` and gets Login's link confirmation step.
  - **Já tenho conta — entrar e aceitar** — Login by password or Google inside this journey (the capability kept only in tab-scoped storage), then **Aceitar convite** → `POST /invitation/accept {Token}` → `[DTO: ResponseAcceptInvitationJson]` (`BranchId`, `BranchUserId`, `Role`, `OperatorId?`). With a signed-in session already present, **Aceitar convite** is direct.
  - **Recusar convite** → a confirmation stating **O convite deixará de valer.** (the contract records only the status, so the copy promises no notification to the lotérica) → `POST /invitation/decline {Token}` → 204; repeating it while the capability is still valid is also 204.
- **Audit / lock context** — acceptance creates or reactivates the membership with the invited role and, for a Member invitation with a pre-selected operator, links that operator, keeping its history and assignments. An active membership is refused (409 `INVITATION_MEMBERSHIP_EXISTS`); another acceptance or a manager taking the operator first fails the whole acceptance without partial membership (409, verbatim). Successful invitation register/Google/accept records mailbox proof.
- **States** — *loading preview* · *ready* · *unusable* (409 `SECURITY_TOKEN_INVALID` for expired, used, declined or replaced links → **Peça um novo convite a quem administra a lotérica.**) · *link missing* (no token / reloaded) · *e-mail mismatch* (403) · *already a member* (409) · *validation* (400 verbatim) · *rate limited* (429) · *Google unavailable* (503) · *declined* · *result unconfirmed* (register/accept/Google have no replay key: after a lost response, sign in — or re-open Branch picker — to see whether the membership exists before trying again; a repeat of a consumed link returns the unusable state) · *success*.
- **Navigation** — e-mail link only. Register or Google completion → Branch picker / session (a single branch opens automatically). Accept → a branch session for the returned `BranchId` → that role's home. Decline, cancel and unusable → Login.

## Plataforma — Nova lotérica

- **Purpose** — let the Lotero team create a lotérica — default seeds, optional initial structure and the owner's Admin invitation — and follow that owner invitation until it is accepted.
- **Primary job** — create one lotérica correctly once, then make sure its owner can get in.
- **Access** — platform identity tier (`[TokenPlatformOperator]`): an active identity whose stored platform flag is rechecked on every call; a branch token or a non-platform identity gets 403 `PLATFORM_ONLY`. The area never reads or opens tenant data; the caller receives **no** membership in the lotérica it creates.
- **Default view** — the onboardings this device created or looked up, newest first, each re-read on open `[derived]` device-local list of `RequestId`s; plus **Nova lotérica** and **Consultar por código** (a request id from the CLI or a teammate). There is no server list of onboardings (gap AB).
- **Data shown**
  - **Wizard form** — `[DTO: RequestOperateBranchJson]` in five steps: (1) **Lotérica** — `Name`, `Cnpj?`, `Address?`, `Phone?` (masks per formatting §6); (2) **Terminais** *(optional, up to 30)* — `Terminals[] {Name, PairedTabName?}`, each optionally with a new paired conta fiado; (3) **Produtos adicionais** *(optional, up to 30)* — `AdditionalProducts[]` names, created besides the default seed products, which the screen mentions without listing (no pre-creation read exists); (4) **Operadores** *(optional, up to 50)* — `Operators[] {Name, TerminalIndexes[]}` pointing at step 2's terminals; (5) **Responsável e revisão** — `OwnerEmail` and a read-only summary. Duplicate names and indexes are checked client-side as a hint; the server validates everything again.
  - **Request identity** — `RequestId`, a client-generated id frozen when the wizard first submits, stored with the payload in the device's isolated identity scope like a financial `Idempotency-Key`. `[DTO]`
  - **Result / detail** — `[DTO: ResponseOperatedOnboardingJson]`: `BranchName`, `BranchId`, `OwnerEmail`, `OwnerInvitationStatus` (label per copy §5), `DeliveryStatus` (label per copy §5: **Enviado ao servidor de e-mail** — SMTP acceptance, not inbox arrival — **Falha no envio**, **Envio pendente**), `ExpiresAt`, `RequestId`.
- **Actions** — **Criar lotérica** → `POST /platform/onboarding` (201 new; 200 when the same id, actor and payload replay — the same branch, never a second one); **Consultar** → `GET /platform/onboarding/{requestId}`; **Reenviar convite do responsável** → `POST /platform/onboarding/{requestId}/reissue-owner-invitation` (replaces the capability; an accepted invitation is 409 `INVITATION_ALREADY_ACCEPTED`). Demo data is a CLI-only option and is not offered here.
- **Audit / lock context** — creation is one transaction: branch, default seeds (categories, types, products, settings, time-entry policy), optional terminals with paired Tabs, extra products, operators with assignments, and a pending owner Admin invitation. The lotérica may have zero members until the owner accepts. No fiado repayment method is seeded; that is the owner's setup (Manager Work Queue checklist).
- **States** — *platform unavailable* (403 `PLATFORM_ONLY` → hide the area, re-read profile) · *editing* (wizard; input kept on the device per step) · *validation* (400 `ONBOARDING_INPUT_INVALID` verbatim, the wizard returns to the step it most plausibly concerns only when unambiguous, otherwise the review step lists it) · *owner e-mail unavailable* (409 `INVITATION_TARGET_UNAVAILABLE`, verbatim — the responsible person's account cannot be invited; correct the e-mail) · *submitting* · *result unconfirmed* (lost response or 5xx → **Verificar e tentar novamente** resends the identical request id and payload, which returns the existing branch if it was created) · *request conflict* (409 `ONBOARDING_REQUEST_CONFLICT`: the id was used with different data — keep the original record, never re-key automatically; a deliberately different lotérica starts a new wizard) · *created* (with delivery status) · *delivery failed* (**O servidor de e-mail não aceitou o convite. Reenvie.**) · *owner accepted* · *not found* (404 `ONBOARDING_NOT_FOUND`) · *error*.
- **Navigation** — from Branch picker or the Session menu (platform operators only); back → Branch picker. It links to no tenant screen.

## Manager Work Queue

- **Purpose** — the manager's home: an **exception-first work queue** of what needs action on the branch — not a KPI page.
- **Primary job** — clear today's approvals and act on exceptions (variances, non-submitters, blockers) fast.
- **Access** — manager-admin; whole-branch.
- **Default view / filter** — branch-local today (`BranchLocalDate` from `GET /branch/current`); the queue never switches day by itself. It has no status filter: every group below is shown, and the needs-action groups (Pending approvals, Rejected) lead — managers open this to act, not to browse. There is no operating calendar: *today* is literal, and earlier pending days surface through the backlog banner. *No activity today* means today's queue response returns no close rows and no `NotSubmitted` row carrying a `DailyCloseId`; the banner then offers the jump.
- **Data shown** *(a queue grouped by exception type in a fixed order — Pending approvals → Rejected / fix-needed → Not submitted → Cash-variance exceptions → Reconciliation blockers → Draft transactions → Operator-link requests; the close, variance, and not-submitted groups, the backlog banner, and the Draft count all come from **one call** — `GET /report/manager-queue?date=`; the owner setup checklist, when shown, precedes the banner)*
  - **Owner setup checklist** *(Manager/Admin, Gestão)* — what the branch still needs before people can work, composed only from delivered reads; there is **no** readiness field or setup endpoint, and the client invents no completion flag. Each item shows **Concluído**, **Pendente** or **Não foi possível verificar** (with its own retry), what it unlocks, and a link to the screen that changes it. `[composed]`
    - *Terminais* — at least one Terminal account: `GET /account` (`Type = Terminal`). Without one, no day can be opened. → Accounts.
    - *Operadores* — at least one operator: `GET /operator`. → Operators / Add employee.
    - *Terminal para cada operador* — each listed operator holds an active Terminal assignment: `GET /operator/{operatorId}/accounts` per operator, read in bounded parallel, at most 50 operators verified per load (beyond that the item says how many were checked). A Member without one cannot work. → Account assignment.
    - *Forma de recebimento de fiado* *(conforme o uso)* — at least one active type with `FiadoPaymentKind`: `GET /transaction-type`. None is seeded; without one, Receber pagamento cannot be used. → Categories & Transaction Types.
    - *Conta fiado pareada* *(conforme o uso)* — Terminals with `TabAccountId`: `GET /account`. Only fiado operations need it. → Accounts.
    - *Feriados de {ano}* *(conforme o uso)* — any holiday in the branch-local year: `GET /holiday?Year=` with `PageSize=1`, reading `TotalCount`. They move cheque/card due dates and time-entry statuses. → Holidays.
    - *Equipe* *(informativo)* — active members `GET /branch/users` and pending invitations `GET /invitation?Status=Pending` as counts with a link to Branch members; it has no completion state, because a one-person lotérica is valid.
    The checklist shows while any of the first three items is pending; once they are all done it collapses to one line (**Configuração inicial concluída**) whose optional items stay reachable. Hiding that line is a device-local preference per branch, never a server state. Opening counts per Terminal belong to server M10's pending go-live feature and are not an item here.
  - **Pending backlog banner** — above the groups whenever an unlocked day before the selected date holds a `Submitted`, `Rejected`, or `Draft` close: counts per status and **Ver dia mais antigo**, which sets the selected date to the oldest such day. **Ver dia mais antigo** sets the selected date to `OldestPendingDate`. `[DTO: ResponseManagerQueueJson.Backlog / ResponseManagerQueueBacklogJson]` (`SubmittedCount`, `RejectedCount`, `DraftCount`, `OldestPendingDate?`) over unlocked days before the requested date; the banner is hidden when all three counts are zero, which is also when `OldestPendingDate` is null. Never stitched from paginated `GET /dailyclose` pages: those cannot give exact per-status counts, and the list's order is not part of the contract.
  - **Seu turno** *(linked Manager/Admin only)* — one line linking into Meu turno. With a workstation already chosen today on this device: the terminal and today's close status (`[composed]`: `GET /operator/self-context` + `GET /dailyclose` for `(account, today)`). Several Terminals and none chosen yet: *"Escolher terminal"*. No usable Terminal assignment: *"Sem terminal atribuído"*, linking to Account assignment. Absent for an unlinked caller.
  - **Pending approvals** — closes with `Status = Submitted`, plus `PendingApprovalCount`. `[DTO: ResponseManagerQueueJson.Closes / ResponseManagerQueueCloseJson]` (AccountName, recorder user/operator, current submitter user/operator, Status, SubmittedAt?). Keep “who counted” separate from “who sent”.
  - **Rejected / fix-needed closes** — closes with `Status = Rejected`. `[DTO: ResponseManagerQueueCloseJson]`.
  - **Not-submitted accounts** — expected terminal accounts with no submitted-or-later close. `[DTO: ResponseManagerQueueNotSubmittedJson]`; when an open Draft exists the row carries `DailyCloseId` + `Status` for the deep-link.
  - **Cash-variance exceptions** — unapproved closes first, biggest `|variance|` first within each group; approved closes follow. `[DTO: ResponseManagerQueueCloseJson.VarianceValue?]` — joined server-side by `(Date, AccountId)`, no client-side cross-join. The biggest-first ordering is `[derived]`: the endpoint returns close rows ordered by account name.
  - **Day variance aggregates** — `TotalVariance` / `MeanVariance` for the selected date. `[DTO: ResponseManagerQueueJson]`.
  - **Month-end reconciliation blockers** — `[DTO: ResponseMonthlyReconciliationJson.Blockers + LockReady]` (`[composed]`: a call to `/report/monthly-reconciliation/{year}/{month}`). Blockers include unapproved closes, Draft transactions, and direct Terminal activity missing its expected close.
  - **Draft transactions blocking month lock** — count of `Status = Draft` transactions on every unlocked day up to branch-local today — not only the earliest unlocked month the reconciliation blockers cover. `[DTO: ResponseManagerQueueJson.UnlockedDraftTransactionCount]`; unlike the backlog banner it does not move with the selected date.
  - **Operator-link requests** — pending requests from Members with no operator link or no usable account assignment; each opens Operators to resolve it. `[DTO: ResponseManagerQueueJson.PendingOperatorLinkRequestCount + ResponseListOperatorLinkRequestsJson]` — count is branch-wide, independent of the selected date; details use bounded `GET /operator-link-request?Status=Pending`. Resolve through Operators, then account assignment as needed.
- **Actions** — open a close **routed by its status** (only `Submitted` is approvable): `Submitted` → Daily-close approval · `Draft` (a `NotSubmitted` row carrying `DailyCloseId`) → Close day (Manager/Admin may edit items) · `Rejected` → Fix & resubmit · `Approved` → Daily-close approval, read-only; open a report; jump to a blocker's source (`UnapprovedClose` → status-routed close, `DraftTransactions` → Transactions list filtered to Draft/day, `MissingExpectedClose` → Open day for the returned account/day); change day. From the owner setup checklist: open the screen that resolves an item (Accounts, Operators / Add employee, Account assignment, Categories & Transaction Types, Holidays, Branch members) and re-read the checklist on return.
- **Audit / lock context** — shows `LockDate` (`[composed]`: `GET /setting`) and reconciliation `LockReady`. `LockReady` is advisory for the viewed month; the lock action atomically rechecks the entire unlocked interval. If imported legacy state shows a current/future `LockDate`, route the manager to Monthly reconciliation: the explicit command is the recovery path and validates from the operational floor before replacing that impossible boundary.
- **States**
  - *loading* — queue skeleton.
  - *checklist partially verified* — an item whose read failed shows **Não foi possível verificar** with its own retry; the queue groups are unaffected and a failed item is never shown as done or pending.
  - *empty* — nothing needs action on the selected day → an all-clear state; the backlog banner still appears when earlier unlocked days hold pending closes. A recent-close summary, if shown, is `[composed]`: `GET /dailyclose` most-recent row.
  - *error* — `ResponseErrorJson` shown; retry.
  - *success* — grouped queue.
- **Navigation** — Gestão home after a Manager/Admin branch session; deep-links to Daily-close approval / Close day / Fix & resubmit (by close status), Open day (a missing expected close), Monthly reconciliation + lock, Transactions list (Draft filter), the report screens, Operators (an operator-link request), and the setup screens named by the owner setup checklist. A linked Manager/Admin may switch explicitly to Meu turno / Operator Day Cockpit without changing the branch token or role.
- **Note** — server M7.5 shipped this screen's one-call read (gaps §3, resolved), and M7.7 Phase 7.8 gave it its final name, `GET /report/manager-queue`, with the fields unchanged: the close, variance, and not-submitted groups need no client-side joins. M7.7 Phase 4 aligned reconciliation readiness with direct Terminal activity and shipped the atomic lock command. What remains `[composed]`: the reconciliation blockers, `LockDate` (`GET /setting`), and the optional recent-close summary on the all-clear state. M7.7 Phase 7.5 added the backlog banner's counts and the Draft-transaction count to the queue response (gap W, resolved), so neither needs a second call.

## Daily-close approval

**M9.5 first-transition limitation — reviewer procedure.** A prior-only retired fee can be included in the server opening while absent from current review rows: an exact physical count can therefore produce −R$100 without proving a cash shortage. Use the **explanation differs from server** state whenever the derived equation differs from the server preview/official variance. Compare monetary values in exact cents for the same count, version and complete active ledger across all pages, excluding the variance product. Before submit, compare the candidate equation with the server preview for those same inputs; on approval compare the saved equation with the official value. Pending, failed or stale reads cannot establish agreement: retain input, refresh the matching data and show **Não foi possível conferir a diferença**. A numerical mismatch detects disagreement, not its historical cause; no completeness flag or omitted amount is inferred.

**Explanation differs from server — Close day and approval.** Label the visible opening total **Subtotal da abertura exibida**. Keep the derived equation separate from **Diferença calculada pelo servidor** (preview) / **Diferença oficial** (saved), displaying the signed BRL server figure with neutral text and no Falta/Sobra wording or sign-based shortage/surplus color. Show a persistent warning: **A conta exibida não confere com a diferença do servidor. Confira a abertura e o fechamento anterior com a gerência antes de enviar ou aprovar.** Copy §7.1 uses this same state. Preserve input and the ordinary save/submit/approval controls and permissions; this is guidance to consult management, not a new forced lock or acknowledgement. Recompare on matching refreshed data; clear the warning only when the values agree. The manager consults the per-Terminal transition inventory output retained with the deployment review (the query is in `server/docs/database-environments.md`), opens the identified prior close and compares its saved fee with the current difference and actual ledger. Record the explanation in ordinary Notes before submit. If unexplained, stop submission/approval and escalate under open gate 3.7. Do not rewrite history, add a compensating transaction or remove counts to force zero. AA recovery and first-transition acceptance remain pending.

- **Purpose** — review one submitted close *as a comparison* and approve it or reject it with a reason.
- **Primary job** — decide approve/reject quickly, with the variance and its cause visible.
- **Access** — manager-admin; whole-branch.
- **Default view / filter** — the single close passed in; day transactions filtered to its `(account, date)`.
- **Data shown** *(comparison: opening → closing → variance, with source clearly marked)*
  - **Close header** — account, date, status, `Version`, opener, immutable recorder user/operator, current submitter user/operator, `SubmittedAt?`, rejection reason (if any), and the recorder's `Notes?` explanation. `[DTO: ResponseDailyCloseReviewJson]` — **one call**, `GET /dailyclose/{id}/review`, serves the header and every item row below. Do not label the submitter as the person who counted. When `RecordedByUserId` is the current user, show the self-recorded marker "Você registrou este fechamento" beside the actions — self-approval is permitted (gap R). `[DTO: ResponseUserLoginJson.UserId]` — the required identity-tier caller id is delivered by server M8 Phase 2.
  - **Closing snapshot — operator-entered** — every active product ordered by `DisplayOrder`, carrying `ProductName` + nullable `ClosingValue?`; a null closing means the operator has not entered that row. `[DTO: ResponseDailyCloseReviewItemJson]`. **Mark non-variance values as operator-entered.**
  - **Opening values — system-derived** — per product, `OpeningValue?` from the most recent prior **counted** close (`ItemsFirstRecordedAt != null`, regardless of Draft/non-Draft status), derived server-side. `[DTO: ResponseDailyCloseReviewItemJson]`. `null` on the variance row by design.
  - **Cash variance (Diferença Caixa) — system-calculated** — the item flagged `IsCashVarianceProduct = true` — **do not name-match the product string**. `[DTO: ResponseDailyCloseReviewItemJson]`; **mark system-calculated (§6.5/§6.12), not operator-entered.**
  - **Variance explanation** — immediately below the opening → closing → variance comparison, the four totals and the equation with this close's actual values, e.g. `R$ 2.437,00 − R$ 2.199,00 − (R$ 400,00 − R$ 150,00) = −R$ 12,00`. Opening and closing totals sum **every** counted product (not only Dinheiro) and exclude the `IsCashVarianceProduct` row; the movement totals are the `Status = Active` entradas and saídas of the close's exact `(account, date)` across **all** result pages — Draft and Cancelled rows excluded. The heading **Como a diferença é calculada**, the generic formula, and the sign/scope teaching text sit in a collapsed **Ajuda sobre diferença de caixa** (copy-guidelines §7), never repeated in the main area. Totals and equation are explanatory `[derived]` from the review items `[DTO]` and the day's transactions `[composed]`; the persisted system-calculated variance stays authoritative and is what the comparison row shows. If the recomputed equation disagrees with the official value, use the **explanation differs from server** state above — never change the official figure or write the recomputation back.
  - **Recorder / submitter without an Operator** — when a named recorder or submitter has a null Operator (an elevated user recording in Gestão), show **Sem operador associado ao registro** with a short explanation that management recorded it; this is valid, not missing data. `[derived]` presentation of nullable recorder/submitter identities in `ResponseDailyCloseReviewJson`.
  - **Day's transactions** — context for the count. `[composed]`: `GET /transaction?AccountId&DateFrom=DateTo=` the close's `(account, date)`. An automatically generated movement carries its **Automática** label here too (see Transactions list).
- **Actions** — **Approve** → `POST /dailyclose/{id}/approve`; **Reject with reason** → `POST /dailyclose/{id}/reject` (`RequestRejectDailyCloseJson`; reason required); on an Approved close, Manager/Admin **Reopen for correction** → `POST /dailyclose/{id}/reopen` (returns to Draft and requires submit + approval again); on an unlocked Submitted close, **Gerenciar fechamento** → the same close's Close day in Gestão, where **Desfazer envio** lives (recall retains the count and the immutable recorder while clearing the current submission identity), returning here with the queue origin kept. This adds discoverability, not a permission: Manager/Admin recall before lock is already allowed, with or without an Operator link.
- **Audit / lock context** — Submitted metadata (SubmittedBy, SubmittedAt), reviewer metadata on finalized closes, and the submitted Notes snapshot. The ledger and notes are frozen at submit, so the displayed count and cash variance are an authoritative immutable snapshot. All actions (Approve, Reject, Reopen) are blocked at or before LockDate. Reopening an approved close reverts it to Draft and requires resubmission and approval.
- **States**
  - *loading* — close + items skeleton.
  - *not-found / cross-branch* — 404.
  - *already finalized* — read-only with the outcome: no Approve/Reject, only **Voltar** — plus **Reabrir para correção** on an Approved close for Manager/Admin before `LockDate`.
  - *self-recorded* — the caller recorded this close: the marker shows and Approve/Reject stay available.
  - *error* — reject without a reason → inline 400 (`ResponseErrorJson`); other failures → the standard error display.
  - *success* — status flips; return to the originating view (Manager Work Queue when none), its pending count decremented.
- **Navigation** — Gestão; from Manager Work Queue (pending item), a Cash-variance summary row, a Monthly reconciliation blocker, Dashboard recent/variance preview or Monthly financial report Terminal/day close link, each status-routed so only `Submitted` opens actionable; returns to the originating view, otherwise Manager Work Queue. **Gerenciar fechamento** → Close day in Gestão and back.

## Transaction — Create (fast entry)

- **Purpose** — record a money movement **fast** (operator at the counter).
- **Primary job** — enter a transaction in as few taps as possible.
- **Access** — branch-member with linked operator + account scope, or manager-admin (same scope as `POST /transaction`).
- **Permission fallback** — Member without a linked operator → **400** `TRANSACTION_MEMBER_REQUIRES_OPERATOR_LINK` (the `RecordedByOperator` resolver runs before the account-scope guard, so it surfaces as a validation error, not a 403); the screen explains a link is needed. Account out of scope → **403** `TRANSACTION_MEMBER_ACCOUNT_OUT_OF_SCOPE`. (Contrast the *read* path §6.10, where no-linked-operator is 403.)
- **Default view / filter** — today's date, the operator's linked/primary account, current time pre-filled.
- **Data shown**
  - **Form (full set)** — `[DTO: RequestCreateTransactionJson]`: `TransactionTypeId` (drives required fields), `Value`, `Date`, `TransactionTime?`, `AccountId`, `ClientId?` (fiado/Tab), `DueDate?` (cheque/card), `Description?`, `RecordedByOperatorId?`, `SaveAsDraft`. **Role-shaped:** a Member must **omit** `RecordedByOperatorId` — even their own id → 400 `TRANSACTION_MEMBER_CANNOT_OVERRIDE_RECORDED_BY_OPERATOR`; a Manager/Admin may supply it (acting on behalf of an operator) and **must** when they have no linked operator (400 `TRANSACTION_REQUIRES_RECORDED_BY_OPERATOR`). In Meu turno, a linked Manager/Admin omits it by default so the server resolves the caller's own Operator; choosing another operator is an elevated on-behalf task entered from Gestão.
  - **Lookups** — types & categories: `[composed]` `GET /transaction-type` + `GET /category` (any branch role); accounts: Member → own scope from `GET /operator/self-context`, Manager/Admin → `GET /account` (Manager/Admin-only); clients: `GET /client`; operators (elevated on-behalf entry): `GET /operator` (Manager/Admin-only). For a linked Manager/Admin entering from Meu turno, self-context supplies the initial own account/operator context; the whole-branch and on-behalf choices belong to Gestão without reducing the caller's server permission. **The type list never offers the fiado repayment types** — a repayment is recorded only through Receber pagamento, which shows the balance, the drawer effect, and the retry protection. Repayment types are hidden by structure, never by name: a type that requires a Tab account and a client with category direction `In` `[derived]` (the server refuses any Tab `In` on create with `TRANSACTION_FIADO_PAYMENT_REQUIRES_COMMAND`); a configured repayment method also carries `FiadoPaymentKind` `[DTO: ResponseTransactionTypeJson]`. Fiado **sale** types stay. Types with a non-null `SystemRole` `[DTO: ResponseTransactionTypeJson]` (the linked Terminal movements below) are never offered for manual creation either (`TRANSACTION_TYPE_SYSTEM_ONLY`).
  - **Physical effect of a fiado sale** — when a fiado sale hands the client counted stock (e.g. raspadinha), saving it also writes, in the same operation, an automatically generated Terminal **stock saída** on the selected Tab's paired terminal, explicitly *not a cash withdrawal*, so the terminal's correct count yields zero difference (§6.12). The operator records the sale once; the system picks the predefined counterpart type. Every fiado sale must identify what the client received, including items or services outside the closing-products list — this does not make a closing-product selector mandatory, and how the shop records each kind of fiado sale (bolão, items outside the list) is an open product question (loto-specs §9). A sale with no counted-stock effect writes only the Tab row. The operator's explicit choice is `RequestCreateTransactionJson.HandsOutCountedStock` `[DTO]` — never preselected or inferred from the type; the response names the generated row in `GeneratedTransactionId`. The pair needs the paired terminal's open Draft close (`TRANSACTION_REQUIRES_OPEN_DAILY_CLOSE` / `TRANSACTION_DAILY_CLOSE_LEDGER_FROZEN`), an active pairing (`TRANSACTION_FIADO_PAIRED_TERMINAL_REQUIRED`) and, for a Member, both the Tab grant and the terminal in scope.
  - **Impact preview** *(automatic, never blocking)* — `[DTO: ResponseCreateTransactionPreviewJson {Impact, Warnings}]` — Receivable / Fiado / CashVariance impact; `Warnings` is a root-level sibling of `Impact`. It runs automatically inline (debounced) once the form holds a complete candidate and refreshes as fields change. It never blocks **Save**, and a failed preview shows nothing blocking. For a counted-stock fiado sale the preview checks the whole pair like the write (the same 403/409 keys can surface early) and its cash-variance part describes the paired terminal's close; whether the sale enters aging comes from the client's FIFO position, so existing credit can keep it out (server M7.7 Phase 5 review fixes).
- **Actions** — **Save** (Active) → `POST /transaction`; **Save as draft** → `POST /transaction` with `SaveAsDraft = true`; the automatic preview → `POST /transaction/preview`. Each real create sends a fresh client `Idempotency-Key`; an uncertain result retries the identical body with the same key and accepts the deterministic replay. A committed replay is resolved before DailyClose account coordination, so an in-flight Submit/Approve cannot turn that durable retry into a ledger-busy conflict.
- **Audit / lock context** — blocked when `Date ≤ LockDate` (explain the period is locked); `RecordedByOperatorId` stamped. A Terminal save first requires an active same-day DailyClose: none → `TRANSACTION_REQUIRES_OPEN_DAILY_CLOSE`, Draft → writable, non-Draft → `TRANSACTION_DAILY_CLOSE_LEDGER_FROZEN`. Tab and Bank writes have no DailyClose requirement — except a fiado sale that delivers counted stock, whose linked Terminal row needs the paired terminal's open Draft close for the date; a Submitted/Approved/Rejected close there blocks the whole pair (`TRANSACTION_DAILY_CLOSE_LEDGER_FROZEN`; server M7.7 Phase 5.6). Both rows are written together or not at all. **Day not open yet:** when that block is exactly "no close yet for this terminal and date" and the caller may open it under Open day's rules (a Member with the terminal in scope, today only; Manager/Admin per their rule), the screen names the terminal — the chosen Tab's paired terminal, not necessarily the workstation — and offers to open the day (**Abrir o dia**, copy-guidelines §7). Opening the day saves nothing else: the operator returns to this form with everything typed and confirms the sale there. A frozen close gets no offer. A sale with no counted-stock effect never shows the prompt. Impact preview remains hypothetical. The server accepts create-envelope replay for 24 hours and periodically purges expired envelopes; changing the body while reusing a live key is a verbatim 409 conflict.
- **States** — *loading* lookups · *validating* (400 inline) · *lock-date blocked* · *terminal day not open* (offer to open, when permitted) · *preview shown* · *success* (return to Day Cockpit / list) · *error* (row **not** assumed saved).
- **Navigation** — from Operator Day Cockpit in Meu turno, Transactions list in either mode, or the **Nova transação** navigation shortcut; returns to the semantic origin on save (Cockpit or list; a shortcut entry has no origin, so it returns to Transactions list). A selected fiado client links to its Client statement. **Abrir o dia** → Open day for the paired terminal → back here with the input intact. *Open, not decided:* whether opening another terminal's day this way leaves the cockpit's workstation choice unchanged.

## Transaction — Edit (correction / audit)

- **Purpose** — correct an existing transaction's limited fields, with full impact preview — a **manager-control / audit** tool, not fast entry.
- **Primary job** — fix a mistake on a recorded row, seeing the downstream impact before committing.
- **Access** — per the §6.11 mutation contract: Manager/Admin elevated; a Member must additionally be the **recording operator** of the row *and* act on the **same branch-local day**. Shared-account lists expose other operators' rows to a Member — those open **read-only** (`[derived]` gate mirroring the guard).
- **Permission fallback** — Member without a linked operator → 403 `TRANSACTION_MEMBER_REQUIRES_OPERATOR_LINK` (mutation path); Member with the transaction's account out of scope → 403 `TRANSACTION_MEMBER_ACCOUNT_OUT_OF_SCOPE`; Member who is not the recording operator → 403 `TRANSACTION_MEMBER_NOT_RECORDING_OPERATOR`; Member editing a prior-day row → 403 `TRANSACTION_UPDATE_REQUIRES_SAME_DAY`; missing/cross-branch id → 404 `TRANSACTION_NOT_FOUND`.
- **Data shown**
  - **Loaded transaction (read context)** — `[DTO: ResponseTransactionJson]`: value, dates, status, audit fields, `Version` — but ids only for type/category/account/client; display labels are `[composed]` role-safely: `GET /transaction-type` + `GET /category` (any role); account name via `GET /operator/self-context` (Member) or `GET /account` (Manager/Admin); client via `GET /client/{id}`. Preserve the response `ETag` with the draft form.
  - **Editable fields (restricted)** — `[DTO: RequestUpdateTransactionJson]`: `Description?`, `DueDate`, `PaidAt?` (cheques and card settlements only — disabled on Tab/fiado rows: the server ignores `PaidAt` for fiado, whose settlement is **Receber pagamento**), `ClientId?`, `TransactionTime?` only. **`Value`, account, type, and `Date` are read-only** — cancel + re-create to change them.
  - **Impact preview** *(Manager/Admin only — see Actions)* — `[DTO: ResponseEditTransactionPreviewJson {TransactionId, Impact, Warnings}]` — all three root-level siblings. Show only the effects that apply to the current candidate, as concrete before/after values; an inapplicable section is omitted, never rendered as zero. An account with no close (a bank account, whatever its name) has no closing count and no cash variance: say so instead of showing **Diferença de caixa: R$ 0,00**. With a close, keep current/projected variance distinct from the change in variance (`VarianceDelta` is structurally zero under the restricted edit — a zero change is not a measured variance) and label the close's workflow status; a Draft close's current/projected figures are unavailable from this preview. Fiado client deltas appear only for an actual Tab client reassignment. Changing the candidate invalidates the displayed preview.
  - **Generated movement** — an automatically generated Terminal movement (a fiado sale's stock saída or a cash repayment's entrada) carries the **Automática** label beside its type, kept separate from its lifecycle status (it can be Rascunho, Ativa, or Cancelada). The detail explains what generated it and who initiated that operation — e.g. *"Gerada automaticamente ao registrar um recebimento de fiado. Operação registrada por {nome}."* — and offers **Abrir origem fiado** when access permits. It is always read-only: corrections and cancellation go through its source operation, whose finalize/cancel carries the counterpart with it. Origin comes from structured data, never from parsing the description or type name: `GenerationKind` and `GeneratedFromTransactionId` `[DTO: ResponseTransactionJson]`; a source names its leg in `GeneratedTransactionId`. Every direct write on the generated row returns `TRANSACTION_GENERATED_ROW_READ_ONLY`; opening either row still applies that row's own access.
  - **Installment row** — **Abrir plano completo para edição** opens Installment plan in existing-plan mode with this installment in view. While the plan still has Draft installments (plan `Status` Draft or Mixed), a row never offers **Finalize draft** here — the plan finalizes as a whole and the server refuses a single installment; a deep link to such a row lands in the plan editor, with this screen's audit details still readable and a clear way back to the plan. After activation the row keeps its individual corrections (settlement date, `PaidAt`) — cheques clear on different days — and stays visibly associated with its plan through **Abrir plano completo**. `[DTO: ResponseTransactionJson.OriginTransactionId]`; the plan's status comes from `[DTO: GET /transaction/installment/{originTransactionId} → ResponseInstallmentPlanJson.Status]`.
- **Actions** — **Preview edit** → `POST /transaction/{id}/edit-preview` — **Manager/Admin only** (the deliberate §6.14 exception); a permitted Member saves without the impact preview; **Save** → `PUT /transaction/{id}` with the loaded `If-Match`; **Finalize draft** → `POST /transaction/{id}/finalize` with the loaded `If-Match` (promote Draft → Active); **Cancel** → `POST /transaction/{id}/cancel` (required reason + loaded `If-Match`). For an installment row, offer **Cancel only this row** or **Cancel remaining plan installments**, behind a confirmation listing the affected cheques (executed per row from each sibling's list `Version`; enumeration and concurrency rules: loto-specs §6.10/§6.11).
- **Audit / lock context** — `UpdatedAt`/`UpdatedByUserId` stamped; blocked when `Date ≤ LockDate`; shows `CancelledAt`/`CancelledByUserId`/reason when cancelled; the current `Status` gates which actions are available (e.g. Finalize only on Draft). Finalize and Cancel additionally return `TRANSACTION_DAILY_CLOSE_LEDGER_FROZEN` while a non-Draft close exists for the row's `(account, date)`; the narrow field edit stays available because it cannot change §6.12 inputs.
- **States** — *loading* · *validating* (400 inline) · *lock-date blocked* · *preview shown* · *read-only* (Cancelled / locked / generated movement) · *success* · *error*.
- **Navigation** — from Transactions list, a drafts list (Day Cockpit), Daily ledger, Fiado aging, Open-cheque aging, Upcoming settlements or Dashboard cheque/receivable items; returns to that actual source with branch, filters/page, report month/section and clicked transaction focus retained. **Abrir plano completo para edição** → Installment plan (existing-plan mode) and back; **Abrir origem fiado** → the source operation.

## Transactions list

- **Purpose** — the browsable, filterable ledger — the audit surface and the entry point to corrections.
- **Primary job** — find a specific transaction fast (by day, account, client, status) and open it.
- **Access** — branch-member: a Member sees rows on their **linked accounts** (§6.10 — a shared account shows both operators' rows; `Mine = true` narrows to own); Manager/Admin see the whole branch.
- **Permission fallback** — on the **list**, every empty/out-of-scope case is an **empty page short-circuit** (no 403, no row-existence leak): Member with no linked operator, linked with zero active account links, or an explicit `AccountId` outside scope. The 403s (`§6.10`) belong to the **detail read** (`GET /transaction/{id}`) and to mutations — not here.
- **Default view / filter** — `DateFrom = DateTo =` today (branch-local), all statuses, all in-scope accounts, `Mine` off, page 1 — the arriving question is almost always about *today*. Deep-links override it (e.g. the Work Queue's Draft-blocker link). In Meu turno, a linked Manager/Admin opening the list from navigation starts with `Mine = true` (the server resolves it to their linked operator; clearing it shows the whole branch); a Member's default is unchanged, since the server already scopes them to linked accounts. The Operator Day Cockpit's today's-transactions link deep-links with the cockpit's `(AccountId, today)`, so a Member and a linked Manager/Admin see the same rows for that account.
- **Data shown**
  - **Rows** — `Version`, `OriginTransactionId?`, `Date`, `Value`, `Direction`, `Status`, `AccountName`, `ClientName?`, `TransactionTypeName`, `DueDate`, `PaidAt?`, `Description?`, `CreatedAt`. `[DTO: ResponseListTransactionsJson.Items]` — names and guarded-action data arrive together; `OriginTransactionId` identifies plan membership and `Version` is the per-row `If-Match` value, so no detail lookup is required before a direct finalize/cancel. An automatically generated movement shows a small **Automática** label beside its type, separate from its status — from structured origin data, never from the description or type name (`GenerationKind` `[DTO: ResponseListTransactionsJson.Items]`; filter them with `TransactionTypeId` of the system types). The date renders as data, not as a separate link.
  - **Paging** — `Page`, `PageSize`, `TotalCount`, `TotalPages`, `HasNext`/`HasPrevious`. `[DTO]`.
  - **Filters** — `[DTO: RequestListTransactionsJson]`, **role-shaped**: every role gets `DateFrom`/`DateTo`, `Status`, `ClientId` (`[composed]` `GET /client`), `Mine`, and deep-link-only `OriginTransactionId` for plan siblings. **Member:** account options come from `GET /operator/self-context` (the admin `GET /account` list is Manager/Admin-only), and the `OperatorId` filter is hidden — the server discards it for Members (`Mine` is the sanctioned own-rows filter). `OriginTransactionId` never widens linked-account scope; an out-of-scope plan is an empty page. **Manager/Admin:** full `AccountId` + `OperatorId` pickers, `[composed]` `GET /account` + `GET /operator`. **Tipo de transação** (every role, default **Todos**) — `TransactionTypeId`, combined server-side with the other filters before paging and counts, so `TotalCount` and the paging metadata describe the filtered set; options from `[composed]` `GET /transaction-type` (active types, including the two system-generated types identified by `SystemRole` — they can be filtered, never created manually). A carried-over id of a retired type still filters; an unknown id is an empty page. Scope rules unchanged; the selection stays visible and survives opening a row and returning, refresh, and paging. Filtering grants no edit access.
- **Actions** — open a row → Transaction — Edit: the **whole row** is the click/tap target (hover and keyboard-focus treatment make it discoverable), plus an explicit keyboard-accessible **Abrir transação** link per row carrying enough accessible context to name the transaction; enlarging the target keeps table semantics, native link behavior, text selection, and horizontal scrolling usable. Independent controls on the row (**Ver parcelas**, checkboxes, buttons) keep their own behavior and never also trigger the row. Opening grants no edit permission — locked, cancelled, and other non-editable rows still open read-only. A row of a plan that still has Draft installments (plan `Status` Draft or Mixed) opens Installment plan in existing-plan mode with that installment in view; identify a cheque-plan row from `OriginTransactionId` and enumerate its siblings with the same filter; issue selected guarded sibling cancels directly from the returned row `Version`s; new entry → Transaction — Create; new cheque plan → Installment plan; filter/paginate → `GET /transaction`.
- **Audit / lock context** — rows with `Date ≤ LockDate` open read-only in the edit screen; Draft/Cancelled rows read visibly distinct (they don't count in totals).
- **States** — *loading* (row skeleton) · *empty* (nothing matches the filter) · *error* · *success*.
- **Navigation** — primary ledger destination in Gestão and Meu turno; Work Queue deep-link (Draft filter); Operator Day Cockpit (its today's-transactions link, filtered to the cockpit's account and today); returns to itself after edit/create when it was the origin.

## Installment (pre-dated cheque) plan

- **Purpose** — record a pre-dated cheque as N installment rows, with the full plan and its downstream impact visible before anything is saved.
- **Primary job** — build a plan that sums exactly and lands on sensible due dates, then commit it in one action.
- **Access** — same scope as the `POST /transaction/installment` write twin: Member with linked operator + account in scope, Manager/Admin elevated.
- **Permission fallback** — same as Transaction — Create: 400 `TRANSACTION_MEMBER_REQUIRES_OPERATOR_LINK` · 403 `TRANSACTION_MEMBER_ACCOUNT_OUT_OF_SCOPE`.
- **Default view / filter** — today's date; the type picker restricted to `SettlementRule = OperatorEnteredCheque` types (`[derived]` filter of the type lookup — the endpoint rejects any other type); manual rows by default, auto-generation opt-in.
- **Data shown**
  - **Plan form** — `Date`, `Value` (must equal the row sum), `Description?`, `TransactionTime?`, `TransactionTypeId`, `AccountId`, `ClientId?`, `RecordedByOperatorId?` (same role rules as Transaction — Create: Members omit it, unlinked Manager/Admin must supply it), manual `Installments[] {DueDate, Value}` (2–24 rows, strictly increasing, first in the future) **or** `AutoGenerateInstallments + DueDate + InstallmentCount`, `SaveAsDraft`. `[DTO: RequestCreateTransactionInstallmentJson]`. Lookups are role-shaped exactly as on Transaction — Create.
  - **Row preview** — `TotalValue`, `InstallmentCount`, per-row `Index`, `DueDate` (weekend/holiday-adjusted), `Value` (rounding residual on the last row), `Description` (`CH PRE (i/N)` convention). `[DTO: ResponseInstallmentPreviewJson / ResponseInstallmentPreviewRowJson]`.
  - **Impact preview** — the would-be open-cheque group (`OutstandingTotal`, `OldestOpenDueDate`, `OldestOpenBucket`, per-row buckets), the aggregated fiado delta (Tab-account plans with a client), the cash-variance shift on the plan's `(account, date)`. `[DTO: ResponseInstallmentPreviewImpactJson]`.
  - **Sum check** — running `Σ rows − Value` hint while editing manual rows. `[derived]` (the server enforces the exact-sum invariant on submit).
- **Actions** — **Preview** → `POST /transaction/installment/preview`; **Save** → `POST /transaction/installment` (returns the created rows `[DTO: ResponseCreateTransactionInstallmentJson]`); **Save as draft** → same with `SaveAsDraft = true` (§6.3 — every row lands `Draft`). Real creates use one fresh `Idempotency-Key` for the whole plan; an uncertain result retries the identical plan/key, and a committed replay bypasses DailyClose account coordination.
- **Audit / lock context** — blocked when `Date ≤ LockDate`; `RecordedByOperatorId` stamped; Draft plans stay out of the open-cheque report, fiado sums, and variance until finalized. A non-Draft close on the plan's `(account, date)` freezes the real plan create with `TRANSACTION_DAILY_CLOSE_LEDGER_FROZEN` (the preview is hypothetical). Sibling cancellation is cataloged on Transaction — Edit and enumerated by `OriginTransactionId`.
- **States** — *loading* lookups · *validating* (400 inline — exact-sum, row bounds, non-cheque type, non-increasing dates; verbatim) · *preview shown* · *lock-date blocked* · *success* (→ back to origin) · *error*.
- **Navigation** — creation from Transactions list or Transaction — Create when a cheque-rule type is picked, returning there on save. Existing-plan mode also enters from a transaction installment, Open-cheque aging, Upcoming settlements or Dashboard cheque/receivable item via OriginTransactionId; return to the actual installment/list/report opener with its window, filters/page, section and clicked transaction focus, through the complete parent chain. Without origin → Transactions list.
- **Existing-plan mode** — the same screen opened with an `OriginTransactionId` (from Transaction — Edit's **Abrir plano completo para edição**, or from any row of a wholly Draft plan) instead of creating a plan; without a plan id the creation screen is unchanged.
  - *Data shown* — every authorized sibling together: the plan `Status` (Draft, Active, Mixed, Cancelled), per-status counts, persisted rows with status, version, due and payment dates and values, and the total of non-cancelled rows `[DTO: GET /transaction/installment/{originTransactionId} → ResponseInstallmentPlanJson]`, followed by correction fields per installment. Sibling enumeration never widens linked-account scope.
  - *Actions* — **Salvar esta parcela** per row → the existing per-transaction correction (`PUT /transaction/{id}` with that row's `If-Match`), limited to the fields the update contract already allows (`Description`, `DueDate`, `PaidAt`, `ClientId`, `TransactionTime`, under its existing guards); saving an unchanged row is disabled. Amounts, the plan total, the installment count, redistribution, account, business date, type, and direction are never editable here — this view grants no broader edit power and is not an atomic whole-plan save. Each row keeps its own rules: Manager/Admin elevated, Members only their own current-day rows, locked and cancelled rows read-only; paid rows remain visible and correctable where the contract permits. A payment timestamp is preserved when its date is unchanged. Each installment also links to its own Transaction — Edit (Manager/Admin impact preview, audit history). In-progress edits survive opening another installment and returning.
  - *Draft plan* — while the plan `Status` is Draft, **Finalizar plano** activates every installment in one atomic operation — all become Active together or none do → `POST /transaction/installment/{originTransactionId}/finalize` with every installment's id and loaded version `[DTO: RequestFinalizeInstallmentPlanJson → ResponseInstallmentPlanJson]`. No single-installment finalize is offered here or through a deep link (the server refuses it). A standalone Draft transaction keeps its individual finalize. Owner decisions (2026-10-16): edits are saved per installment (**Salvar esta parcela**) — there is no atomic **Salvar rascunho**, so pending edits are saved (or explicitly abandoned) before **Finalizar plano**, which sends the versions it just loaded; discarding is per-installment cancel — there is no whole-plan discard. A stale set returns `TRANSACTION_PLAN_STALE_WRITE`: reload and review before trying again.
  - *Mixed plan* — `Status` Mixed (Draft installments alongside Active and/or Cancelled ones, e.g. after cancelling one Draft installment): never described as wholly Draft. **Finalizar parcelas restantes** names exactly the remaining Draft installments and their total and asks for explicit confirmation; it sends `ConfirmMixedPlan = true` with those installments only. Without the confirmation the server answers `TRANSACTION_PLAN_MIXED_CONFIRMATION_REQUIRED`.
  - *Navigation* — returns to the originating installment or list.

## Client statement (Extrato de fiado)

- **Purpose** — one client's fiado debt and its history: *quanto o José deve e desde quando*.
- **Primary job** — answer the counter question in one screen, then collect.
- **Access** — Manager/Admin: any client in the branch. Member: any branch client, once they hold at least one explicit `OperatorAccount(Tab)` grant (signed 1.8 — never implied by a Terminal assignment). Fiado is the client's debt with the lotérica, not with one drawer, so the statement is always the client's complete branch-wide history across every Tab — including repayments recorded on Tabs the caller is not assigned to — so its running balances reconcile row by row and its window reconciles to the balance. Shared counter work: keeps the entry mode, like Clients.
- **Permission fallback** — a Member with no Tab grant sees an explanation that fiado needs a Tab assignment, and no data.
- **Default view / filter** — the client passed in; the whole fiado history through branch-local today, newest first, paged.
- **Data shown**
  - **Client** — `Name`, `Phone`, `Cpf?` (masks per formatting §6). `[DTO: GET /client/{id} → ResponseClientJson]`.
  - **Balance** — `OutstandingTotal` (branch-wide `Out − In` as of today) and `OldestUnpaidDate?`, labelled **Data da venda mais antiga em aberto**: the earliest sale `Date` (not due date) among the client's sales that still have a positive unpaid remainder after branch-wide FIFO settlement — a partially paid sale stays eligible, a fully settled one drops out, and none left → null. It is the minimum over the remaining unpaid sales, not the first row in due-date order. Netting is branch-wide FIFO per client (`DueDate, Date, Id`): a payment on any Tab settles the oldest debt first; aging still uses due dates. `[DTO: ResponseClientFiadoStatementJson]` — the statement read below, not the Client DTO.
  - **Balance display** — the signed internal balance (`Out − In`) is mapped for display, never changed: positive → the amount with **em aberto**; zero → **quitado**; negative → client credit, shown as a **positive** amount with a plus sign, the success color, and the label **crédito do cliente** (internal −10 → **+R$ 10,00 · crédito do cliente**; formatting §3). The same mapping applies to the current, opening, and closing balances and to every `RunningBalance`; movement amounts and their In/Out directions are unchanged. Explain credit in plain words, never with an equation that appears to make `80 − 90 = +10`. There is no credit-spending or refund command. `[DTO]` — `GET /client/{id}/fiado-statement` → `ResponseClientFiadoStatementJson` (server M7.7 Phase 5.5); a Member needs an explicit Tab grant (`CLIENT_FIADO_STATEMENT_ACCESS_DENIED`) and then reads the whole branch-wide statement.
  - **Movements** — every active fiado sale (`Out`) and repayment (`In`) on every Tab: `Date`, `Direction`, `Value`, `AccountName`, `TransactionTypeName`, `Description?`, and `RunningBalance` — the client's balance after that row, computed server-side over the full history. Draft and Cancelled rows are excluded, as in the balance. `[DTO: ResponseClientFiadoStatementItemJson]`, ordered `Date DESC, CreatedAt DESC, Id DESC`.
  - **Window** — `DateFrom`, `DateTo`, `OpeningBalance` (before the window), and `ClosingBalance` (at its end): each row's `RunningBalance` equals the chronologically previous row's `RunningBalance` plus its own `Out − In`, so consecutive rows reconcile on any single page; the window's oldest row starts from `OpeningBalance` and its newest ends at `ClosingBalance`, so `OpeningBalance + Σ(Out − In)` over **all** the window's rows — every page — `= ClosingBalance`, and a window ending today has `ClosingBalance = OutstandingTotal`. Omitted `DateFrom` means the whole history (`DateFrom = null` in the response); omitted `DateTo` means today. Paging per the list convention, `PageSize` 50 by default and at most 100. `[DTO: ResponseClientFiadoStatementJson]`.
- **Actions** — **Receber pagamento** → Receber pagamento for this client; change the window → the same read with `DateFrom`/`DateTo`; page through movements; print or share → the device's own print / PDF (there is no export endpoint).
- **States** — *loading* · *empty* (no fiado history — all-clear) · *error* · *success*.
- **Navigation** — from Clients (a client row), Transaction — Create (a fiado client selected), and Fiado balance (a client drill); returns to its source.

## Receber pagamento

- **Purpose** — settle a client's open fiado debt, partially or in full.
- **Primary job** — see the client's current debt, enter the amount and how it was paid, register it.
- **Access** — Manager/Admin, and Members holding at least one explicit `OperatorAccount(Tab)` grant (signed 1.8). A client has no owning Tab — the debt is branch-wide — so any such caller may take a payment for any client, recorded on a Tab they may use (see Form).
- **Data shown**
  - **Client and current balance** — `[DTO: ResponseClientFiadoStatementJson]` (`OutstandingTotal`, `OldestUnpaidDate?`) from the Client statement read.
  - **Form** — the Tab account receiving the payment (default: the workstation terminal's paired Tab in Meu turno; changeable among the caller's Tabs — a Member's granted Tabs, any Tab for Manager/Admin), amount, payment method (the choice of repayment transaction type — no separate field), date (branch-local today), description. `[DTO: RequestReceiveFiadoPaymentJson]` — `POST /transaction/fiado-payment`, server M7.7 Phase 5.1; the default Tab comes from the workstation Terminal's `PairedTabAccountId` `[DTO: ResponseOperatorAccountJson]` and is offered only when that Tab is among the operator's own grants. The method options are the types with a `FiadoPaymentKind` `[DTO: ResponseTransactionTypeJson]`. **The payment method has no default, for every role:** nothing is preselected and the last method used is not remembered; confirming without a choice is refused with **Escolha a forma de pagamento.** The method is a statement about the drawer, so a silent default would make a physical claim for the operator. The receiving Tab keeps its default.
  - **Drawer effect** — shown once a method is chosen: **dinheiro** (physical cash into the counted drawer) also writes an automatically generated Terminal **cash entrada** on the Tab's paired terminal; every other method (PIX, for example) reduces the client's debt with no drawer movement and no change to the counted Dinheiro. The same Tab can receive both kinds; bank-side entries and settlement timing for non-cash methods are separate contracts. The effect follows the method's `FiadoPaymentKind` (`CountedCash` / `NonCash`) `[DTO]`; a cash payment needs the paired terminal's open Draft close and, for a Member, that terminal in scope.
  - **Balance after payment** — the confirmation uses the Client statement balance display (an overpayment reads **+R$ … · crédito do cliente**). The authoritative post-payment balance is re-read from the Client statement `[DTO]`; the display mapping is `[derived]`.
- **Actions** — **Confirmar pagamento** → `POST /transaction/fiado-payment` `[DTO: RequestReceiveFiadoPaymentJson → ResponseCreateTransactionJson]`: records an `In` for the client on the chosen Tab (`AccountId`) with a fresh `Idempotency-Key` (signed 1.7) — together with the linked Terminal cash entrada for a cash payment, both or neither; an uncertain result retries the identical request with the same key, and a replay never creates another pair. Netting is branch-wide, so whichever Tab records it, the client's oldest debt is reduced first; a partial payment leaves the remainder aged. This is the only way to record a fiado repayment: Transaction — Create does not offer the repayment types.
- **Audit / lock context** — blocked when the date is at or before `LockDate`. A non-cash repayment is a Tab write and needs no DailyClose (M7.7 Phase 3 boundary); a **cash** repayment's linked Terminal row needs the paired terminal's open Draft close for the date — a Submitted/Approved/Rejected close blocks the payment. A Member needs the explicit Tab grant **and** access to the affected terminal. **Day not open yet:** the same offer and return as Transaction — Create — name the paired terminal, offer **Abrir o dia** when the caller may open it, return to this form with everything typed, and record the payment only when the operator confirms it here.
- **States** — *loading* · *validating* (no method chosen) · *terminal day not open* (cash only — offer to open, when permitted) · *success* (new balance shown) · *error* (row not assumed saved).
- **Navigation** — from Client statement, Clients, Transaction — Create, or Fiado balance; returns to Client statement when opened there, otherwise to its source. **Abrir o dia** → Open day → back here with the input intact.

## Daily ledger

- **Purpose** — the per-account statement: every movement in a window, wrapped in opening → closing balances.
- **Primary job** — reconcile one account's activity for a day (or short period) line by line.
- **Access** — manager-admin; whole-branch.
- **Default view / filter** — today, one account (`AccountId` is **required** by the endpoint); the UI preselects the last account viewed (`[derived]` client memory). Reconciliation happens account by account, so the forced choice fits the job.
- **Data shown**
  - **Header** — `AccountName`, window, `OpeningBalance`, `ClosingBalance`, `TotalIn`, `TotalOut`, `NetTotal`. `[DTO: ResponseDailyLedgerJson]`. A deactivated account still opens (server M11 Phase 2.4): `AccountActive = false` `[DTO]` shows an **Inativa** badge beside the name; only a missing or other-branch id is 404.
  - **Rows** — `Date`, `Value`, `Direction`, `Description?`, `TransactionTypeName`, `CategoryName`, `ClientName?`, `RecordedByOperatorName`, `DueDate`, `PaidAt?`. `[DTO: ResponseDailyLedgerItemJson]` (row `Id` carried for the deep-link).
  - **Paging** — `[DTO]`.
- **Actions** — change account/window (≤ 366 days; violations → 400 verbatim) → `GET /report/daily-ledger`; open a row → Transaction — Edit.
- **States** — *loading* · *empty* (no movement in the window) · *error* · *success*.
- **Navigation** — reports nav; from Manager Work Queue.

## Fiado balance

- **Purpose** — who owes what: outstanding fiado per client across the branch, as of a date.
- **Primary job** — scan the debtors and pick who to chase.
- **Access** — manager-admin; whole-branch.
- **Default view / filter** — `AsOfDate` = branch-local today (the server default when omitted), all clients.
- **Data shown**
  - **Total** — `TotalOutstanding`, `AsOfDate`. `[DTO: ResponseFiadoBalanceJson]`.
  - **Per-client rows** — `ClientName`, `OutstandingTotal`. `[DTO: ResponseFiadoClientBalanceItemJson]`.
  - **Debt and credit, separated** — two tabs: **Dívidas em aberto** (clients with a positive balance) and **Saldo crédito** (clients with a negative internal balance, shown as positive credit per the Client statement mapping); a client at zero appears in neither. Each tab has its own total under the same client/date filters — **Total em aberto** (`TotalDebt`, with `DebtorCount`) and **Crédito dos clientes** (`TotalCredit`, a positive amount, with `CreditorCount`) — `[DTO: ResponseFiadoBalanceJson]` (server M11 Phase 3.1). The net `TotalOutstanding` is never presented as the amount to collect: one client's credit does not settle another's debt. FIFO, aging, grants, and branch scope are unchanged; credit stays out of aging.
- **Actions** — filter one client / change the as-of date → `GET /report/fiado/balance`; switch between the debt and credit tabs; drill a client → Client statement (the tab and filters are kept for the return), or Fiado aging with the client filter carried; quick action **Receber pagamento**.
- **States** — *loading* · *empty* (nothing outstanding — all-clear) · *error* · *success*.
- **Navigation** — reports nav; drills into Client statement and Fiado aging.

## Fiado aging

- **Purpose** — every unpaid fiado row, aged into buckets — how overdue the branch's credit is.
- **Primary job** — spot what slid into a worse bucket and act on it.
- **Access** — manager-admin; whole-branch.
- **Default view / filter** — `AsOfDate` today, all clients and accounts; server order `DueDate ASC, Date ASC, Id ASC` — oldest exposure first, which is already the action order.
- **Data shown**
  - **Rows** — `Date`, `DueDate`, `Value`, `DaysOutstanding`, `Bucket` (label per copy-guidelines §5; future-due rows appear as `Current` by design), `ClientName?`, `AccountName`, `Description?`. `[DTO: ResponseFiadoAgingItemJson]` (`TransactionId` carried for the deep-link).
  - **Bucket subtotals and totals** — whole-set, not page-local: `OutstandingTotal`, `ByBucket { Bucket, Value, RowCount }` (every bucket, zeros included) and `OldestUnpaidDate?` (the oldest unpaid **sale** date, labelled **Venda mais antiga em aberto**). `[DTO: ResponseFiadoAgingJson]` (server M11 Phase 3.2) — computed from the same FIFO netting and filters as the rows.
  - **Envelope** — paging, `AsOfDate`. `[DTO: ResponseFiadoAgingJson]`.
- **Actions** — filter client/account/as-of → `GET /report/fiado/aging`; drill a client → Client statement; open a row → Transaction — Edit (read context — `PaidAt` is disabled on fiado rows). Aging is computed server-side by **FIFO query-time netting** (server M7.7 Phase 5.1): a client's cumulative `In` payments, on any Tab, cancel the oldest-due `Out` rows and only the unpaid remainder is aged — each row's `Value` is that remainder `[DTO: ResponseFiadoAgingItemJson]`; an account filter narrows the netted result; per-row `PaidAt` plays no part. Fiado debt is never settled by editing past rows; settlement is **Receber pagamento**.
- **States** — *loading* · *empty* (no open fiado) · *error* · *success*.
- **Navigation** — from Fiado balance (client drill); reports nav.

## Open-cheque aging

- **Purpose** — cheques still unpaid (not yet cleared): pre-dated plans grouped by plan, and standalone cheques as their own groups (server M11 Phase 4.2), aged by their oldest open due date.
- **Primary job** — see which cheque plans are due or overdue and follow up.
- **Access** — manager-admin; whole-branch.
- **Default view / filter** — `AsOfDate` today; server order `OldestOpenDueDate ASC` — most urgent plans first.
- **Data shown**
  - **Groups** — `OutstandingTotal`, `OldestOpenDueDate`, `OldestOpenBucket`, `OpenRowCount`/`TotalRowCount` (an open-of-total count, `[derived]` phrasing), `ClientName?`, `AccountName`, `Description?`. `[DTO: ResponseOpenChequeAgingGroupJson]`. `OriginTransactionId` identifies a plan; when it is null the group is a **standalone cheque** — a single row of a type classified `Cheque` — labelled *Cheque avulso* and opened by its row's `TransactionId`, never shown as a plan. Which standalone rows count depends on the type classification, not on the type's name or settlement rule (working answer to loto-specs §9 question 3, pending confirmation).
  - **Expanded rows** — per unpaid installment: `DueDate`, `Value`, `DaysOutstanding`, `Bucket`. `[DTO: ResponseOpenChequeAgingRowJson]` (`TransactionId` for the deep-link).
  - **Totals** — whole-filter, every page: `OutstandingTotal`, `OpenRowCount` and `ByBucket { Bucket, Value, RowCount }` over every matching open plan row and standalone cheque (server M11 Phases 2.1 and 4.2); `TotalCount` is the open-group count (plans plus standalone cheques). `[DTO: ResponseOpenChequeAgingJson]`.
  - **Envelope** — paging, `AsOfDate`. `[DTO: ResponseOpenChequeAgingJson]`.
- **Actions** — filter account/client/as-of → `GET /report/cheques/open-aging`; expand a group; open an installment or a standalone cheque → Transaction — Edit (set `PaidAt` as cheques clear); open a plan → Installment plan (existing-plan mode).
- **States** — *loading* · *empty* (no open cheques) · *error* · *success*.
- **Navigation** — reports nav; rows deep-link to Transaction — Edit.

## Cash-variance summary

- **Purpose** — variance per `(date, account)` over a period, with aggregates — the trend view that complements the Work Queue's single-day exceptions.
- **Primary job** — spot repeat offenders and patterns (an account short every Friday).
- **Access** — manager-admin; whole-branch.
- **Default view / filter** — current month-to-date, all accounts. Variance review follows the monthly lock rhythm, so the month is the natural window.
- **Data shown**
  - **Rows** — `DailyCloseId`, `Date`, `AccountName`, authoritative persisted `VarianceValue` (signed, formatting §3), `DailyCloseStatus` (a pending number reads differently from a signed-off one). Recalled/reopened/correction Draft snapshots are excluded even though their physical variance row is retained. `[DTO: ResponseCashVarianceSummaryItemJson]`; the id is resolved by exact `(Date, AccountId)`, never date alone.
  - **Aggregates** — `TotalVariance`, `MeanVariance`, `MaxVariance`, `MinVariance`, and the official rows by status — `SubmittedCount`, `ApprovedCount`, `RejectedCount` (they add up to `TotalCount`; server M11 Phase 2.2). `[DTO: ResponseCashVarianceSummaryJson]`.
  - **Paging** — `[DTO]`.
- **Actions** — filter account/window (≤ 366 days) → `GET /report/cash-variance`; open a row directly by its `DailyCloseId` and route by status. No extra close-list lookup is needed.
- **States** — *loading* · *empty* (no cash-variance rows match the window — a Draft close has no variance row yet, so empty does not mean no closes exist) · *error* · *success*.
- **Navigation** — reports nav; from Work Queue (day aggregates → trend); rows route by close status like the Work Queue (only `Submitted` is approvable; finalized closes open read-only).

## Monthly reconciliation + lock

- **Purpose** — the month's gatekeeper: day-by-day closes, variance, and transaction counts, plus the blockers standing between the manager and advancing `LockDate`.
- **Primary job** — verify the month is clean, clear what isn't, lock it.
- **Access** — manager-admin; whole-branch.
- **Default view / filter** — the earliest unlocked month, initially `[derived]` from `Setting.LockDate` (`[composed]`: `GET /setting`) and, for a fresh `DateTime.MinValue` branch, `Branch.CreatedAt`. If the lock command discovers earlier active operational history, its `SETTING_LOCK_MONTH_INTERMEDIATE_UNRESOLVED` message names the first blocking `MM/yyyy`; show that month prominently beside the existing month navigation so the manager does not have to hunt for it. The view remains freely navigable via the `{year}/{month}` route.
- **Data shown**
  - **Lock readiness** — `LockReady` is true only when every close is Approved, zero Draft transactions remain, and every direct active Terminal `(account, date)` activity pair has a close. A completely empty month is ready; direct Terminal activity without any close is not. Weekends, holidays, and activation windows add no independent expectation, and paired-Tab fiado alone does not make its Terminal expected. `[DTO: ResponseMonthlyReconciliationJson]`.
  - **Blockers** — structured: `Type` (`UnapprovedClose` / `DraftTransactions` / `MissingExpectedClose`), `Day`, `DailyCloseId?`, `AccountId?`, `AccountName?`, `CloseStatus?`, `DraftTransactionCount?`. `[DTO: ResponseMonthlyReconciliationBlockerJson]` — the client composes the pt-BR sentence (copy-guidelines §5) and deep-links via the returned identifiers.
  - **Calendar days** — per day: closes (`AccountName`, `Status`, authoritative persisted `VarianceValue`, `DailyCloseId`), `ActiveTransactionCount`, `DraftTransactionCount`, `CancelledTransactionCount`, `NetVariance`. Draft retained snapshots are excluded from `VarianceValue`/`NetVariance`. `[DTO: ResponseMonthlyReconciliationDayJson / ...DayCloseJson]`.
  - **Lock context** — `LockDate?` (null = never locked), `IsMonthLocked` (month end on or before `LockDate`) and `IsMonthElapsed` (month end before branch-local today). `[DTO: ResponseMonthlyReconciliationJson]` (server M11 Phase 2.3) — no separate `GET /setting` call; `LockReady` and the blockers are unchanged.
- **Actions** — open a blocker: `UnapprovedClose` routes by its `CloseStatus` (only `Submitted` is approvable — `Submitted` → Daily-close approval · `Draft` → Close day · `Rejected` → Fix & resubmit); `DraftTransactions` → Transactions list (Draft filter, that day); `MissingExpectedClose` → Open day for the returned Terminal/day; change month → `GET /report/monthly-reconciliation/{year}/{month}` (out-of-range → 400 verbatim); **Bloquear mês** → `POST /setting/lock-month {Year, Month}` with the current Setting `ETag` in `If-Match`, behind a confirmation that states the consequence. The button follows this report's `LockReady`, which is **advisory**: the server's atomic recheck over the whole unlocked interval is the authority. When the lock is refused because an earlier month is unresolved, the returned `MM/yyyy` is shown prominently and navigable. The current/unfinished month is never lockable. Floor derivation, legacy-boundary repair, and coordination: loto-specs §6.6/§6.14.
- **Audit / lock context** — this screen *is* the lock control; once locked, the month's rows read as immutable everywhere else.
- **States** — *loading* · *clean month* (`LockReady`, zero blockers — all-clear, lock enabled) · *blockers present* · *error* · *success (locked)*.
- **Navigation** — from Work Queue (reconciliation-blockers group); reports nav. Unapproved-close blockers route by close status like the Work Queue (only `Submitted` is approvable; Draft → Close day, Rejected → Fix & resubmit, finalized closes open read-only); a Draft-transactions blocker → Transactions list (Draft filter, that day), then Transaction — Edit per row. Each returns here.

## Dashboard

- **Purpose** — a concise, read-only overview of the latest relevant fact from every manager report, each linking to its full report (owner decision 2026-10-16). It never takes the Work Queue's place and performs none of its actions.
- **Primary job** — see at a glance whether anything across the branch looks off today or this month, then open the report that explains it.
- **Access** — manager-admin; whole-branch; no operator link needed (an unlinked Manager reads it). `GET /report/management-overview` (server M11 Phase 7) — 400/401/403 fail the whole page before any section is shown.
- **Default view / filter** — the current month, partial through today. A month selector (both year and month, or neither) moves only the month sections; it never moves *today*: `AsOfDate` is always branch-local today and is not a parameter. A later month is refused verbatim (`REPORT_MONTH_IN_FUTURE`). The selector never jumps to "the last month with data".
- **Data shown** — `[DTO: ResponseManagementOverviewJson]`. The envelope carries `GeneratedAtUtc`, `AsOfDate`, `BranchLocalNow` (one clock read for every section), `Year`, `Month`, `MonthDateFrom`, `MonthDateTo`, `IsPartialMonth`. Each section carries its own window, `Status` (`OverviewSectionStatus`: *Atualizado* / *Nada no período* / *Não configurado*, copy-guidelines §5/§7.5, indicator `dom.overview-section-status.*`), whole-set totals, `PreviewLimit`/`TotalCount` where it lists, and the ids its full report needs. In catalog order:
  - **Pendências** — Work Queue counts for today (`Queue`: pending approvals, rejected, not submitted, backlog per status and oldest pending date, unlocked Draft transactions, pending operator-link requests). Counts only; the Work Queue owns the items.
  - **Fechamentos recentes** — `RecentCloses`: the last 7 days (`[AsOfDate − 6, AsOfDate]`), counts per status and up to 10 closes in the `GET /dailyclose` order with account, status, recorder and submitter (user and operator) and the **official** variance — null for a Draft close, whose retained value is never shown.
  - **Diferença de caixa do mês** — `CashVariance`: the month's official total, mean, max, min and per-status counts, plus the 5 largest absolute variances `[DTO: ResponseCashVarianceSummaryItemJson]`.
  - **Fechamento do mês** — `Reconciliation`: the selected calendar month's `LockDate`, `IsMonthLocked`, `IsMonthElapsed`, the advisory `LockReady` and blocker counts by type. A month that has not elapsed is never presented as lockable.
  - **Fiado** — `Fiado`, as of today: debtors and total debt, creditors and total credit (a positive magnitude, never subtracted from debt), FIFO unpaid aging by bucket, the oldest unpaid sale date and the 5 largest debtors.
  - **Cheques em aberto** — `OpenCheques`: open groups (plans and standalone cheques), open rows, outstanding total by bucket, oldest open due date and the 5 oldest groups.
  - **A receber** — `UpcomingSettlements`: due in the next 14 days (`[AsOfDate, AsOfDate + 13]`), count and value per instrument, up to 10 items, and **overdue** as its own line, never added to the period. A cheque that is also an open cheque appears in both sections; the two are never summed.
  - **Movimento das contas hoje** — `AccountActivity`: every active Terminal plus any account, active or deactivated, with Active or Draft rows today (cap 50, by name): entradas, saídas and net of that account only, Active and Draft counts (Draft never summed), last activity date and an `IsActive` flag. There is no cross-account total.
  - **Registros por operador hoje** — `OperatorActivity`: active operators plus any operator, active or deactivated, with rows today (cap 50, most rows first): count, recorded entradas/saídas (recorded volume, not revenue) and the automatic share as a subset — Active rows only, a Draft neither counts nor lists an operator. Not close ownership.
  - **Horas do mês** — `Hours`: operators listed, *em turno agora* (an open segment today) and *saídas não registradas* (an earlier day still open, 0 h until corrected), positive and negative balances summed apart, and the 5 most behind. In-progress hours are provisional.
  - **Financeiro do mês** — `MonthlyFinancial`: official variance, Tarifa de bolão and Sobras (each null — *não configurado* — when its marker is unset) and hours, side by side, never added together. The section's `Status` is *Não configurado* only when neither marker is set; even then its official variance and hours are real figures and stay visible beside the missing-configuration notice.
- **Actions** — refresh (re-read; nothing updates live); change month → `GET /report/management-overview?Year&Month`; open any section's full report with that section's window and ids: Work Queue (`?date=AsOfDate`), status-routed closes, Cash-variance summary (month window), Monthly reconciliation + lock (`{year}/{month}`), Fiado balance/aging, Open-cheque aging, Upcoming settlements (`DueDateFrom`/`DueDateTo` of the section, or an instrument), Daily ledger (`AccountId`, today), My transaction summary in manager context (`OperatorId`, today), My time-entry balance in manager context (month window, or one operator), Monthly financial report. A *Não configurado* section links to Categories & Transaction Types. No section performs an approval, lock, payment or edit.
- **States** — *loading* (the page appears whole; there is no per-section partial result) · *error* (any failure fails the whole read — render `ErrorMessages` verbatim, offer retry; never show the sections that happened to load) · *success* with each section in its own `Status`: *Nada no período* is a sentence with the window, *Não configurado* names what is missing and where it is configured, and neither is ever shown as zero · an empty branch shows every section empty or not configured, none as zeros.
- **Navigation** — Gestão navigation (Reports); the Work Queue stays the management home and links here as a secondary destination. Every drill-down returns to the Dashboard with its selected month kept; without an origin the fallback is Manager Work Queue.

## Upcoming settlements

- **Purpose** — money the shop expects to receive from card acquirers and cheques, by due date, from rows whose transaction type is classified with a settlement instrument.
- **Primary job** — see what lands in the coming days, what is already overdue, and follow up on what has not arrived.
- **Access** — manager-admin; whole-branch. `GET /report/upcoming-settlements` (server M11 Phase 5).
- **Default view / filter** — due today through today + 13 (the Dashboard's window), all accounts and instruments. The window is required, inclusive and at most 366 days; an account may be any of the branch's accounts, deactivated ones included; the instrument filter offers Cheque, Cartão de crédito and Cartão de débito only.
- **Data shown**
  - **Rows** — `DueDate`, `Date` (the day it was recorded), `Value`, `Instrument` (label §5; badge `dom.settlement-instrument.*`), `TransactionTypeName`, `AccountName`, `ClientName?`, and the plan link when `OriginTransactionId` is present (an installment keeps its plan; each installment row appears once). Ordered `DueDate, Date, Id`. `[DTO: ResponseUpcomingSettlementItemJson]`.
  - **Totals** — whole-filter, every page: `TotalCount`, `TotalValue` and `ByInstrument` (all three instruments, zeros included). **Overdue** — `OverdueCount`, `OverdueValue`: rows due before today under the same account/instrument filters, whatever the window; shown as its own line and never added to the window total (a window that starts before today also lists overdue rows). `[DTO: ResponseUpcomingSettlementsJson]`.
  - **Configuration** — `IsConfigured`: false only when no transaction type of the branch, active or retired, carries an instrument. `[DTO]`.
  - **Provisional meaning** — cards count as receivables until the payout lands, and a cheque is paid when it clears (working answers to loto-specs §9 questions 2–3, pending the shop's confirmation); shown as a short note, not hidden.
- **Actions** — change window/account/instrument → the same endpoint; open a row → Transaction — Edit (where `PaidAt` is set when the money lands), or the installment plan for a plan row. The report never marks anything paid, never infers a bank reconciliation and never moves money.
- **States** — *loading* · *not configured* (`IsConfigured = false`: "nenhum tipo classificado", with a link to Categories & Transaction Types — never "nada a receber") · *empty* (configured, nothing due in the window and nothing overdue) · *error* (validation messages verbatim) · *success*.
- **Navigation** — Reports nav; from the Dashboard's *A receber* section with its window; rows → Transaction — Edit / Installment plan, returning here.

## Monthly financial report

- **Purpose** — the month's financial picture of §7.2 step 4: official cash variance and the day's bolão fee per Terminal/day, commercial leftovers, and hours per operator/day — side by side, never added together.
- **Primary job** — review the month figure by figure, per Terminal and per operator, before the manual CEF borderô comparison.
- **Access** — manager-admin; whole-branch. `GET /report/monthly-financial/{year}/{month}` (server M11 Phase 6). Distinct from Monthly reconciliation + lock, which is the readiness/lock surface.
- **Default view / filter** — the current month, partial through today (`IsPartialMonth`, `DateTo` = today); any earlier month opens whole. A month that has not started is refused verbatim (`REPORT_MONTH_IN_FUTURE`).
- **Data shown** — `[DTO: ResponseMonthlyFinancialReportJson]`.
  - **Month totals** — `OfficialVarianceTotal` with `OfficialCloseCount`; `BolaoServiceFeeTotal`; `CommercialLeftoverTotal` with `LeftoversByType` (Sobra de Bolão and Sobra de Federal stay distinct, a retired type flagged); `HoursTotal` with `ContainsInProgress`. Separate figures, no grand total. A figure whose marker is unset (`IsBolaoServiceFeeConfigured` / `IsCommercialLeftoverConfigured` false) is null and reads *não configurado*, never zero.
  - **Por terminal e dia** — `TerminalDays`: date, terminal (`AccountActive` flag), the close (`DailyCloseId`, `CloseStatus`) and its **official** variance (null without a close or while Draft), the day's `BolaoServiceFee`, and the close's recorder and submitter (user and operator). One row per Terminal/day, even when several operators shared it — never split between them; a fee day without a close appears without one. `[DTO: ResponseMonthlyFinancialTerminalDayJson]`.
  - **Sobras** — `Leftovers` per date, terminal, recording operator and type, with value (a loss shown positive) and row count. `[DTO: ResponseMonthlyFinancialLeftoverJson]`.
  - **Horas por operador e dia** — `Hours`: date, operator (`OperatorActive` flag), `Status` (label §5), `TotalHours`, `BalanceHours`, `IsInProgress` — today's open segment is live and provisional, an earlier day still open counts 0 h until corrected. `[DTO: ResponseMonthlyFinancialHoursDayJson]`.
  - **Provisional meaning** — the fee is the day's fee summed for the month, leftovers are commercial losses, and close figures stay per Terminal/day (working answers to loto-specs §9 questions 4–6, pending confirmation); stated beside the figures.
- **Actions** — change month → the same endpoint; open a Terminal/day's close (status-routed like the Work Queue: only `Submitted` is approvable); open a terminal's day → Daily ledger; open an operator's month → My time-entry balance in manager context; a *não configurado* figure links to Categories & Transaction Types. The CEF borderô comparison stays manual, outside the system.
- **States** — *loading* · *empty* (no close, fee, leftover or hour in the month) · *not configured* figures inside an otherwise ready report · *error* (verbatim) · *success*. A partial month is labelled as such.
- **Navigation** — Reports nav; from the Dashboard's *Financeiro do mês* with the same month; drill-downs return here.

## My transaction summary

- **Purpose** — the operator's own production: totals and a per-category breakdown for a window.
- **Primary job** — answer "how much did I move this month?" without asking a manager.
- **Access** — any branch role (`[TokenAuthenticateBranch]`), single-operator resolution: Member → own linked operator; Manager/Admin must name `operatorId` or `mine` (neither → 400 `REPORT_OPERATOR_ID_REQUIRED` — this endpoint has **no** branch-wide roll-up).
- **Permission fallback** — Member with no linked operator, **or linked with zero active account links**, → **empty summary short-circuit** (not an error); Member naming another `operatorId` → 403 `REPORT_MEMBER_NOT_OWN_OPERATOR`.
- **Default view / filter** — current month; the totals feed the same monthly rhythm as payroll and the lock.
- **Data shown**
  - **Header** — `OperatorName`, window, `TotalTransactionCount`, `TotalInValue`, `TotalOutValue`, `NetValue`. `[DTO: ResponseOperatorTransactionSummaryJson]`. When a manager drills into a deactivated operator by id (server M11 Phase 2.4), `OperatorActive = false` `[DTO]` shows an **Inativo** badge; a Member's own view and `Mine` are unchanged.
  - **By category** — `CategoryName`, `Count`, `TotalIn`, `TotalOut`. `[DTO: ResponseOperatorCategoryTotalJson]`.
  - **Automatic share** — the summary counts rows, and it **includes** the automatically generated Terminal movements, which keep the initiating operator for audit. Because this screen shows totals, not rows, it says how much of each figure is automatic — e.g. *"7 transações, 2 delas automáticas"*, with the automatic entradas and saídas beside the totals, overall and per category — so the terminal side of a fiado repayment is not read as a second receipt. The rows themselves, each with its **Automática** label, are inspected in Transactions list with `Mine`. `[DTO: ResponseOperatorTransactionSummaryJson]` — `GeneratedTransactionCount`, `GeneratedInValue`, `GeneratedOutValue`, and per category `GeneratedCount`/`GeneratedIn`/`GeneratedOut`, each a subset of the matching total (server M7.7 Phase 5.8).
- **Actions** — change window (≤ 366 days) → `GET /report/operator-summary`. Managers reuse this same screen pointed at one operator (`operatorId`), entered from Operators or Dashboard operator activity with its explicit OperatorId and date window.
- **States** — *loading* · *empty* (no transactions in the window, or unlinked Member) · *error* · *success*.
- **Navigation** — Meu turno from Operator Day Cockpit for own context; Gestão entry from Operators or Dashboard operator activity for a manager-selected operator. Return to that validated opener with its period, mode, Dashboard month/section/row and focus; without origin → Operators.

## My time-entry balance

- **Purpose** — hours worked against the daily target: totals, banco-de-horas balance, and the day-by-day trail.
- **Primary job** — answer "am I ahead or behind?" at a glance.
- **Access** — any branch role (`[TokenAuthenticateBranch]`): Member → own operator; Manager/Admin → `operatorId` (one), `mine` (own), or **neither → branch-wide roll-up** — the payroll view: one element per **active operator**, zero-entry operators included with empty `Days` and zeroed totals whether or not they carry a login link (M7.7 Phase 7), plus any operator with entries in the window even after deactivation. Labelling an operator's missing days *Sem registro* is a client-side derivation (requested window minus returned `Days`) — the server publishes no operating-day matrix.
- **Permission fallback** — unlinked Member → **empty `Operators` list** (short-circuit); Member naming another `operatorId` → 403 `REPORT_MEMBER_NOT_OWN_OPERATOR`.
- **Default view / filter** — current month (banco de horas settles monthly).
- **Data shown**
  - **Window** — `DateFrom`/`DateTo` on the wrapper (one range for all operators). `[DTO: ResponseTimeEntryBalanceSummaryJson]`.
  - **Per operator** — `OperatorName`, `OperatorActive` (an **Inativo** badge for a deactivated operator, server M11 Phase 2.4), `TotalHours`, `TotalBalanceHours`, `PresentDays`, `AbsentDays`, `OwingDays`, `AbonadoDays`, `ContainsInProgress`. `[DTO: ResponseTimeEntryBalanceOperatorJson]` — decimal hours render as durations (formatting §5).
  - **Per day** — `Date`, `Status` (label per copy-guidelines §5), `TotalHours`, `BalanceHours`, `IsInProgress` (live-recomputed rows flagged), plus the day's target `[derived]` as `TotalHours − BalanceHours` (the contract carries no target field and no endpoint exposes the policy ledger; the identity holds for every status). `[DTO: ResponseTimeEntryBalanceSummaryDayJson]`. Balances are computed under the effective-dated `TimeEntryPolicy` applicable to each day (§3.20/§6.7), so a settings change never rewrites the days before it — a window spanning a change legitimately shows different targets per day. The target is a per-day value: it appears only on a single operator's day-by-day table, never on the branch roll-up, whose window can span a policy change.
  - **Anything-open flag** — `Operators.Any(ContainsInProgress)`. `[derived]` — the contract deliberately has no branch-level field.
- **Actions** — change window (≤ 366 days — the standard report guardrails apply here too, 400 verbatim) → `GET /report/timeentry-balance` (`mine` and `operatorId` are mutually exclusive — 400 verbatim); drill a day → Clock in / out (own) or Time-entry management (manager).
- **States** — *loading* · *empty* (no entries / unlinked) · *in-progress* variant (live rows marked) · *error* · *success*.
- **Navigation** — Meu turno for own context; in Gestão, the Manager/Admin roll-up doubles as the payroll summary reached from Time-entry management. Dashboard hours opens this roll-up or an explicit operator, and Monthly financial report opens the hour row’s operator for its entire selected-month window. Return through any nested roll-up to the actual validated opener with month/filters/mode/section/row/focus retained; without origin → Time-entry management.

## Operator Day Cockpit

- **Purpose** — the operator's single "today" home: shows the day's state and the **next action**, so operators don't navigate modules. It is an operational action hub, **not** a financial KPI dashboard: no money totals or stat tiles — financial analysis belongs to My transaction summary.
- **Primary job** — know and do the next step of the day (open → record → close → resubmit).
- **Access** — a Member in Meu turno, or a Manager/Admin linked to an active Operator after explicitly switching to Meu turno; own operator + linked accounts establish the cockpit context, while the branch role and server permissions remain unchanged.
- **Permission fallback** — Member without a linked operator → a **setup-needed** state (no operator linked) with **Solicitar vínculo**, which calls Member-only `POST /operator-link-request` and returns the same pending id on repetition `[DTO: ResponseOperatorLinkRequestJson]`; own status comes from `GET /operator-link-request/self` `[DTO: ResponseOwnOperatorLinkRequestJson.Request?]` — no request yet; **Solicitação enviada em {data/hora}** while `Pending`; after `Resolved`, a re-read of self-context decides: usable → the cockpit, otherwise the account setup-needed state saying the link was made and a terminal is still missing (`HasUsableAccount = false`), with **Solicitar vínculo** offered again because a new eligible request is allowed. A linked Member with no usable Terminal assignment sees the account setup-needed state with the same request action. A linked Manager/Admin without a Terminal gets setup guidance and uses Operators / Account assignment in Gestão under the existing management role; the Member-only request action is not offered to them `[derived from existing role matrix]`. A Manager/Admin without an active link is intercepted before cockpit entry and stays in Gestão with the setup explanation defined by the IA map. Read/list areas may empty-short-circuit per their own endpoints; **write** actions (open day, record, close) are disabled or surface their own permission/validation errors (e.g. create's 400 `TRANSACTION_MEMBER_REQUIRES_OPERATOR_LINK`). §6.10 governs transaction-list *reads* specifically — not the whole screen.
- **Default view / filter** — today (branch-local) on the **workstation terminal**, chosen from the Terminal accounts in `ResponseSelfContextJson.AvailableAccounts` (Tab and Bank never count): exactly one → bound automatically, no prompt; more than one → on first entry the cockpit asks *"Em qual terminal você vai operar hoje?"* before showing the next action, and its header shows the terminal with **Trocar**. The choice is kept per device, per branch, per branch-local day: a reload does not ask again; Switch branch and the next branch-local day clear it. A linked Manager/Admin in Meu turno follows the same rule. `PrimaryAccount` never guesses the workstation.
- **Data shown** *(next-action oriented)*
  - **Today's close state** — the workstation terminal's close for today, if any, and its status. `[composed]`: `GET /dailyclose?AccountId&DateFrom=DateTo=` today. When a Draft needs context, `GET /dailyclose/{id}` distinguishes plain work, a rejected-correction Draft (`RejectionReason`), and a predecessor-triggered opening recheck (`OpeningRecheckRequiredAt` + triggering-close/user ids); the lightweight list row does not carry those fields.
  - **Today's transactions + draft count** — the rows: `[composed]` `GET /transaction?AccountId={workstation}&DateFrom=DateTo=` today, paged — the `(account, date)` the close is judged on, never filtered by author. The Draft count is exact and separate: the same filter with `Status=Draft&PageSize=1`, reading `TotalCount` — exactly what blocks Submit, and what P3 evaluates. On a shared terminal it splits into *seus* (the same request with `Mine=true`, reading `TotalCount`) and *de outros operadores* (the difference).
  - **My open closes today** — every close today on my Terminal accounts that I recorded or that is still unclaimed: a set, not a single value. `[composed]`: `GET /dailyclose?DateFrom=DateTo=` today (a Member's read scope already limits it to linked accounts; a linked Manager/Admin keeps only their own Terminal assignments), keeping rows whose recorder is me or none. When it holds a terminal other than the workstation, an **outros terminais** strip beside the next action lists each with its status, so a terminal left unsubmitted is always visible.
  - **Clock status** — clocked in/out, live-running. `[composed]`: `GET /timeentry` (today, `Mine`).
  - **Next action** — `[derived]`; the first matching row wins:
    - **P1 Correction needed** — a close I recorded, on any unlocked date up to today, that is `Rejected` or an opening-recheck / rejected-correction Draft → *"Fechamento de {data} precisa de correção"* · the rejection reason, or *"O fechamento anterior foi corrigido; reconte este."* with **Ver o que mudou** (the before/after detail defined on Fix & resubmit, from `GET /dailyclose/{id}/history`) · **Corrigir fechamento** → Fix & resubmit. `[composed]`: `GET /dailyclose?Mine=true&DateFrom=LockDate+1&DateTo=today` (`Mine` matches the recording operator); a prior-day Draft is resolved with `GET /dailyclose/{id}` because list rows lack the correction fields.
    - **P2 Day not open** — no close today on the workstation terminal → *"Dia ainda não aberto"* · *"Abra o dia do {terminal} para registrar movimentações."* · **Abrir dia** → Open day.
    - **P3 Drafts block the close** — a Draft close today with Draft transactions on its `(account, today)`. The blocker count stays terminal-wide (never filtered by author — every draft blocks Submit), and its *seus / de outros operadores* split sits next to the primary message, worded by role and ownership (singular/plural per copy-guidelines §7: *"1 movimentação em rascunho"*, *"2 movimentações em rascunho"*):
      - *Own drafts only, or a Manager/Admin caller* (elevated callers can act across authors) → *"{n} movimentações em rascunho"* · *"Finalize ou cancele os rascunhos antes de fechar o caixa."* · **Finalizar movimentações** → Transactions list (Draft filter, that day), which returns here.
      - *A Member with only other operators' drafts* → **Pendência do terminal** · *"O fechamento está bloqueado por 1 rascunho de outro operador"*, explaining that the recording operator or management must finalize or cancel it · **Ver pendência** / **Ver pendências** → the same Draft-filtered list, which grants no mutation permission.
      - *A Member with both* → **Resolver meus rascunhos** (the same list with `Mine=true`) and a distinct **Ver pendências de outros operadores**; the full blocker count stays visible after the caller clears their own.
      This is presentation only: terminal accounting, ownership, and Submit eligibility are unchanged, and no notification or assignment endpoint is implied.
    - **P4 Day open** — a Draft close today → *"Dia aberto"* · *"Registre as movimentações e feche o caixa no fim do turno."* · **Fechar caixa** → Close day; secondary **Nova transação**.
    - **P5 Another terminal still open** — *My open closes today* holds another terminal with an open or uncounted close → *"{terminal} ainda está aberto"* · *"Você tem outro caixa aberto hoje. Feche-o antes de encerrar o turno."* · **Ir para {terminal}** → that terminal's Close day.
    - **P6 Submitted** today → *"Aguardando aprovação do gerente"* · *"Enviado às {hora}."* · **Desfazer envio** only for the same-day recorder.
    - **P7 Approved** today → *"Dia encerrado e aprovado"* · *"Nada pendente hoje."* · no action; the approved close opens read-only.
  - **Today's close shortcut** — whenever today's close exists on the workstation terminal, **Ver fechamento de hoje** stays beside its status, whichever next action won: the priority is a recommendation, not a navigation lock (a P1 correction on another day does not hide today's count). It opens that exact terminal/date and returns here; ownership, read-only states, and Submit blockers are unchanged. `[composed]` from the workstation/date close read described above.
- **Actions** — **Open day** → Open day (`POST /dailyclose`); **Record** → Transaction — Create; **Close day** → close flow (`PUT /dailyclose/{id}/items` + `POST /dailyclose/{id}/submit`); **Fix & resubmit** → edit a rejected or opening-recheck close and resubmit; **Trocar** terminal (more than one Terminal); **Solicitar vínculo** → `POST /operator-link-request` (Member setup-needed only; repeat returns the same pending request, and 409 `OPERATOR_REQUEST_NOT_NEEDED` means the context already became usable — re-read self-context) `[DTO: ResponseOperatorLinkRequestJson]`; **Clock in/out** → `/timeentry` for Members only. Linked Manager/Admin callers keep the elevated time-entry contract and record their own hours in Gestão → Time-entry management instead of the Member tap.
- **Audit / lock context** — a rejected close shows its rejection reason (via `GET /dailyclose/{id}`); a submitted close shows submitted-at; `LockDate` rarely bites for today.
- **States** — *loading* · *terminal choice* (more than one Terminal, first entry of the day) · *setup-needed* (unlinked Member, or linked caller without a usable Terminal → guidance; **Solicitar vínculo** is Member-only) · *error* · *success* (state + next action P1–P7). A Manager/Admin in Gestão is never gated behind an operator link.
- **Data shown**
  - **Why this close needs review** — one group, **Por que este fechamento precisa de revisão?**, with the reviewed terminal/date and the current workflow status above it, listing separate, explicitly named events rather than two identical warnings. A rejection and an opening change are independent causes; a cascade-demoted Rejected close legitimately carries both. `[DTO: GET /dailyclose/{id}/history → ResponseDailyCloseHistoryJson.Events]`, oldest first, each with its own `Type`, `OccurredAt` and actor (`ActorUserName`, `ActorOperatorName?` — display names any reader of the close receives). When `IsHistoryComplete` is false the close predates captured events, so a missing event renders its unavailable fallback below.
    - **Rejeitado na conferência** — its own **Rejeitado em {data/hora}**, the actor, and the reviewer's reason labelled **Observação da gerência**. `[DTO: ResponseDailyCloseHistoryEventJson]` with `Type = Rejected` (`OccurredAt`, actor names, `RejectionReason`). O fechamento anterior mudou a abertura deste dia."* `[DTO: ResponseDailyCloseHistoryEventJson]` with `Type = OpeningChanged` (`OccurredAt`, actor names, `SourceDailyCloseId`/`SourceDate` — the source is on this close's own terminal — and `PreviousSourceDailyCloseId`/`PreviousSourceDate`). `OpeningRecheckRequiredAt` on Get/review remains the current recheck marker only, never reused for the rejection. Never suggest the recorded closing count was overwritten — only this day's opening changed.

No captured actor → none shown, never inferred.

With reliable timestamps the events are chronological and the order is stated; without one, no order is inferred. The event types stay separate from the current status.
    - **Next action** — one line ending the group: *"Revise a observação da gerência, confira a abertura alterada e reenvie a contagem."* After resubmission prior events may remain as history but are never presented as outstanding requests.
  - **The close form** — identical to Close day, **including gap AA's retained-retired-product edit/preview gate and the Day's transactions context**: review items, item form, and the close's `(account, date)` movement — a rejection is usually about a number the reviewer could not reconcile against that movement. - **States** — *rejected* (reason leading) · *opening changed* (recount explanation leading) · *rejected + opening changed* (both facts) · *editing* (back in Draft) · *resubmitted* (awaiting) · *error*.
- **Navigation** — from the Day Cockpit's rejected state or a status-routed management exception; back to the cockpit after an own-context resubmit, or to the originating Work Queue / Cash-variance summary / Monthly reconciliation / Dashboard / Monthly financial report view after elevated handling, preserving report month/section/row and nested approval origins.

- **Default view / filter** — current month, all operators, `InProgressFirst = true`, so forgotten punches are prioritized across the full result before paging. A focused queue sends `IsInProgress = true` and returns only open-segment entries.
- **Data shown**
  - **Entry rows** — `Date`, `OperatorName`, `Status` (label §5), `TotalHours`, `BalanceHours`, `IsInProgress`. `[DTO: ResponseListTimeEntryItemJson]`; filters `OperatorId`, `DateFrom`/`DateTo`, `Status`, `Mine`, `IsInProgress`, `InProgressFirst`, paging. `[DTO: RequestListTimeEntriesJson]`.
  - **Entry detail** — the full segment list with audit fields (`UpdatedAt`, `UpdatedByUserId`). `[DTO: ResponseTimeEntryJson / ResponseTimeEntrySegmentJson]`.
- **Actions** — set a day's status / edit its segments → `PUT /timeentry` (admin shape: full snapshot `Segments[{Id?, ClockIn, ClockOut?}]`, never `Action`). **The snapshot reconciles ids rather than replacing the segment set by omission:** every persisted active segment id must appear in the payload (a missing one → `TIMEENTRY_SEGMENT_NOT_FOUND`), an existing segment's `ClockIn` is immutable through this route (`TIMEENTRY_SEGMENT_CLOCK_IN_LOCKED` — use the granular segment `PUT`), new segments carry `Id = null`, and removals go through the granular `DELETE`. A successful snapshot commits its permitted changes together; this is not a replace-all contract. *(§6.7's "replaces the entire segment set atomically" wording is stale against this shipped behavior — flagged as a server spec-sync issue, not a catalog decision.)* Granular routes: add → `POST /timeentry/{timeEntryId}/segment`; edit → `PUT /timeentry/segment/{segmentId}`; remove → `DELETE /timeentry/segment/{segmentId}`; **Remover registro do dia** → `DELETE /timeentry/{timeEntryId}` — for an entry created by mistake (wrong operator, wrong date, duplicate), never to record an absence, which is a Status. The two are opposites: a Status keeps the day in the banco de horas (an abonado day scores the target with zero balance; an owing day scores −target), while removal takes the day out entirely and it falls back to *Sem registro*. Confirmation: *"O registro de {data} de {operador} será removido. O dia passa a contar como sem registro e sai do banco de horas. Essa ação não pode ser desfeita."*
- **Audit / lock context** — every admin edit stamps the audit pair on entry and segment; day-bounds and ≤ 24 h segment rules are server-enforced (verbatim on violation). A correction recomputes the entry's totals under the effective-dated `TimeEntryPolicy` for that entry's own date (§3.20/§6.7) — never today's constants — so fixing an old punch cannot silently apply a newer target or lunch tier. Every mutation route is blocked when the effective `Date ≤ LockDate` (`TIMEENTRY_DATE_LOCKED`): full-snapshot `PUT /timeentry`, whole-entry `DELETE`, and granular segment add/edit/remove. All share the month boundary through commit, so a write queued behind a successful lock is rejected instead of rewriting or removing payroll totals inside the locked month. A busy boundary returns retryable `SETTING_LOCK_MONTH_COORDINATION_BUSY`.
- **States** — *loading* · *empty* · *in-progress highlighted* · *error* · *success*.
- **Navigation** — Gestão admin navigation; pairs with the branch-wide roll-up of My time-entry balance for totals.

## Operators (admin)

- **Purpose** — manage the branch's employees: create, rename, link or unlink a login, deactivate, and resolve operator-link requests.
- **Primary job** — get a new employee working (row + login link + terminal) in under a minute, through Add employee.
- **Access** — manager-admin.
- **Data shown**
  - **Operators** — `Name`, `UserId?` (linked active branch login or none). `[DTO: ResponseListOperatorsJson / ResponseOperatorJson]`. A non-null id resolves through the active `GET /branch/users` membership list `[composed]`. The operator row linked to the signed-in person carries a small **você** badge beside the name — a marker only, adding or removing no action; the row is the one whose id equals `GET /operator/self-context`'s `OperatorId` `[composed]`. Removing a membership atomically clears every matching Operator link for that branch while preserving the employee row, history, and assignments, so no stale unresolvable identity remains.
  - **Operator-link requests** — pending requests, oldest first: `UserName`, `CreatedAt` (audit instant), `Status`. `[DTO: GET /operator-link-request?Status=Pending → ResponseListOperatorLinkRequestsJson]`, bounded pages of at most 100. A request from a removed, inactive or role-changed person disappears from the list without being destroyed.
- **Actions** — **Adicionar funcionário** → Add employee; **Desligar** (a row) → Offboard employee; create → `POST /operator {Name, UserId?}`; rename / change link → `PUT /operator/{id}` (`UserId = null` **clears the login link but keeps the employee row** — history survives); deactivate → `DELETE /operator/{id}`. Linking enforces at most one active linked operator per user per branch (`OPERATOR_USER_ALREADY_LINKED`, verbatim). **Resolve a pending request** → link the requester to an existing unlinked operator (`PUT /operator/{id}` with the request's `UserId`) or create one (`POST /operator {Name, UserId}`), then `POST /operator-link-request/{id}/resolve` → `[DTO: ResponseOperatorLinkRequestJson]` with the actual `OperatorId` and `HasUsableAccount`. Resolution needs a live link (`OPERATOR_REQUEST_SETUP_REQUIRED` otherwise) and grants no account: when `HasUsableAccount` is false the screen continues to Account assignment for that operator. A repeated resolution with a surviving link is idempotent; missing, foreign, removed or inactive targets are 404 `OPERATOR_REQUEST_NOT_FOUND`.
- **States** — *loading* · *empty* (no operators → **Adicionar funcionário**) · *no pending requests* · *error* (link conflicts verbatim) · *partially resolved* (linked but not yet resolved, or resolved without a usable terminal — each shown as the remaining step) · *success*.
- **Navigation** — Gestão admin navigation and the Work Queue's operator-link group; a row links to Account assignment, to My transaction summary in Gestão with that operator selected, and to Offboard employee.

## Categories & Transaction Types (admin)

- **Purpose** — the classification model behind every transaction: categories fix the direction, types drive settlement and the fiado requirement.
- **Primary job** — add a new type (a new payment method) without breaking the classification invariant.
- **Access** — mutations manager-admin; list/get any branch role (these lists feed every type picker).
- **Data shown**
  - **Categories** — `Name`, `DefaultDirection` (label §5). `[DTO: ResponseListCategoriesJson / ResponseCategoryJson]`.
  - **Types** — `Name`, `CategoryName`, `SettlementRule` (label §5), `RequiresTabAccountAndClient`, `FiadoPaymentKind?` (label §5 — marks a fiado repayment method; none is seeded), `SettlementInstrument` and `MonthlyFinancialRole` (labels §5, badges `dom.settlement-instrument.*` / `dom.monthly-financial-role.*` — the report classifications, server M11 Phases 4/6) and `SystemRole?` (the two system-generated movement types, shown read-only with the **Automática** explanation). `[DTO: ResponseListTransactionTypesJson / ResponseTransactionTypeJson]`. A new branch arrives with its card, cheque, Tarifa Bolão and Sobra types classified; an existing branch's types arrive *Sem classificação* and stay so until a manager classifies them — the reports then say *não configurado*.
- **Actions** — category: create → `POST /category {Name, DefaultDirection}` · rename → `PUT /category/{id}` (**direction is immutable** — the update DTO carries the name only; transactions denormalize direction at creation, §6.1) · deactivate → `DELETE /category/{id}`. Type: create → `POST /transaction-type {CategoryId, Name, SettlementRule, RequiresTabAccountAndClient, FiadoPaymentKind?, SettlementInstrument?, MonthlyFinancialRole?}` · edit → `PUT /transaction-type/{id}` (same fields minus category — **category is immutable**; an omitted classification is kept, so the edit form always sends the value it shows, and choosing *Sem classificação* / *Nenhuma* clears it) · deactivate → `DELETE /transaction-type/{id}` (a retired type keeps its classification, and the reports still count its rows). **Recebível** (`SettlementInstrument`) is independent of the settlement rule: the form never derives one from the other. **Relatório financeiro mensal** offers *Tarifa de bolão* only on an entrada type and *Sobra (perda comercial)* only on a saída type (`TRANSACTION_TYPE_MONTHLY_FINANCIAL_ROLE_DIRECTION_INVALID`), and explains that a change re-labels past months' report figures — locked ones included — without changing any transaction. **Forma de recebimento de fiado** (`CountedCash` / `NonCash`) is offered only on an entrada type that requires a conta fiado and a client; the server refuses any other combination (`TRANSACTION_TYPE_FIADO_PAYMENT_KIND_INVALID`), so the control explains the condition instead of hiding the reason. System types are read-only: edit and deactivate are not offered (`TRANSACTION_TYPE_SYSTEM_READ_ONLY` if reached).
- **States** — *loading* · *empty* (no categories or types yet — offer the permitted create action) · *error* (verbatim) · *success*.
- **Navigation** — Gestão admin navigation; the pickers in Transaction — Create and Installment plan read these lists.

## Settings (admin)

- **Purpose** — the branch's few global knobs: the lock date and the time-entry constants.
- **Primary job** — check the lock date; adjust hour targets when policy changes.
- **Access** — read: any branch role (`GET /setting` feeds lock checks everywhere); update: manager-admin.
- **Data shown** — `LockDate`, `DailyTargetHours`, `LunchDeductionOver6H`, `LunchDeductionOver4H` — decimal hours render as durations (formatting §5: `7.33` → `7h 20min`). `[DTO: ResponseSettingJson]`. The three time constants are the branch's **current** values — the mirror of the latest effective-dated `TimeEntryPolicy` row (§3.20); history lives in the policy ledger and is never edited here.
- **Actions** — update time-entry constants → `PUT /setting` (partial: only provided fields change; `[DTO: RequestUpdateSettingJson]`) with the loaded response `ETag` in `If-Match`. A real change takes effect from the branch-local **day of the change** (a second same-day change replaces that day's values): today's and future balances use the new constants, while every earlier day keeps the policy that governed it (M7.7 Phase 7) — stated plainly in the screen's copy. Inline helper under the time-constant inputs: *"Alterações entram em vigor a partir de hoje ({data_atual}). Os registros de dias anteriores mantêm as metas vigentes na época e não são recalculados."* On save, **only when a constant actually changed** (a value-identical save appends nothing and shows no confirmation), confirm first — target changed, with or without lunch tiers: *"Confirmar alteração de meta?"* / *"A nova meta de {nova_meta} será aplicada a partir de hoje, {data_atual}. Os dias anteriores deste mês permanecerão calculados sob a meta anterior ({meta_antiga})."*; only lunch tiers changed: *"Confirmar alteração das regras de jornada?"* / *"As novas regras de jornada valem a partir de hoje, {data_atual}. Os dias anteriores mantêm as regras vigentes na época."* Buttons: **Cancelar** · **Confirmar e salvar**. `LockDate` is read-only here: sending it returns 400 `SETTING_LOCK_DATE_READ_ONLY`. Its sole write path is Monthly reconciliation's `POST /setting/lock-month {Year, Month}`, also guarded by the Setting-root `If-Match`; normal state advances, while an impossible current/future legacy value is repaired there only after full validation.
- **States** — *loading* · *stale* (409 `SETTING_STALE_WRITE` → reload and let the user reconcile) · *error* (`SETTING_LOCK_DATE_READ_ONLY` or field validation, verbatim) · *success* (store the returned new `ETag`).
- **Navigation** — Gestão admin navigation; conceptually paired with Monthly reconciliation's lock action.

## Branch members (admin)

- **Purpose** — who can log into this branch, and as what role; who has been invited and whether the invitation is still usable.
- **Primary job** — invite a person by e-mail and role, whether or not they have an account, and keep the access list correct.
- **Access** — manager-admin, with a **role matrix**: an Admin manages every role; a Manager may only target and assign `Manager`/`Member` — never touch an Admin membership, see an Admin invitation or grant `Admin`. The UI gates accordingly (`[derived]`); the server enforces it. **Nobody acts on their own membership:** the caller's own row renders role change and removal disabled, with an explanation (`BRANCH_USER_SELF_MEMBERSHIP_CONFLICT`, distinct from last-active-Admin protection). The own row carries the same **você** badge as Operators, marked by comparing the contracted caller id `[DTO: ResponseUserLoginJson.UserId]` with the membership `UserId`.
- **Data shown**
  - **Members** — `Name`, `Email`, `Role` (label §5), `Active`. `[DTO: ResponseListBranchUsersJson / ResponseBranchUserJson]`.
  - **Invitations** — `Email`, `Role`, `OperatorId?` (resolved to an operator name through `GET /operator` `[composed]`), `Status` (label §5; `Expired` is projected by the server at read time), `ExpiresAt` (audit instant), `DeliveryStatus` (label per copy §5; SMTP acceptance, never inbox arrival). `[DTO: GET /invitation → ResponseListInvitationsJson / ResponseInvitationJson]`, filter by `Status` (default **Pendente**), newest first, pages of at most 100. The contract carries no issue date or inviter name; the screen shows none.
- **Actions** — **Convidar** → `POST /invitation {Email, Role, OperatorId?}` under the role matrix; `OperatorId` is offered only for a `Member` invitation and lists active unlinked operators. **Reenviar** → `POST /invitation/{id}/reissue` for a pending, expired, declined or failed-delivery invitation: omitted body keeps the operator choice, an explicit choice replaces or clears it (Member only); e-mail, branch and role never change, and every reissue invalidates the previous link. Change an existing member's role → `PUT /branch/users/{branchUserId}/role`; remove → Offboard employee, which calls `DELETE /branch/users/{branchUserId}`. **Adicionar funcionário** → Add employee. A pending invitation cannot be withdrawn by the branch (gap AC): the row says until when it stays valid.
- **Audit / lock context** — removal also clears that user's Operator login link(s) in the branch atomically; the **last-active-Admin invariant** is server-enforced (verbatim), and the UI also disables the offending action preemptively (`[derived]`). Issue/reissue refusals render verbatim: `INVITATION_PENDING_CONFLICT`, `INVITATION_MEMBERSHIP_EXISTS`, `INVITATION_TARGET_UNAVAILABLE`, `INVITATION_OPERATOR_UNAVAILABLE`, `INVITATION_OPERATOR_ROLE_INVALID`, `INVITATION_ALREADY_ACCEPTED`.
- **States** — *loading* · *no other members* · *no invitations for the filter* · *delivery failed* (row-level, with **Reenviar**) · *error* (last-admin, self-membership, role-matrix denial, invitation conflicts — verbatim) · *coordination busy* (409 `SECURITY_COORDINATION_BUSY`, retry) · *success* (**Convite enviado** only after a 201/200; a `Failed` delivery is reported as such, never as sent).
- **Navigation** — Gestão admin navigation; pairs with Operators (a member's login is what an operator row links to); a member row opens Offboard employee.

## Add employee (guided)

- **Purpose** — get a new employee working through one guided journey across the delivered operator, assignment and invitation commands — the Operators screen's "under a minute" promise without visiting three screens.
- **Primary job** — finish the setup an employee needs to record their first transaction, and see plainly anything still missing.
- **Access** — manager-admin; the invitation step follows Branch members' role matrix.
- **Composition rule** — there is no all-in-one employee command. Each step calls its own endpoint and commits on its own; earlier steps are never rolled back by a later failure. The journey state is always re-derived from server reads (`GET /operator`, `GET /operator/{id}/accounts`, `GET /branch/users`, `GET /invitation`), so leaving and re-entering for the same operator resumes truthfully; only unsent form input lives on the device.
- **Data shown** *(steps, in order)*
  1. **Funcionário** — `Name`; **Novo operador** or **Operador existente sem login** (from `GET /operator`, `UserId = null`, for a returning employee). `[DTO: RequestCreateOperatorJson / ResponseOperatorJson]`
  2. **Terminais e contas** — the branch accounts `[composed: GET /account]`; selecting one assigns it (`POST /operator/{operatorId}/accounts {AccountId}`) and one may be marked primary (`PUT …/{accountId}/primary`). A conta fiado is a separate, explicit grant: it is never implied by its paired Terminal and the step says so. `[DTO: ResponseOperatorAccountJson]`
  3. **Acesso ao sistema** *(optional — an operator may exist without a login)* — `Email` and `Role` (default `Member`). A `Member` invitation carries the operator from step 1 (`OperatorId`), so acceptance links it atomically. A `Manager`/`Admin` invitation cannot carry an operator; the step records **Vincular login depois** as remaining work, done in Operators after acceptance. If the e-mail already belongs to an active member (`INVITATION_MEMBERSHIP_EXISTS`), the step offers linking that member to the operator directly (`PUT /operator/{id} {Name, UserId}`) instead. `[DTO: RequestIssueInvitationJson → ResponseInvitationJson]`
  4. **Resumo** — every step's confirmed outcome: operator name, assigned accounts with the primary, invitation status and delivery, and what remains (**Sem terminal atribuído**, **Convite pendente até {data/hora}**, **Vincular login depois**, **Envio do convite falhou**). `[composed]`
- **Actions** — **Continuar** per step (each a real write); **Tentar novamente** on a failed step; **Concluir depois** at any point → back to the origin with completed steps kept; **Reenviar convite** from the summary. Step 1 → `POST /operator` or selection; step 2 → assignment calls, one per account, reported per account; step 3 → `POST /invitation`.
- **Uncertain outcomes** — operator create and assignments have no replay key: after a lost response, re-read (`GET /operator`, `GET /operator/{id}/accounts`) and let the manager confirm before writing again; never create a second operator automatically. An assignment that already exists returns `OPERATOR_ACCOUNT_ALREADY_ACTIVE`, which the step treats as confirmed. An invitation retry after a lost response may meet `INVITATION_PENDING_CONFLICT`, meaning the first one exists: re-read the invitation list.
- **States** — *step editing* · *step saving* · *step done* · *step failed* (verbatim) · *partially complete* (summary with remaining items) · *complete* · *coordination busy* (retry).
- **Navigation** — from Operators, Branch members or the owner setup checklist; completion or **Concluir depois** → the origin, re-read; without an origin → Operators.

## Offboard employee (guided)

- **Purpose** — end a person's access to the branch and tidy their operational setup while keeping every historical record.
- **Primary job** — remove access correctly in one pass and know what still exists afterwards.
- **Access** — manager-admin under the role matrix; never for the caller's own membership (disabled with the reason) or the last active Admin (disabled, server-enforced).
- **Composition rule** — as in Add employee: separate commands, no rollback, state re-derived from reads. Starting from a member row finds the linked operator through `GET /operator` (`UserId` match) `[composed]`; starting from an operator without a login skips the access step. Keep the selected membership and any resolved operator ids in the in-session journey before removing access, because that removal clears the link. A member with no operator still completes the access/invitation steps; account cleanup and operator deactivation are skipped. Always read pending invitations: `ResponseInvitationJson.OperatorId` matching the journey’s retained operator id is a verified link even without a membership. For a membership entry, also match its retained e-mail; take the union and deduplicate by invitation id. Never guess a link from the operator name.
- **Data shown** *(steps)*
  1. **Acesso** — the membership (`Name`, `Email`, `Role`) → **Remover acesso** → `DELETE /branch/users/{branchUserId}` `[DTO: ResponseRemoveBranchUserJson]`. The same commit clears this person's operator link(s) in the branch; the operator row, assignments and history remain. The person's identity session is not revoked, but every branch request they make afterwards is refused by the server's live membership check.
  2. **Convites pendentes** — pending invitations whose `OperatorId` matches the retained operator id, plus those matching the membership e-mail when present `[composed: GET /invitation?Status=Pending]`, deduplicated by id. They cannot be withdrawn by the branch (gap AC); show each `ExpiresAt` and no reissue action. An unexpired invitation remains a route to access even after membership removal; keeping the operator allows acceptance to create a membership and link it again. Deactivating its linked operator makes acceptance fail with `INVITATION_OPERATOR_UNAVAILABLE`. E-mail-only invitations without that link are not invalidated by operator deactivation.
  3. **Contas atribuídas** *(optional)* — the operator's assignments `[DTO: GET /operator/{id}/accounts]` → **Remover** each → `DELETE /operator/{operatorId}/accounts/{accountId}`.
  4. **Operador** *(optional)* — **Desativar operador** → `DELETE /operator/{id}`; history, closes and transactions keep the name.
  5. **Resumo** — what changed and what remains, each from a fresh read. List each still-usable pending invitation as **Acesso ainda possível por convite até {data/hora}** (`ExpiresAt`). For a pending invitation whose linked operator was confirmed deactivated, show **Convite impedido: operador desativado** (`INVITATION_OPERATOR_UNAVAILABLE`); never claim it was cancelled. A failed invitation read shows **Não foi possível verificar convites**, never an all-clear.
- **Actions** — each step's write after a confirmation that states its consequence (**A pessoa deixará de acessar esta lotérica. O histórico registrado continua disponível.**); **Concluir depois**.
- **States** — *step disabled* (self, last Admin, Manager targeting Admin — reason visible) · *step done* · *step failed* (verbatim) · *partially complete* · *complete*.
- **Navigation** — from an Operators row or a Branch members row; completion → the origin, re-read.
