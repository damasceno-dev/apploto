# Web Agent Notes

Milestones for this area live in `web/docs/milestones.md`.

## Stack direction

- Use Next.js App Router
- Prefer Server Components whenever possible
- Use Suspense and skeletons for loading states
- Use TanStack Query for client-side server state
- Package name is `@loto/web`; ESM only; the tsconfig extends the root `tsconfig.base.json`
- Consume `@loto/api` and `@loto/core` as source packages through Next `transpilePackages` — no build step in `shared/`

## Component guidance

- Use composition instead of prop-heavy components
- Prefer reusable components only
- Use Tailwind with merge and variant helpers rather than raw class interpolation
- Prefer named exports over default exports
- Build components to the design system's component contract (`design/specs/components/`) and screens to the screen catalog (`design/docs/screens.md`) plus their blueprints (`design/specs/screens/`)

## Design tokens

- Read `design/tokens/*.json` at build time through the web Tailwind preset — tokens never pass through `shared/`
- App code uses semantic and domain tokens only: no raw hex/rgb literals and no primitive-token references outside the token-adapter module (enforced by lint)
- Light and dark themes ship together
- Impeccable (design-refinement CLI) is a standing refinement tool at the build stage; feed it the token vocabulary so refinements stay inside the system

## API usage

- Server Components and route handlers call raw functions from `@loto/api`
- Client components use the hooks from `@loto/api/queries`
- Errors render `ResponseErrorJson.ErrorMessages` verbatim through the shared `ApiError` normalization

## Auth and the route-handler BFF

- The backend remains the real backend for web and mobile. The web layer never re-implements business rules, aggregations, or validation the API owns.
- A thin route-handler BFF **is expected** for browser auth: Next route handlers own login, branch session, token renewal, and logout, and keep the identity, branch, and refresh tokens in `httpOnly` cookies so no token is readable from browser JavaScript.
- Browser-side API calls reach the backend through that same cookie-to-bearer layer; it forwards request and response headers the contract depends on (`Idempotency-Key`, `If-Match`, `ETag`) unchanged and passes error bodies through untouched.
- Anything beyond auth, cookies, and header forwarding is not a BFF concern and needs a concrete web-only reason before it is added.

## Important decisions

- Mobile clones web: the screen set and its semantics are identical across platforms, so a web screen is built from the same catalog entry the mobile screen uses.
- pt-BR is the product language; follow `design/specs/copy-guidelines.md` and `design/specs/formatting-ptbr.md` (implemented by `@loto/core`).
- Business day and time come from `GET /branch/current`, never the device clock.

## M2 session and data plumbing (2026-10-21; per-tab branch context 2026-10-22; accepted locally, single instance)

Evidence and the criterion map are in `docs/milestones.md` (Web M2). Durable decisions:

- **Layout.** BFF routes: `src/app/bff/session` (GET state; `x-loto-branch` for a tab's branch, `?branches=1` for the picker's membership rule), `…/login`, `…/branch` (POST open a branch for this identity), `…/logout`, and the forwarder `src/app/bff/api/[...path]`. Their logic lives in `src/server/session` (cookies, `exp` reading, single-flight renewal, generations, service) and `src/server/bff` (allowlist, policy, forwarder) so it is tested without Next. `src/lib/bff-protocol.ts` and `src/lib/route-policy.ts` are isomorphic (no secrets). Browser code is under `src/client`.
- **Cookies.** Identity and refresh tokens, identity metadata (`sid`, identity scope, returned user), the navigation intent and one **branch slot per branch** (`__Host-loto-b-{branchId}`: token, branch summary, branch generation, bound to the `sid` that opened it; at most 4, oldest evicted) live in `__Host-loto-*` cookies: `HttpOnly; Secure; SameSite=Lax; Path=/`, no `Domain`, 7-day max-age (intent 30 min). A deletion must repeat `Secure; Path=/` with `Max-Age=0` (`applyCookieWrites`), or the browser keeps the cookie. No token appears in JSON, logs, storage, the query cache or a URL.
- **Secure local origin.** Use `http://localhost:<port>`: browsers treat localhost as a secure context, so `Secure` and `__Host-` cookies work without TLS. Any other host needs HTTPS. Never drop `Secure` to make a check pass.
- **Forwarder.** The allowlist is generated from Shared's committed operation map (`pnpm --filter @loto/web generate:bff`; `lint` fails on drift). Credential-bearing or session-ending operations are BFF-owned and never forwarded (`tooling/bff-operations.mjs`). Every BFF call needs `x-loto-bff: 1`; state changes also need a same-origin `Origin` (`LOTO_WEB_ORIGIN` behind a proxy). `x-loto-bff-error` marks a response produced **without** forwarding (nothing executed); `x-loto-session` reports a forwarded 401's recovery.
- **Renewal.** One path: proactive 30 s before `exp` (the API has zero clock skew), reactive on a forwarded 401 (one cycle). Only GET is re-sent; a write is never replayed. While a renewal outcome is unknown, writes are refused before dispatch even on a still-valid bearer; reads continue. Renewal and branch-session recreation are single flights keyed by token hashes in a process-wide registry on `globalThis` (shared by `proxy.ts` and route handlers); a rotation is handed to late holders of the old token for 15 s. **Boundary:** in-process only — more than one Next instance needs sticky sessions or a shared store (M12 hosting decision).
- **Per-tab branch context (D-M2-1, owner decision 2026-10-22).** Every branch-scoped page lives under `/f/{branchId}/…` (`src/lib/branch-route.ts`; a technical route convention, not an API); identity/account/global routes stay outside it. The route's id is **untrusted navigation context**: the proxy, the `/f/[branchId]` layout guard and the server client select only the signed-in identity's own slot for it, and a missing slot is opened through `POST /branch/session` (which verifies the membership; the API re-verifies membership and role on every call). A branch the identity cannot open is a **403** page (verbatim messages, link to `/filiais`) for pages and a not-forwarded `403 branch-unavailable` for BFF calls. Browser calls carry the tab's branch in `x-loto-branch` and its scope `x-loto-scope` = `{identity scope}.{branch generation}`; the forwarder requires both for branch work and refuses an old generation (409). Opening a branch never moves another tab; Sair or another login ends every tab's branches. Unscoped branch paths (`/gestao/…`) wait for a chosen branch and resume inside its namespace.
- **Generations.** Login and logout start or end the identity generation (`sid`) and identity scope; a branch slot carries its own generation, kept through renewal and re-opening while the role holds, new when the role changed or the branch was lost and regained. A late result for a generation another request ended writes no cookie (slot writes carry their generation to the fence). Cookies of an ended generation or a superseded rotation never authorize.
- **Session commands.** Login, branch opening and logout are serialized per browser (non-secret `__Host-loto-device` id) and compare-and-swap on the identity part of the scope the browser declares in `x-loto-scope`: a command issued against an older identity is superseded (409 `session-scope-changed`) and changes nothing. `GET /bff/session` and the proxy are serialized behind them. The identity `SessionProvider` ignores any read in flight when a command starts or settles; each tab's `BranchSessionProvider` (`/f/[branchId]` layout) re-reads only its own branch, and again whenever the identity changes under it.
- **Gate.** `src/proxy.ts` renews and resolves the gate for gated page requests before render (Server Components cannot set cookies, so they never renew); for `/f/{branchId}` it resolves that branch. Layouts repeat it with `requireBranchSession(branchId)`/`requireIdentity`. Destinations come from the shell blueprint route map; `gateRedirect` is the single typed-route assertion until M4 builds them. A gated deep link is held in the intent cookie, bound to the e-mail known at capture (a `/f/` path names its branch itself).
- **Data.** Server Components use `requestApiClient(branchId)` / `serverRead({ tier: 'branch', branchId }, …)` (one `createApiClient` per request, the route's branch only). The browser uses one scoped client (`/bff/api`, `null` token provider, the tab's branch header) and one `QueryClient` per scope: the identity scope at the root and, nested inside `/f/[branchId]`, the branch scope; the deepest mounted scope is the tab's default for generated hooks (`mountBrowserApiClient`, settled in layout effects before any query subscribes). Keep branch-scoped client state (mode, workstation, filters, selections, origin) under the branch subtree, so moving a tab to another branch resets it. Mutation retry is 0; reads retry once only for transient failures.
- **Writes and device input.** Every write is sent with the client of the scope it was prepared in (`useScopedApiClient()`, or the controller's own client), never the process default. `OperationController`/`useIdempotentOperation` freeze one `Idempotency-Key` per intent in device storage before dispatch, are disposed with their scope, recheck disposal/pause after every await, and quarantine unreadable or incomplete stored records (every recovery field is validated) until an explicit recovery; resends need the replay window proved from server `Date` headers (the forwarder relays the API's `Date`). Navigation intents with credential-like query parameters are dropped. `guardedWrite` round-trips `ETag`/`If-Match`; a guarded 409 is the generic reload path. A stored record of another operation is quarantined like a corrupt one. Device drafts are partitioned by SHA-256 of the returned login e-mail + branch, refuse credential-like values and are cleared only per context/partition.
- **Tests.** `pnpm --filter @loto/web test` runs the M1 tooling tests and Vitest (`vitest.config.ts` mirrors the app's TanStack alias). `pnpm --filter @loto/web test:e2e` starts its own disposable stack (`e2e/stack.ts`) and drives the installed Google Chrome; fixtures are `page.e2e.tsx` files (branch ones under `src/app/f/[branchId]/e2e/`) compiled only with `LOTO_WEB_E2E_FIXTURES=1` into `.next-e2e`; `e2e/branch-tabs.spec.ts` drives two or more pages of one browser context (one cookie jar) for the per-tab proof. Test pins: Vitest `5.0.3` (Vite `8.3.2`), jsdom `30.1.1`, Testing Library React `16.3.3` / DOM `10.4.2`, Playwright Test `1.64.0`.

## M3 design system (2026-10-22; review round 1 corrected, awaiting re-verification)

Evidence and the criterion map are in `docs/milestones.md` (Web M3). Consumption rules:

- **Tokens.** `src/theme/token-adapter.ts` is the only reader of `design/tokens/*.json` and the only raw-color/primitive exemption. A PostCSS plugin (`tooling/token-css.mjs`, first in `postcss.config.mjs`) expands the `@loto-tokens;` marker in `src/app/globals.css` at build time, so token values never live in a source CSS file. After a token change that adds or renames names, run `pnpm --filter @loto/web generate:tokens` (`lint` fails on drift of `src/theme/tokens.generated.ts`, which holds names only).
- **Class vocabulary.** Colors by semantic path (`bg-surface-default`, `text-text-muted`, `border-border-control`, `hover:bg-action-primary-bg-hover`); domain colors through `StatusBadge`/`DomainText`; spacing by scale or name (`p-4`, `px-inset-control-x`, `gap-stack-md`, `h-size-control-height`); `rounded-control|panel|badge`; `shadow-raised|floating`; breakpoints `medium:`, `wide:`, `xwide:` (em, so enlarged text switches earlier); roles as utilities `type-<role>`, `motion-<transition>` (reduced motion zeroes them) and `layer-<name>`. Tailwind's default palettes and scales are cleared: a fractional or default-scale class (`p-0.5`, `text-2xl`) produces nothing, and palette/primitive references (`bg-blue-600`, `color.primitive.*`) fail lint.
- **Direct variable references.** In inline styles or arbitrary values use the per-theme variables (`var(--loto-sem-…)`, `var(--loto-dom-…)`, `var(--loto-shadow-…)`), never `var(--color-…)`: Tailwind's `--color-*` resolve at `:root`, so they ignore a region pinned with `data-theme-scope`. A unit test scans `src/` for it.
- **Themes.** Device preference cookie `__Host-loto-theme` (`light`/`dark`/`system`, not `HttpOnly`, never cleared with the session) → `data-theme-preference` on `<html>` in the server render; Sistema is pure CSS (`prefers-color-scheme`). `ThemeProvider`/`ThemeControl` (`src/theme/`) change it live and sync tabs.
- **Components.** `src/components/ui/` (named exports, CVA + `cn()`), one file per contract family. Formatting goes only through the `PresentationFormat` port (`format-port.tsx`, `FormatProvider`): it has no Web implementation and throws when absent — M4 wires `@loto/core` once Shared M3 is accepted. Calendar values are `YYYY-MM-DD` strings (`calendar.ts`, no `Date`); "today" is the branch clock's, passed in. Popovers use the browser top layer (`popover="manual"`), dialogs the native modal `<dialog>`. One modal layer only: below a dialog (`useInDialog`), pickers that would open a compact bottom sheet open in the popover layer instead (`useCompactOutsideDialog`). The field context only **adds** state: a control's own `disabled`/`required`/`aria-invalid` are kept, and a disabled field or `disabled` prop closes every opening and choice path of a composite (select, searchable select, date, range, stepper, month).
- **Gallery.** `/styleguide` (`src/app/styleguide/page.styleguide.tsx`) exists in `next dev` and in an explicit `LOTO_WEB_STYLEGUIDE=1` build (`.next-styleguide`); an ordinary build has no such route (asserted by `tooling/check-bundles.mjs`). Its fixture formatter is finite reference tables, never imported elsewhere. `pnpm --filter @loto/web test:styleguide` builds and drives it (no API needed). Impeccable is not installed on this machine; refinement so far is manual and contract-based.
- **Pins added.** `axe-core 4.14.0` (devDependency, the version already resolved in the workspace) for the gallery's supplementary accessibility scan.
